# GUNZ 5.0.0 — Graduated Underlying Navigation Zones -
**ISA · Runtime · Library**

---

## 1. Overview

GUNZ is a deterministic, offline tool that takes a set of discrete‑clock parameters and produces a map of the most stable operating frequencies for any process that advances in fixed time steps. It produces compressed resonance maps — **stability topographies** — that describe optimal operating frequencies for any process governed by a fixed‑quantum clock. The format targets AI‑driven feedback loops, heterogeneous hardware deployment, and long‑term archival.

The specification is split into four independent layers:

- **GUNZ‑ISA** – bytecode format and instruction semantics (optional; an AI‑orchestration extension).
- **GUNZ‑RT** – execution runtime (memory, lanes, map generation).
- **GUNZ‑LIB** – library profiles, resonance map format, fingerprinting, and integrity.
- **GUNZ‑NET** *(future companion specification; currently under construction)*

A normative **Conformance** chapter specifies test vectors that any compliant implementation must satisfy.
**Normative vs. Informative** – Sections marked as *(Informative)* contain recommendations; all other sections are normative.

### 1.1 Architectural Intent and Conformance Profiles

GUNZ serves two distinct personas through a single specification:

| Persona | Profile | Description |
|---------|---------|-------------|
| **Systems Integrator** | Minimal (§1.2) | Embeds GUNZ as a pure C library. Constructs `ZoneBatch` or `ExecutionPlan` structures natively and passes them directly to the static‑lane evaluator. The bytecode interpreter may be entirely omitted. |
| **AI Orchestrator** | Full | Uses the bytecode ISA to generate scan programs dynamically. The VM provides a sandboxed execution environment with deterministic fuel bounds, memory isolation, and dynamic call dispatch (`PURE_CALL`) for autonomous exploration. |

The bytecode VM is an **orchestration and security boundary**, not an execution pipeline. For a fixed‑range sweep, the Minimal Profile suffices and delivers maximum performance with zero overhead. For untrusted AI‑driven exploration, the full profile adds the necessary resource controls.

*Trust boundaries (Informative)*
Unsandboxed `PURE_CALL` callbacks execute as native host code. A library profile supplying callbacks is therefore a trust boundary. Untrusted bytecode combined
with untrusted library callbacks can result in arbitrary native execution.

Sandboxed callbacks are required for canonical maps. Unsandboxed maps are non-canonical and carry no physical purity guarantee.

A valid `xxh3_64` checksum detects accidental corruption only. It does not imply that a map is safe to decode or that it was produced by a trusted source.

Imported maps are not inherently resource-bounded by their file size. A conformant runtime SHOULD enforce an implementation-defined maximum entry
count, maximum logical frequency span, maximum number of long-jump entries, and maximum decompressed interval count.

`xxh3_64` and XXH3‑128 are not tamper-evident or cryptographic identities. Canonical map authenticity requires an external signature or keyed MAC over the
map file.

Companion specifications, such as GUNZ-ORACLE, GUNZ-DRIFT, or GUNZ-DEWASTER, may introduce additional trust boundaries outside this core specification.

### 1.2 Minimal Conformance Profile (Static Lane, Trusted Code)

A conformant GUNZ implementation that targets the Minimal Profile **SHALL** implement the following:

- **Bytecode header parsing** (§2.2) – Accept only the static lane opcode set. Accept only the exact bytecode version `0x00040000` (major 4, minor 0). Reject any other version with `GUNZ_MALFORMED_BYTECODE`. Validate `magic`, `time_unit ≤ 12`, and `target_ticks ≥ 1`.

- **Static opcode subset** – Implement `HALT`, `ZONE`, `SKIP_ZONE`, `SCAN_RES`, and `EXPORT`. All other opcodes (including `LOOP`, `IMPORT`, `STREAM`, `PURE_CALL`) **SHALL** be rejected with `GUNZ_MALFORMED_BYTECODE`.

- **Resonance Evaluator** (§3.11) – Implement Phase 1 dense scan and Phase 2 stability width. Use integer arithmetic in the base time unit, half‑to‑even rounding (§4.5.1), and the deterministic standard deviation algorithm (§4.5.3). Enforce the plan's declared `max_scan_iterations` and `total_max_scan_iterations` (§3.4.1), failing with `GUNZ_ITERATION_LIMIT_EXCEEDED` if exceeded.

- **Map output** (§4.2, §4.2.1) – Produce 16‑byte map entries with canonical ordering, run‑length consolidation, and the long‑jump sentinel. Compute the canonical map data `xxh3_64` checksum over the **64‑byte header** and entries. Write a valid map header with `map_version = 0x0062`.

- **Error reporting** – Return `GUNZ_Result` codes as defined in §3.3. No additional diagnostic strings or structured error payloads are required.

- **Opcode validation** – A Minimal‑profile implementation **SHALL** reject any bytecode that contains an opcode not listed in the mandatory set, returning `GUNZ_MALFORMED_BYTECODE`. It **SHALL** also reject any `SCAN_RES` instruction with a non‑zero `flags` operand.

The Minimal Profile does **not** require:
- Dynamic lane opcodes, the bytecode VM, or fuel accounting.
- `PURE_CALL`, `STREAM`, `IMPORT`, or any callback infrastructure.
- Sandboxing, environment snapshots, or attestation.
- Thread safety or reference counting (single‑threaded use is assumed).  The `ExecutionPlan_Acquire` and `ExecutionPlan_Release` functions (§3.2) may be implemented as empty no‑op functions in a Minimal‑profile implementation.  Reference counting is optional for single‑threaded, trusted‑code environments.
- Streaming, sparse maps, long‑term scan, or compressed statistics.
- Structured diagnostic strings or machine‑readable error payloads.
- Generation of the `.gunzmeta` companion metadata file (see §4.6).
- Fuel accounting for static‑lane‑only implementations (see §3.5).  If the Minimal‑profile implementation supports the Dynamic Lane, full fuel accounting is required.
- Sandbox enforcement for callbacks (callbacks may be treated as ordinary functions).
- UUID‑v4 validation for `session_id` (any string or `null` is acceptable).
- Attestation signatures (`attestation_signature` may be omitted).
- Compressed statistics (`.gunzstatz`) in the normative LEB128 format (any lossless compression may be used, or none at all).

An implementation satisfying the Minimal Profile is fully conformant for all GUNZ programs that do not use dynamic opcodes, callbacks, or network features. Implementors **MAY** optionally support higher conformance tiers (dynamic lane, sandboxing, etc.) by following the normative sections of this specification.

## 2. GUNZ‑ISA (Bytecode)

The bytecode ISA enables AI agents to programmatically orchestrate complex multi‑zone scans, deterministic conditional logic via `PURE_CALL`, and library composition — all without runtime recompilation. The ISA's primary purpose is **orchestration**, not bulk scanning: a typical dynamic program issues a handful of `ZONE` instructions (each defining a frequency range to explore) and lets the static‑lane evaluator (§3.4) process millions of candidates. Implementations may support only static‑lane programs (rejecting dynamic programs at load time) and still be conformant; the bytecode VM is an optional extension for advanced autonomous exploration.

### 2.1 Binary Encoding

- All multi‑byte integers are encoded in **little‑endian** byte order.
- The bytecode is **tightly packed**; no padding bytes exist between fields.
- Operands immediately follow their opcode without alignment padding.
- The header is exactly 32 bytes for all version 4.x revisions. Future major versions may define a different header size; implementations **SHALL** reject unknown major versions.
- **Version handling:** The bytecode version stored in the header is `0x00040000` (major 4, minor 0). This value is fixed for the bytecode format defined by this specification and does not change with document revisions. An implementation **MUST accept only this exact version**. Any other version **SHALL** be rejected with `GUNZ_MALFORMED_BYTECODE`.
- Decoding is host‑endianness‑independent by construction: the bytecode is always little‑endian, and a correct decoder converts fields to host byte order. A mismatch of the `magic` field after correct little‑endian decoding **SHALL** be rejected.
- **Unaligned accesses (normative):** The bytecode stream is intentionally tightly packed; decoders **MUST** perform unaligned multi‑byte reads using portable methods that resolve to the correct little‑endian value on any host CPU. Failure to handle unaligned accesses correctly is non‑conforming. The following C snippet illustrates a safe 32‑bit little‑endian read that is independent of host endianness:

```c
/* Safely read a 32-bit little-endian integer from potentially unaligned memory,
   independent of host CPU endianness. */
static inline uint32_t le32(const uint8_t *p) {
    return (uint32_t)p[0] |
          ((uint32_t)p[1] << 8) |
          ((uint32_t)p[2] << 16) |
          ((uint32_t)p[3] << 24);
}
```

The evaluator's hot path operates on native‑aligned structures constructed at plan‑build time (§3.4.1), so unaligned accesses are a decoding concern only.

Capability checks are performed individually for capability-requiring flags:

- If bit 11 (`streaming`) is set and the scanner does not support streaming map output, the program SHALL be rejected with `GUNZ_INVALID_LIBRARY`.

- Bit 12 (`deduplicate`) is an optional cache hint. If unsupported, the implementation MAY ignore it.

- Bit 10 (`sparse_map`) is independent and is handled as specified above.

Reserved bits 13‑14 SHALL remain zero.

The header contains no runtime‑only state (e.g., dynamic/static lane classification); that is determined at load time (see §2.4).

### 2.3 Opcodes

**Opcodes not explicitly listed in this section are reserved and shall cause the decoder to reject the bytecode with `GUNZ_MALFORMED_BYTECODE`.** Reserved opcodes are assigned for future standard extensions.

#### 2.3.1 Static Lane Opcodes (0x00‑0x0E)

These opcodes are deterministic and may only be used by programs that satisfy the Static Lane criteria of §2.4. The column **Minimal** indicates whether the opcode is permitted in the Minimal Profile (§1.2).

| Opcode | Mnemonic | Operands | Description | Minimal |
|--------|----------|----------|-------------|---------|
| `0x00` | `HALT` | – | End of program (§2.3.3.1). | Yes |
| `0x01` | `LOOP` | `u16 count, u16 block_bytes` | Repeat a bytecode block (§2.3.3.2). | No |
| `0x02` | (reserved) | – | Reserved. | – |
| `0x03` | `ZONE` | `u32 freq_low, u32 freq_high` | Define a frequency range (§2.3.3.3). | Yes |
| `0x0C` | `SKIP_ZONE` | `u32 freq_low, u32 freq_high` | Skip a frequency range (§2.3.3.4). | Yes |
| `0x04` | `EXPORT` | `u32 object_id, u32 len` | Write map to object (§2.3.3.5). | Yes |

| `0x0B` | `SCAN_RES` | `u32 step_freq, u8 flags` | Set dense‑scan step size (§2.3.3.9). | Yes |
| `0x0D` | `ORACLE` | `u8 query_class, u32 max_block_time_inaccuracy, u8 max_jitter, u16 max_advance_regularity, u16 min_stability_width, u8 flags, u32 freq_low, u32 freq_high, u32 object_id` | Constraint‑query evaluation (see companion specification GUNZ‑ORACLE). All `object_id` values are 32‑bit indices into the runtime's private object table (§3.9); they are never raw memory addresses.

#### 2.3.2 Dynamic Lane Opcodes (0x10‑0x1F)

These opcodes are only available when the program does not meet the Static Lane criteria. They allow mutable state and non‑deterministic behaviour.

| Opcode | Mnemonic | Operands | Description |
|--------|----------|----------|-------------|
| `0x10` | `ADVANCE` | `u32 mult_num, u32 mult_den` | Temporarily override multiplier. Before executing this instruction, the VM shall verify that `mult_num ≠ 0` and `mult_den ≠ 0`. If either is zero, the VM shall halt immediately and return `GUNZ_MALFORMED_BYTECODE`. |
| `0x11` | `ROUND` | `u8 mode` | Temporarily override rounding. The mode values follow the same encoding as `round_mode` in the header (§2.2). **If `mode` is not in the range `0‑3`, the VM shall halt immediately and return `GUNZ_MALFORMED_BYTECODE`.** |
| `0x12` | `DELTA` | `u32 d_lo, u32 d_hi` | Set explicit delta pair as integer counts of quantum units. `d_lo` and `d_hi` are dimensionless integer counts; the evaluator multiplies them by `quantum` when computing block time. Both values must be non‑negative. All subsequent zone evaluations shall use these exact values as the per‑cycle deltas, overriding the normal derivation from the cycle time. The placement of `d_hi` cycles remains driven by the continuous cycle time; only the per‑cycle advances and block‑time sum are affected. **Lifetime and override detection:** Executing a `DELTA` instruction updates the override state.  The pair `(d_lo, d_hi) = (0,0)` is a *sentinel* that clears (deactivates) the override; any other pair activates the override with the supplied values.  Clearing the override restores the continuous‑delta calculation. Values must satisfy `d_lo ≤ d_hi`. The block‑time computation using `d_lo_ov` and `d_hi_ov` SHALL use 128‑bit unsigned arithmetic. Under the normative bounds on `N`, `d_lo_ov`, `d_hi_ov`, and `quantum`, no overflow can occur. No additional `N_max` validation is required for `DELTA`. If `d_lo > d_hi`, the VM SHALL halt immediately and return `GUNZ_MALFORMED_BYTECODE` |
| `0x13` | `LIBREF` | `u16 library_id` | Switch active library and reset mutable VM overrides. Pending `PURE_CALL` is preserved and resolved against the new library. |
| `0x14` | (reserved) | – | Reserved. |
| `0x15` | (reserved) | – | Reserved for future use. |
| `0x16‑0x1F` | (reserved) | – | Reserved. |

**`LIBREF` semantics.**

When `LIBREF` executes, the VM SHALL:

1. Verify that the requested `library_id` exists in the library table; otherwise halt with `GUNZ_INVALID_LIBRARY`.
2. Clear `ADVANCE`. The effective multiplier reverts to the §3.10 merged result using the bytecode header and the newly active library.
3. Clear `ROUND`. The effective rounding mode reverts to the bytecode header’s `round_mode`. The previous `ROUND` override, if any, is discarded and has no further effect.
4. Reset `DELTA` to `(0,0)`, deactivating the override.
5. Preserve any pending `PURE_CALL` specification. It is resolved against the newly active library when the next `ZONE` or `SKIP_ZONE` is executed.

These resets SHALL complete before the next VM instruction is processed.

*(Informative)* The mutable override state (`ADVANCE`, `ROUND`, `DELTA`) is cleared. Pending `PURE_CALL` is preserved and re‑resolved against the newly active library. Deferred operations already captured on the deferred‑operation queue, and the active streaming callback previously installed by `STREAM`, are not affected by `LIBREF`.

The `BRANCH` opcode has been removed to enable static analysis and eliminate branch dispatch in the hot loop; programs requiring runtime‑conditional logic must use `PURE_CALL`. All callbacks used by GUNZ programs must satisfy the purity requirements of §3.7; non‑deterministic callbacks are not permitted.

#### 2.3.3 Opcode Semantics (Normative)

This section provides the complete behavioural definition for every static‑lane opcode.  The compact table in §2.3.1 cross‑references these descriptions.

**2.3.3.1 `HALT`**  
End of program. Reaching the end of the bytecode without an explicit `HALT` is equivalent to executing `HALT` at that point.
For fuel accounting, an implicit end-of-bytecode HALT SHALL be treated exactly as an explicit HALT: it consumes 1 fuel if the remaining fuel is greater than 0, otherwise it consumes 0.

**2.3.3.2 `LOOP`**  
Repeat the following `block_bytes` bytes `count` times.  The block is self‑delimiting; decoders skip it in constant time by advancing `block_bytes`.  `block_bytes` must be ≤ 65535. `block_bytes` SHALL be greater than `0`. A `LOOP` instruction with `block_bytes == 0` is malformed and SHALL be rejected with `GUNZ_MALFORMED_BYTECODE`.  The LOOP instruction itself costs 1 fuel.  Instructions inside the block are executed `count` times; their fuel costs are incurred on each iteration.  **The LOOP instruction is exactly 5 bytes: one opcode byte, two `count` bytes, and two `block_bytes` bytes. Let `PC` be the byte offset of the `LOOP` opcode itself.**

The VM SHALL verify that:

```
PC + 5 + block_bytes ≤ total_length
```

If this condition does not hold, the VM SHALL halt immediately and return GUNZ_MALFORMED_BYTECODE. Equality is valid: the loop body may end exactly at the end of the bytecode buffer

**Note:** `LOOP` is allowed in Static Lane, but **not** permitted in Minimal Profile. In the Static Lane, nested `LOOP` instructions are expanded recursively at plan‑construction time (§3.4.1). In the Dynamic Lane, nested `LOOP` instructions are permitted and executed according to the Dynamic‑Lane Loop Execution model in §3.5.1. `count` SHALL be greater than `0`. A `LOOP` instruction with `count = 0` is malformed and SHALL be rejected with `GUNZ_MALFORMED_BYTECODE`.

**2.3.3.3 `ZONE`**  
Define a frequency range for evaluation.  Both boundaries are given in 10⁻⁵ Hz units.  The zone must satisfy `freq_low ≥ 1`, `freq_high ≥ 1`, and `freq_low ≤ freq_high`.  A frequency of `0` is rejected because it would cause division‑by‑zero when computing the cycle time `T`.  Frequencies as low as 1 (10⁻⁵ Hz) are permitted; invalid jitter points are automatically skipped.  All zones within the program — including `SKIP_ZONE` regions — must be strictly disjoint and grid‑aligned; see §3.3 for the definition.

**2.3.3.4 `SKIP_ZONE`**  
Skip evaluation of this zone.  The scanner emits entries covering the full skipped interval; see §3.11 for emission rules.  The same frequency constraints apply as for `ZONE`: `freq_low ≥ 1`, `freq_high ≥ 1`, `freq_low ≤ freq_high`, strict disjointness, and grid alignment (see §3.3).

**2.3.3.5 `EXPORT`**  
Write compressed map to the runtime object identified by `object_id`.  `len` is the expected number of bytes to write; if the actual map size differs, the operation shall still succeed as long as the map is valid.  Accidental-corruption detection and content identity are provided by the map's XXH3‑64 checksum, not by `len`.  In a static‑lane program, this operation is deferred (see §3.4.5).

**2.3.3.6 `IMPORT`**

Load an external map into the runtime object table. The runtime must ensure that the imported map is not mutated while the import is in progress; either a snapshot copy or an immutable object is used.

`len` is a hint for buffer allocation; the actual number of bytes read is determined by the map data. A mismatch between `len` and the actual map size does not cause failure.

To determine the canonical map layout, the decoder SHALL first verify that the imported map file contains at least the 64‑byte map header. If the file is shorter than 64 bytes, import SHALL fail immediately with `GUNZ_MALFORMED_BYTECODE`, and checksum validation SHALL NOT be attempted.

The canonical map layout is fixed: 64‑byte header followed by zero or more 16‑byte map entries.

After the canonical layout is known, the canonical map data `xxh3_64` checksum SHALL be validated before any other map validation. If the checksum is invalid, import SHALL fail immediately with `GUNZ_INVALID_LIBRARY`; threshold and parameter validation SHALL NOT be performed.

After checksum validation, import SHALL validate:

- `time_unit` against the plan’s `time_unit`;
- `map_version` against the runtime’s pinned `map_version`.

Any mismatch SHALL fail with `GUNZ_INVALID_LIBRARY`.

After checksum and version validation, import SHALL reject any stored detrimental threshold equal to `0` with `GUNZ_MALFORMED_BYTECODE`, unless a converter has already normalised the value to the resolved non‑zero threshold.

The imported map SHALL then be fully decoded and validated according to §4.2.1 and §6. This validation SHALL include:

- all header field semantics;
- `effective_step` ≥ 1; a value of `0` SHALL be rejected with `GUNZ_MALFORMED_BYTECODE`;
- `evaluated_candidate_count` consistency with the decoded entry stream, as specified in §6;
- reserved byte checks, including any reserved bytes;
- entry‑flag, long‑jump, delta, and structural validation.

Any reserved-bit, entry-flag, long-jump, delta, or structural violation SHALL cause the import to fail with `GUNZ_MALFORMED_BYTECODE`.

In a static‑lane program, this operation is deferred (see §3.4.5).

**2.3.3.7 `STREAM`**  
Set streaming callback for batched map output. The callback must satisfy the general callback ABI of §3.6 and the streaming callback contract of §3.6.1. Full `PURE_CALL` purity restrictions do not apply to streaming callbacks, subject to the limitations of §3.6.1. The runtime performs actual I/O on separate worker threads; the callback itself must not block and must complete within a deterministic, constant‑time budget relative to its arguments. 

 If the streaming callback cannot consume entries at the rate they are produced, the runtime shall pause the evaluator until buffer space becomes available. This pause is a backpressure mechanism only. It does not require releasing per-invocation `ScratchArena` resources, because §3.1 makes each invocation the exclusive owner of its arena; no shared arena locks exist.

Any shared ring-buffer reference management is implementation-defined, but the implementation SHALL ensure that pausing the evaluator cannot deadlock with consumer/flusher threads.  The pause is not considered a callback execution; it is a backpressure mechanism to bound memory usage.  If `STREAM` appears multiple times in a program, only the most recently **processed** `callback_id` in the deferred‑operation queue is active. Deferred `STREAM` operations are executed in capture order (§3.4.5, §3.5), so the active streaming callback at any point during deferred processing is the one most recently installed by a preceding `STREAM` in that queue.

**2.3.3.8 `PURE_CALL`**  
Invoke a deterministic external function (see §3.7).  The instruction length is `6 + 4 × arg_count` bytes, with each `u32` argument following the `arg_count` byte in little‑endian order.  `arg_count` must be ≤ 16; a value > 16 shall cause the bytecode to be rejected with `GUNZ_MALFORMED_BYTECODE`.

A pending `PURE_CALL` specification is not cleared by intervening non-zone instructions. In particular, `SCAN_RES` does not clear a pending `PURE_CALL`. The pending specification is consumed only by the next `ZONE` or `SKIP_ZONE` in execution order, or replaced by a subsequent `PURE_CALL`. `LIBREF` preserves the pending specification and re-resolves it against the newly active library.

When a `PURE_CALL` is captured and attached to a `ZONE`, the callback is invoked **once per evaluated candidate** by the resonance evaluator, as described in §3.11. It may read the candidate context buffer and use it as temporary scratch space. All writes by the callback are ignored for map generation.

**2.3.3.9 `SCAN_RES`**  
Set the dense‑scan step size in 10⁻⁵ Hz units.  A value of 0 means "use the normative default of 1" (i.e., 10⁻⁵ Hz). 

 If a program never emits a `SCAN_RES` instruction, the evaluator behaves as if `effective_step = 1` (10⁻⁵ Hz).  A `SCAN_RES` with `step_freq = 0` is equivalent to the absent case.  The `flags` operand is reserved and must be `0x00`; a non‑zero value shall cause the bytecode to be rejected with `GUNZ_MALFORMED_BYTECODE`.  

The `effective_step` is a **program‑wide constant**.  The bytecode loader **SHALL** scan the entire bytecode (including any bytecode that may be expanded from `LOOP` instructions) and reject the program with `GUNZ_MALFORMED_BYTECODE` if any `SCAN_RES` opcode is found at a byte offset greater than the offset of the first `ZONE` or `SKIP_ZONE` instruction.  This check is performed statically before execution begins; it applies equally to static‑lane and dynamic‑lane programs.

For programs containing `LOOP` instructions, the loader SHALL determine the effective inline instruction sequence by either:

 – literal expansion, subject to the implementation-defined expansion limit of at least `2²⁰` bytes specified in §3.4.1, or

 – structural analysis of loop nesting and iteration counts.

If structural analysis is used, it SHALL produce exactly the same effective instruction sequence as literal expansion would produce when the expansion limit is not exceeded. The `SCAN_RES` ordering check SHALL then be applied to that effective sequence, not to the raw pre-expansion byte offsets.

A `SCAN_RES` with `step_freq = 0` is considered present for the purpose of the ordering check. It establishes the default `effective_step` of `1` but does not cause the program to be treated as if no `SCAN_RES` instruction existed.

The effective step size is recorded in the map header's `effective_step` field (see §4.2.1).

**2.3.3.10 `ORACLE`**  
The `ORACLE` opcode performs a constraint‑query evaluation according to the companion specification **GUNZ‑ORACLE**.  The instruction captures the current system state (multiplier, rounding mode, delta pair, `effective_step`, and any pending `PURE_CALL` specification) and the given parameters, including the `object_id`.  

In both static‑lane and dynamic‑lane programs, `ORACLE` is **always deferred**: it is appended to a deferred‑operation queue and executed after the zone scan and before any map exports.  When executed, the oracle evaluates the query range and stores the resulting Constraint Query Result (CQR) in the runtime object table at the specified `object_id`.  If the object table entry already exists, it is overwritten.

The ORACLE instruction is exactly 24 bytes. Its packed little‑endian operand layout is defined in the companion GUNZ‑ORACLE specification.

The effect of `ORACLE` on the live pending `PURE_CALL` specification — whether it is preserved, consumed, or otherwise modified — is defined by the GUNZ‑ORACLE
companion specification. Core GUNZ specification SHALL NOT assign additional preserve/clear semantics to that interaction.

**2.3.3.11 `EXPORT_ORACLE`**  
The `EXPORT_ORACLE` opcode writes the CQR data from the object table entry identified by `object_id` to a `.gunzoracle` file.  The second operand `reserved` must be `0x00000000`; a non‑zero value shall cause the bytecode to be rejected with `GUNZ_MALFORMED_BYTECODE`.  If the object does not contain a valid CQR, the operation fails with `GUNZ_INVALID_OBJECT`.

Implementations that do not support the GUNZ‑ORACLE companion shall reject opcodes `0x0D` and `0x0E` with `GUNZ_MALFORMED_BYTECODE`.  For any implementation that supports `ORACLE`, the `flags` operand of the `ORACLE` instruction **must** be `0`; a non‑zero value shall cause the bytecode to be rejected with `GUNZ_MALFORMED_BYTECODE`.

The `EXPORT_ORACLE` instruction is exactly 9 bytes.

### 2.4 Lane Selection

*(Informative)* Static‑lane classification is independent of conformance profile. A program containing only static opcodes remains Static Lane, even if it uses static opcodes outside the Minimal‑profile mandatory subset, such as `LOOP`, `ORACLE`, or `EXPORT_ORACLE`. A Minimal‑profile implementation may reject those optional static opcodes with `GUNZ_MALFORMED_BYTECODE` because they are outside its mandatory static subset.

A program is **Static Lane** if:

- It contains **only** opcodes from the explicitly enumerated set `{0x00, 0x01, 0x03, 0x04, 0x05, 0x07, 0x0A, 0x0B, 0x0C, 0x0D, 0x0E}` (the static opcodes listed in §2.3.1, excluding all reserved opcodes including `0x02`, `0x06`, `0x08`, and `0x09`).

- The capability-requiring flags defined in §2.2 are supported by the scanner. If a required capability is not supported, the loader SHALL reject the program with `GUNZ_INVALID_LIBRARY`.

- **No** Dynamic Lane opcodes are present. If any opcode from the Dynamic‑lane set appears, the program is classified as Dynamic‑lane regardless of the static‑lane opcode subset.

Otherwise the program is executed in the Dynamic Lane. The lane classification is runtime metadata; it is **never serialized** in the bytecode.  
*Note: Although `LOOP` (0x01) is permitted in Static‑Lane programs, Minimal‑Profile implementations are not required to support it; see §1.2 and §2.3.1.*

*(Informative)* Opcodes `0x0D` (ORACLE) and `0x0E` (EXPORT_ORACLE) are part of the static‑lane opcode set; a program containing only these plus other static‑lane opcodes remains Static Lane.  They may also appear in dynamic‑lane programs without changing classification.

## 3. GUNZ‑RT (Runtime)

### 3.1 Memory Model


- **Arena:** `mark()`/`rewind()` resets the arena to a previous point; no data is touched. Rewind is O(1) and does not modify freed memory. Objects allocated after a mark must not outlive the matching rewind. No pointer obtained from the arena may be dereferenced after a `rewind` of the same arena.

- **Pointers:** Hot paths use native pointers. Serialised maps and the global library table use 32‑bit indices.

- **Cache‑line padding:** All shared mutable structures (ring‑buffer indices, arena metadata fields) occupy distinct cache lines. Thread‑local builders should be aligned to separate cache lines.

- **`ScratchArena` is strictly per‑invocation.** Each call to `ExecutionPlan_Run` receives its own `ScratchArena`; no sharing across threads occurs. This guarantees that the hot loop never requires atomics for arena access.

### 3.2 ExecutionPlan Lifecycle

- Plans are published with **release** semantics and read with **acquire** semantics. They are immutable after publication.

- `ExecutionPlan` objects are immutable and may be accessed concurrently by any number of threads. Implementations must ensure that a plan is not freed while any thread still holds a reference to it.

- **Reference counting:** Each `ExecutionPlan` carries an atomic, thread‑safe reference count. Threads call `ExecutionPlan_Acquire(plan)` before using a plan, and `ExecutionPlan_Release(plan)` when finished. When the count reaches zero the plan is freed. `ExecutionPlan_Run()` does not implicitly acquire or release a reference; the caller must hold a valid reference throughout the execution.

- **Crash semantics:** If a thread terminates abnormally while holding a reference, that reference is considered leaked and the plan will not be freed until the process exits or an out‑of‑band recovery mechanism is invoked. Implementations should provide a mechanism to detect such leaks and log them; they are not required to reclaim the memory automatically. An implementation may, optionally, offer an administrative API to force release of leaked references with appropriate attestation.

- **Epoch‑based schemes** are discouraged because a single stalled thread can prevent all reclamation, leading to unbounded memory growth. If an implementation uses such a scheme, it must document how the stall problem is avoided and must still guarantee that `ExecutionPlan` objects are eventually freed.

- Plans remain valid until freed, even if evicted from a plan cache.

### 3.3 ExecutionPlan Interface

```c
typedef struct ExecutionPlan ExecutionPlan;   // opaque handle
typedef struct ScratchArena ScratchArena;     // opaque, exclusive to one invocation

typedef enum {
    GUNZ_OK = 0,
    GUNZ_CALLBACK_FAILED = 1,
    GUNZ_ARENA_EXHAUSTED = 2,
    GUNZ_INVALID_LIBRARY = 3,
    GUNZ_MALFORMED_BYTECODE = 4,
    GUNZ_FUEL_EXHAUSTED = 5,
    GUNZ_INVALID_OBJECT = 6,
    GUNZ_ITERATION_LIMIT_EXCEEDED = 7,
    GUNZ_SANDBOX_VIOLATION = 8,
} GUNZ_Result;
```

*Note:* `GUNZ_FUEL_EXHAUSTED` is only meaningful for implementations that implement fuel accounting.  `GUNZ_SANDBOX_VIOLATION` is defined for Full‑profile conformance.  Minimal‑profile implementations may never return this code, but they **SHALL** include it in the enumeration to maintain API compatibility.

```c
void          ExecutionPlan_Acquire(ExecutionPlan *plan);
void          ExecutionPlan_Release(ExecutionPlan *plan);
GUNZ_Result   ExecutionPlan_Run(const ExecutionPlan *plan,
                                const ZoneBatch *zones,
                                SparseMapBuilder *out,
                                ScratchArena *scratch);
void          SparseMapBuilder_Release(SparseMapBuilder *builder);
```

`ScratchArena` is owned by the caller and must not be accessed concurrently.  
An `ExecutionPlan` contains no runtime feature‑selection branches; all invariant properties are resolved at construction time. The hot loop contains only data‑dependent operations.

`SparseMapBuilder_Release` frees all internal resources held by the builder, including any persistent buffers allocated for map‑entry storage.  The caller shall invoke `SparseMapBuilder_Release` when the builder is no longer needed; after this call, the builder handle is invalid.  
`SparseMapBuilder_Release` does not affect the `ScratchArena` passed to `ExecutionPlan_Run`; it releases only the builder's internally held persistent resources.  The `ScratchArena` remains the caller's responsibility.

*(Informative)*  The `SparseMapBuilder` handle passed to `ExecutionPlan_Run` is created by the caller through an implementation‑defined mechanism.  A typical C API would provide a function such as `SparseMapBuilder_Create()` that allocates and returns an empty builder; the caller then passes this handle to `ExecutionPlan_Run` and later releases it with `SparseMapBuilder_Release`.  The exact name and signature are left to the implementation.

**`ZoneBatch`** is an opaque container of zero or more zones to be evaluated. Each zone is a triple `(freq_low, freq_high, evaluator_id)`. The plan must document the mapping from `evaluator_id` to the specific evaluator implementation. Zones in a batch may be evaluated in any order; the final output must be identical regardless of order. Implementations must provide a way to populate a `ZoneBatch` from the bytecode's `ZONE` and `SKIP_ZONE` instructions; the exact mechanism is implementation‑defined but must preserve determinism. A `SKIP_ZONE` adds the zone boundaries to the batch with a special marker; no evaluator is invoked for these zones.

**`effective_step`** is the program‑wide dense‑scan step size in 10⁻⁵ Hz units. It is resolved as follows:

- In the bytecode / plan‑construction context: from the last `SCAN_RES` before the first zone. `SCAN_RES = 0` or absent resolves to `1`.
- If the program contains no `ZONE` or `SKIP_ZONE` instructions, `effective_step` SHALL be the value of the last `SCAN_RES` instruction if one exists, otherwise `1`. In this no‑zone case, `effective_step` is recorded in the map header but does not influence evaluator behavior because no candidates are evaluated.
- In the map‑decoding context: directly from the `effective_step` field as specified in §4.2.1.

This definition is authoritative for all normative uses of the dense‑scan step size. `step_freq` appears only as the bytecode `SCAN_RES` operand. It is not a map header field and is not used in map decoding or normative formulas.

**Terminology.**
- `step_freq` is the bytecode `SCAN_RES` operand. It is an encoding that may be `0` to request the default `effective_step` of `1`. It is not a map header field.
- `effective_step` is the resolved numeric dense‑scan step size actually used by the evaluator, decoder, and all normative formulas. It SHALL be `≥ 1`.
- In the map header, `effective_step` is stored directly as a `u32` at offsets 40–43. The stored value is the resolved `effective_step`, with no further resolution step.
- Normative formulas SHALL use `effective_step`. `step_freq` appears only where the bytecode `SCAN_RES` operand or its defaulting rule is described.
**Zone grid alignment (normative).**
 Let `base_freq` be the minimum `freq_low` among all `ZONE` and `SKIP_ZONE` instructions in the program. If the program contains no `ZONE` or `SKIP_ZONE` instructions, `base_freq` SHALL be defined as `0`, and the alignment condition is vacuously satisfied.

*(Informative)* This stronger alignment requires every zone boundary to lie on the same global grid anchored at the minimum zone start. It simplifies map reconstruction and is intentional.

Every `ZONE` and `SKIP_ZONE` SHALL satisfy both:

- `(freq_low  − base_freq) % effective_step == 0`
- `(freq_high − base_freq) % effective_step == 0`

If either condition is not met, plan construction SHALL fail with `GUNZ_MALFORMED_BYTECODE`.

**Normative Requirement:** All zones within a single bytecode program — whether defined by `ZONE` or `SKIP_ZONE` — SHALL be strictly disjoint. Zones are strictly disjoint if and only if, when sorted in ascending order by `freq_low`, each zone satisfies:

`freq_low_next ≥ freq_high_prev + effective_step`

where `effective_step` is defined above. This requirement applies equally to `ZONE` and `SKIP_ZONE` instructions. If the program contains any zones that violate this condition, the plan constructor SHALL reject it with `GUNZ_MALFORMED_BYTECODE`.

**This permits adjacency: when equality holds, the zones are placed end‑to‑end with no intervening frequencies.**

*(Informative)* The disjointness condition requires:

  freq_low_next ≥ freq_high_prev + effective_step

When equality holds, the zones are adjacent: the next zone starts at the first grid frequency after the previous zone, with no intervening candidates. There is no requirement for an additional gap beyond this step boundary. This rule simplifies deterministic map reconstruction.

*(Informative)* The `effective_step` for a zone is the program‑wide value captured from the most recent `SCAN_RES` instruction (or the default of 1 if none).  The `effective_step` is a program‑wide constant; it is not affected by any `SCAN_RES` instruction that appears after the first `ZONE` or `SKIP_ZONE`.

**`SparseMapBuilder`** is an opaque, thread‑local object that accumulates map entries. Implementations must provide a function to append a map entry in either serialised 16-byte form or an equivalent absolute-frequency internal form, and to finalise the map header.

The canonical 16-byte serialized entry, including `freq_delta_start`, SHALL be produced only by the final map serialization phase, after gap insertion and sparse emission.

The `SparseMapBuilder` shall not rely on the `ScratchArena` for storage of the accumulated map entries.  Its contents must survive a `ScratchArena` rewind.  If the implementation uses arena memory for builder‑internal storage, it shall copy the complete entry data to a persistent buffer before any arena rewind occurs.  The partial map returned on error shall be fully valid and readable regardless of the arena state.

**Canonical ordering:** 
The `SparseMapBuilder` SHALL assemble intervals in ascending `absolute_start` order, as defined in the absolute-frequency
normalisation below.

During per-thread assembly, serialized `freq_delta_start` is not meaningful; ordering and gap detection use absolute frequencies only.

When multiple threads evaluate zones concurrently, each thread writes to its own `SparseMapBuilder`. Before the global K-way merge, each per-thread builder SHALL order its accumulated intervals in ascending `absolute_start` order.

The global merge SHALL then emit entries in strictly ascending `absolute_start` order. Because zones within a batch are strictly disjoint and
grid-aligned, `absolute_start` collisions cannot occur. This ordering must be preserved even when splitting entries due to `run_length` overflow.

For future extensions that introduce such collisions, the normative tie rule will be defined at that time; no current tie rule is imposed.


**Absolute-frequency normalisation (normative).**
Before gap detection and placeholder insertion, every entry produced by a per-thread `SparseMapBuilder` SHALL be represented in absolute frequencies on the global grid anchored at `base_freq`.

For this phase, each entry SHALL carry:

- `absolute_start` — the absolute frequency of the first candidate or gap position represented by the entry.
- `absolute_end` — the inclusive absolute frequency of the last candidate or gap position represented by the entry.

Absolute frequencies in this phase SHALL use at least 64-bit unsigned arithmetic. Long-jump endpoints may exceed the `u32` range of the serialized `freq_low` and `freq_high` fields.

For every entry:

```
  `absolute_end ≥ absolute_start`
```

This is an inclusive frequency relationship and gives implementations a simple consistency check.

All `absolute_start` and `absolute_end` values SHALL lie on the global frequency grid anchored at `base_freq`. Equivalently, for every absolute frequency `F` in this phase:

```
  `(F − base_freq) % effective_step == 0`
```

Differences between grid positions are exact multiples of `effective_step`.



`freq_delta_start` is **not** used during this absolute-frequency phase.

- For long-jump entries, `freq_delta_start` remains the type tag.
- For normal entries, `freq_delta_start` is temporarily unspecified until final serialization.

**Per-thread builder current.**
Each per-thread builder SHALL maintain an absolute current frequency:

- When a builder starts or resumes a zone, its current SHALL reset to that zone’s absolute `freq_low`.
- After any non-long-jump entry — an evaluated normal interval or a `FLAG_INVALID` normal entry — the current advances by `run_length × effective_step`.
- After a long-jump entry, the current advances by the decoded gap.

Equivalently:

- For any non-long-jump entry:

  `absolute_start = zone.freq_low` for the first entry in a zone; otherwise `absolute_start = previous.absolute_end + effective_step`.

- For a long-jump entry, `absolute_start` is the builder’s current absolute frequency immediately before that long-jump.

A zone reset may leave a frequency discontinuity: the new zone’s `freq_low` may be greater than `previous.absolute_end + effective_step`.

Such a discontinuity is not an error and SHALL NOT cause a per-thread builder to emit an inter-zone long-jump. It SHALL be handled later by the global gap-detection phase.

**Entry endpoints.**
For an evaluated normal interval or a `FLAG_INVALID` normal entry:

  `absolute_start = current_before_emission`

  `absolute_end = absolute_start + (run_length − 1) × effective_step`

For a long-jump entry:

  `absolute_start = current_before_emission`

  `absolute_end = absolute_start + gap − effective_step`

The long-jump endpoint is inclusive, as required by §3.3 and §4.2.

**Per-thread ordering before merge.**
Each per-thread `SparseMapBuilder` SHALL order its accumulated entries in ascending `absolute_start` order before participating in the K-way merge.

If a builder processed multiple zones out of frequency order, it SHALL sort its entries by `absolute_start` after zone completion and before the merge.

**Global merge current.**
During the global K-way merge and subsequent gap insertion, the runtime SHALL maintain a single absolute current, `global_merge_current`, initialised to `base_freq`.

After each emitted entry, `global_merge_current` advances by the same rules as a per-thread builder:

- by `run_length × effective_step` for a non-long-jump entry;
- by the decoded gap for a long-jump entry.

The `global_merge_current` pointer used for K-way merge emission, for gap detection, and for excluded-zone splice insertion SHALL be the same logical absolute-frequency pointer. There is only one global merge current during the global merge and gap-insertion phase.

After gap insertion and optional sparse emission, `global_merge_current` continues as the decoder-style current used by final serialization.

**Special-zone boundary insertion.**
The global merge/gap-detection phase SHALL maintain one ordered cursor over all special zones — excluded zones and `SKIP_ZONE` zones — in ascending `freq_low` order.

At each step, the next special zone is the one with the smallest `freq_low`.

Special-zone boundaries SHALL be processed in ascending absolute-frequency order, interleaved with evaluated per-thread entries by `absolute_start`.

At each merge step, compare:

  `next_evaluated.absolute_start`

with:

  `next_special.freq_low`

Process whichever is smaller.

If the values are equal, process the special zone first.

Ties of this kind are permitted by the grid-alignment and disjointness rules.
If a future extension creates an actual overlap, that overlap SHALL be rejected before merge processing.

Classification precedence SHALL be:

  excluded > skipped > evaluated

A zone marked excluded by the global iteration pre-pass SHALL be processed only under the excluded-zone rules, even if its bytecode opcode was `SKIP_ZONE`.
It SHALL NOT be processed as a skipped zone.

**Excluded-zone processing.**
For an excluded zone:

1. Insert its type-0 long-jump sequence at the current `global_merge_current`, either when:

   `global_merge_current == excluded_zone.freq_low` or before the next per-thread entry whose `absolute_start` exceeds `excluded_zone.freq_low`.

   If no later per-thread entry exists whose `absolute_start` exceeds the excluded zone’s `freq_low`, insert the excluded-zone sequence after the last per-thread entry.

2. The total gap is:

   `gap_total = freq_high + effective_step − global_merge_current`

3. Apply the universal long-jump splitting rule of §4.2 if
   `gap_total > max_lj_gap`.

4. For each emitted long-jump entry:

   `absolute_start = global_merge_current`

   `absolute_end = absolute_start + gap_entry − effective_step`

   `global_merge_current = global_merge_current + gap_entry`

5. After the full excluded-zone sequence:

   `global_merge_current = freq_high + effective_step`

6. When `global_merge_current < freq_low` at insertion time, the sequence covers both the inter-zone gap and the excluded zone as a single unevaluated interval. No separate `FLAG_SKIPPED` entry or long-jump SHALL be emitted for the inter-zone gap before this sequence.

**Skipped-zone processing.**

For a `SKIP_ZONE` that is not excluded:

1. If `global_merge_current < freq_low`, emit one or more type-0 long-jump entries covering:

   `gap_to_zone = freq_low − global_merge_current`

   using the universal long-jump splitting rule of §4.2 if
   `gap_to_zone > max_lj_gap`.

   This alignment gap SHALL use type-0 long-jump entries even if the candidate count is 65535 or fewer. It SHALL NOT be represented by a `FLAG_SKIPPED`
   placeholder.

2. Emit the skipped-zone representation:

   `candidate_count = (freq_high − freq_low) / effective_step + 1`

   - If `candidate_count ≤ 65535`, emit a single `FLAG_SKIPPED` placeholder with zero metrics and:

     `freq_delta_start = 0`
     `run_length = candidate_count`

   - Otherwise emit one or more type-0 long-jump entries covering:

     `gap_zone = freq_high + effective_step − freq_low`

     using the universal long-jump splitting rule of §4.2 if
     `gap_zone > max_lj_gap`.

3. Set:

   `global_merge_current = freq_high + effective_step`

The generic inter-zone gap-detection rules SHALL NOT cover any interval already represented by:

- an excluded-zone long-jump sequence, or
- a skipped-zone alignment long-jump, or
- a skipped-zone placeholder, or
- a skipped-zone long-jump sequence.

**Final serialization boundary.**
The absolute-frequency representation is an internal merge-phase construct. It is not serialized.

Final `freq_delta_start` values are assigned or recomputed only after gap insertion and optional sparse emission, in the serialization order defined by §4.2.

During per-thread assembly, an implementation MAY store entries in this absolute-frequency representation rather than as completed 16-byte serialized entries. The 16-byte serialized entry, including `freq_delta_start`, SHALL be produced only by the final map serialization phase defined in §3.3 and §4.2.

*(Informative)* This rule closes a previously under-specified coordinate-system boundary. The merge and gap-detection rules reuse decoder terms such as `current + freq_delta_start`; without this normalisation phase, whether `current` is per-thread or global is ambiguous. Because different `SparseMapBuilder`s may start at different zone origins and may process disjoint zones, raw per-thread deltas are not directly comparable.

Absolute-frequency normalisation makes the invariant explicit: merge ordering and gap detection operate in absolute frequency coordinates; serialized deltas are computed only afterwards. This adds deterministic bookkeeping but does not restrict evaluation order, vectorisation, or memory layout.

**If, after all entries from all builders have been ordered, the ending frequency of an entry is less than the starting frequency of the immediately following entry, the merge shall insert a placeholder covering the unscanned interval.  The ending frequency of an entry is determined as follows:**

- **For a long-jump entry** (identified by `run_length == 0` and `block_time_inaccuracy == 0`): the ending frequency is `absolute_start + gap − effective_step`, where `absolute_start` is the long-jump’s absolute starting frequency — `global_merge_current` immediately before that long-jump in the absolute-frequency phase — and `gap` is the long-jump’s decoded gap value.

In serialized form, this `gap` is the signed 64-bit integer decoded from bytes 8–15 of the entry. In the absolute-frequency phase, it is the gap carried directly by the entry.

This `gap` is **already expressed in 10⁻⁵ Hz units** and must not be multiplied by `effective_step`. The gap SHALL be strictly positive and an exact multiple of `effective_step`; see §4.2 for the normative rule.

The long-jump ending frequency is **inclusive**: it is the last grid candidate covered by the long-jump interval.

- **For all other entries** — evaluated normal intervals, `FLAG_SKIPPED` placeholders, and `FLAG_INVALID` normal entries — the ending frequency is:

  `absolute_start + (run_length − 1) × effective_step`

where `absolute_start` is the entry’s absolute starting frequency assigned during absolute-frequency normalisation.

`freq_delta_start` SHALL NOT be used during gap detection.

This ending frequency is inclusive: it is the last grid candidate represented by the entry.

- **For a normal entry**, the absolute starting frequency is its `absolute_start`. The final serialized `freq_delta_start` is assigned only during final serialization.

- **For a long-jump entry**, `freq_delta_start` is the type tag and SHALL NOT be used in frequency reconstruction. In the absolute-frequency phase, the long-jump starts at `global_merge_current` immediately before it. In final serialization, it starts at the global decoder current.

Let `Δ` be the frequency difference between the starting frequency of the next entry and the ending frequency of the previous entry (both in 10⁻⁵ Hz units). Because all zone boundaries are grid‑aligned, `Δ` is always an exact multiple of `effective_step`.

If `Δ == effective_step`, there is no skipped candidate between them; no placeholder is inserted.

If `Δ > effective_step`, the unscanned candidates are located at frequencies:

`previous_end + effective_step, previous_end + 2·effective_step, …, next_start − effective_step`

The number of such candidates is:

`gap_candidates = (Δ / effective_step) − 1`

Because `Δ > effective_step`, `gap_candidates ≥ 1`.

If `gap_candidates ≤ 65535`, the merge SHALL emit a single `FLAG_SKIPPED` entry with:

`freq_delta_start = 0`
`run_length = gap_candidates`

The placeholder starts at `global_merge_current`, which is the first unscanned candidate after the previous entry.

If `gap_candidates > 65535`, the merge SHALL emit one or more type-0 long-jump entries covering:

`gap = Δ − effective_step`

using the universal long-jump splitting rule of §4.2 if `gap > max_lj_gap`.

No `FLAG_SKIPPED` entries SHALL be emitted for the same interval when `gap_candidates > 65535`.

After a placeholder or long-jump entry is inserted, `global_merge_current` is advanced to `next_start`.

During final serialization, an immediately following normal entry SHALL be emitted with `freq_delta_start = 0`; no positive delta is assigned by gap insertion itself.

This normalisation applies to entries inserted or normalised by the merge/gap insertion process.

Sparse emission under §4.2 SHALL be applied after merge and gap insertion.
Sparse emission may set positive `freq_delta_start` values only where `map_flags.sparse_map == 1`.

A positive delta SHALL NOT be assigned to the immediately following evaluated normal entry after a long-jump boundary; at least one omitted interval must have accumulated after the long-jump flush before a later evaluated normal entry may receive a positive delta.
 This exception applies only when `map_flags.sparse_map == 1`. In dense maps, the merge‑normalisation rule remains unconditionally in force.

Excluded zones SHALL be processed exclusively by the Special-zone boundary insertion subsection above. They SHALL NOT be reprocessed by the generic inter-zone gap-detection rules.

Because an excluded-zone sequence starts at `global_merge_current` immediately before the excluded zone, the generic gap detection treats `Δ == effective_step`
between the preceding entry and that special-zone sequence, and no separate inter-zone gap entry SHALL be inserted.

This guarantees that the final map contains no implicit frequency discontinuities between independently evaluated zones.

*(Normative)* **Threading contract:**
 Zones within a `ZoneBatch` are independent and may be evaluated in parallel by separate threads. Each zone **must** be processed by a single thread; no intra‑zone parallelism is permitted. The deterministic merge of per‑thread maps is an implementation responsibility, but the final output must be identical regardless of the thread scheduling. Arena‑allocated pointers obtained during a scan are invalidated after `rewind()` and must not be dereferenced thereafter. The merge shall use a streaming K‑way merge algorithm whose peak memory does not exceed O(K) plus the size of a single entry, where K is the number of per‑thread builders.

**Map assembly pipeline (normative).**
The final map SHALL be produced in the following order:

1. Phase 1 and Phase 2 produce per‑candidate metrics for each included zone.
2. Detrimental-mode `FLAG_AVOID` marking SHALL be applied to evaluated intervals as defined in §3.11.
3. Each `SparseMapBuilder` emits its per‑candidate interval stream as an unconsolidated stream. That stream includes evaluated intervals,
   `FLAG_INVALID` normal entries, and long‑jump entries produced by the evaluator.
4. The per‑thread streams are deterministically merged into one ascending dense interval stream.
5. Inter‑zone gap placeholder insertion is applied as defined above.
6. If sparse emission is active for the plan — either because the bytecode program set header bit 10 and the implementation accepted it, or if a native `ExecutionPlan` configuration requested it — sparse emission SHALL be applied to the dense stream as defined in §4.2.
   An implementation that does not support sparse maps SHALL reject the program or plan before this pipeline as required by §2.2.
7. Final map‑entry consolidation is applied as defined in §3.11.

The evaluated portion of the stream delivered to sparse emission SHALL consist of unconsolidated evaluated candidate intervals. The stream as a whole may also contain `FLAG_INVALID` normal entries, `FLAG_SKIPPED` placeholders, and long-jump entries, as specified in §4.2. Zone‑local consolidation, if used internally, SHALL be reversible and SHALL NOT be visible in that stream.

After sparse emission, `map_flags.sparse_map` SHALL be `1` if and only if sparse emission actually omitted at least one qualifying interval, whether encoded as a positive `freq_delta_start` or one or more type‑1 long‑jump entries. Otherwise it SHALL be `0`.

**Sparse‑omission ordering (normative).** 
Sparse‑map omission SHALL be applied only **after** per‑thread map merging and **after** inter‑zone gap placeholder insertion.

Positive `freq_delta_start` values are produced only by the §4.2 sparse‑emission algorithm, which runs after the pre‑sparse merge and gap‑detection phase. Therefore they do not exist on evaluated normal intervals during merge and gap detection. If such a positive delta is encountered in this earlier phase, the stream is malformed and SHALL be rejected with `GUNZ_MALFORMED_BYTECODE`; it SHALL NOT be treated as a sparse‑omitted interval at this stage.

**Run‑length overflow:** 
The `run_length` field in a map entry is a `u16` (0–65535). When consolidating consecutive identical candidates, if adding another candidate would cause `run_length` to exceed 65535, the `SparseMapBuilder` shall finalize the current entry and begin a new entry for the remaining consecutive candidates, repeating as necessary until the entire interval is covered. The split must preserve all metric fields (including flags) for each split piece. **When splitting an entry due to run‑length overflow, the subsequent entry SHALL have `freq_delta_start = 0`. Because the decoder’s current frequency is exactly the next candidate after the preceding chunk, this makes the chunks physically contiguous. No long‑jump is required, regardless of `effective_step`.**

### 3.4 Static Lane Execution

#### 3.4.1 Plan Construction

- Full constant propagation, direct callback binding (no runtime `callback_id` lookup), and resolution of all feature flags into specialised evaluator blocks. The resulting hot loop contains no opcode decoding, no branch dispatch, and no feature‑test branches.
- Zones are grouped by identical evaluator configuration, producing a schedule of `EvaluatorBlock` structures. Each block holds a function pointer, embedded constants, zone span, and scratch offsets. If an explicit delta pair is active for a zone, the evaluator block carries the `(d_lo, d_hi)` override values and a boolean flag indicating the override is active; otherwise those fields are zeroed and the evaluator computes `d_lo`/`d_hi` from the cycle time.
- **Compile‑time binding of DELTA state:** A purely static‑lane bytecode program cannot contain `DELTA`, because `DELTA` is a Dynamic Lane opcode. However, the static‑lane evaluator may still receive an explicit delta override through a native `ExecutionPlan` configuration, or from zones captured after a Dynamic Lane `DELTA` instruction. When an explicit delta override is active, the `(d_lo, d_hi)` override is captured and embedded immutably into each `EvaluatorBlock`. This guarantees that `ZoneBatch` entries remain stateless with respect to `DELTA`; worker threads evaluating zones in any order see a consistent snapshot of the override state.
- If an explicit delta override is supplied through a native `ExecutionPlan` configuration and `d_lo > d_hi`, plan construction SHALL fail with `GUNZ_INVALID_LIBRARY`.
- When an explicit delta override is active, the override values `d_lo_ov` and `d_hi_ov` are invariant and SHALL be embedded immutably in the evaluator block. The continuous deltas `d_lo_cont` and `d_hi_cont` still vary per candidate because they depend on the cycle time `T`, even when an override is active.
  For general zones, no precomputed `N_max` based on continuous advances is assumed. An implementation MAY use such a precomputation as an internal optimization only if it proves that the resulting candidate classifications are bit‑identical to the normative per‑candidate computation.
  The N‑search remains bounded solely by `MAX_N = 2³¹ − 1`.
- Zone data is stored contiguously; the layout is implementation‑defined but must support efficient vectorisation.
- **Plan complexity iteration bounds:** During construction, the plan's total number of evaluator blocks, worst‑case scan iterations per zone, and worst‑case evaluation iterations per candidate are computed. The plan must be capable of carrying a declared `max_scan_iterations` (per zone) of at least 2²⁴ (16 777 216). Implementations may support higher values; they must never accept a plan whose declared limit is lower than this minimum. A `max_eval_iterations` (per candidate, non‑long‑term) of at least 65 536 is also required, along with a `total_max_scan_iterations` (global) of at least 2²⁶ (67 108 864). If the user does not supply a higher value, the runtime **SHALL** initialise `max_scan_iterations` to 2²⁴.  

For `long_term_scan` plans, the per‑candidate evaluation limit is **derived by the plan constructor** and SHALL NOT be taken from a user‑supplied value.
Plan construction SHALL ensure `quantum ≥ 1` before computing this limit; if not, construction fails as specified in §3.10.
The constructor SHALL set:

  long_term_max_eval = ceil(window_duration / quantum)

using 128‑bit unsigned arithmetic, saturating the result to `2⁶⁴ − 1`.

The constructor SHALL set:

  max_eval_iterations = long_term_max_eval

Any user‑supplied `max_eval_iterations` is ignored for long‑term scans.

This limit is intentionally conservative. For every valid long‑term candidate, the raw block time is a positive integer multiple of `quantum`; therefore `ceil(window_duration / quantum)` is an upper bound on the number of raw blocks needed to reach `window_duration`.
 
  If the bytecode header sets the `long_term_scan` flag but no `window_duration` is supplied at plan‑construction time, plan construction SHALL fail with `GUNZ_INVALID_LIBRARY`.  
  
  For non‑long‑term scans, if the plan’s declared `max_eval_iterations` is lower than 65 536, construction SHALL fail with `GUNZ_ITERATION_LIMIT_EXCEEDED`.  
 
  If the user does not supply a higher value, the runtime SHALL initialise `max_eval_iterations` to 65 536 for non‑long‑term scans and `total_max_scan_iterations` to 2²⁶ (67 108 864). 

For long‑term scans, the constructor‑derived `max_eval_iterations` takes precedence over the default 65 536. In non‑long‑term scans `max_eval_iterations` does **not** govern the N‑search. The N‑search is bounded solely by `MAX_N`. The `max_eval_iterations` parameter remains required to be at least 65 536 for plan‑complexity accounting, but it is not used as an inner‑loop bound for N‑search. It remains normative for long‑term scans, where it bounds temporal block repetition per candidate. Global budget enforcement is performed exclusively by the single‑threaded pre‑pass described in §3.11 “Global iteration limit enforcement.” Plan construction SHALL NOT fail solely because the sum of zone candidate counts exceeds `total_max_scan_iterations`. The pre‑pass will deterministically exclude zones as necessary and return `GUNZ_ITERATION_LIMIT_EXCEEDED` after producing a partial map.  
 
  If the total number of evaluator blocks exceeds an implementation‑defined threshold (at least 65,536), construction fails with `GUNZ_ARENA_EXHAUSTED`, as an implementation‑defined resource/complexity limit. These protections prevent denial‑of‑service via small bytecode programs that expand to enormous evaluator workloads.

For the three plan iteration limits, an explicitly supplied value of `0`, or an absent/uninitialised field treated as `0`, SHALL mean “use the default”:
- `max_scan_iterations = 0` → `2²⁴`
- `max_eval_iterations = 0` in a non‑long‑term scan → `65 536`
- `total_max_scan_iterations = 0` → `2²⁶`

A positive declared value below the corresponding minimum SHALL cause plan construction to fail with `GUNZ_ITERATION_LIMIT_EXCEEDED`.
For `long_term_scan` plans, `max_eval_iterations` is derived by the plan constructor; any supplied value, including `0`, SHALL be ignored.

**Immutability of embedded constants:**
Once constructed, the plan's copy of `reference_block_time` and all other system parameters are fixed. Subsequent changes to the map header or library profile do not retroactively affect an already‑built plan.

After library merging, `mult_num` and `mult_den` must both be non‑zero; otherwise plan construction fails with `GUNZ_INVALID_LIBRARY`. If the implementation does not support the GUNZ‑DRIFT companion and a plan construction input `drift_enabled` is supplied with value `true`, plan construction SHALL fail with `GUNZ_INVALID_LIBRARY`. A value of `false` or absence SHALL be treated as drift disabled.

**Static‑lane parsing of `LOOP` and `PURE_CALL`:**  
In a **Full‑profile** static‑lane program, the bytecode is parsed in a single linear pass.  

Each `LOOP` instruction is expanded by repeating the enclosed block of bytecode the specified number of times; the expanded instructions are then processed as if they had appeared inline.  The expansion respects the same `block_bytes` bound that applies in the dynamic lane.  

The total size of the expanded bytecode produced by all `LOOP` instructions in the program must not exceed an implementation‑defined limit; that limit shall be at least 2²⁰ (1,048,576) bytes. 

This expansion limit applies to Static-Lane plan construction only. Dynamic-Lane execution does not materialise a fully expanded bytecode stream; it is bounded by fuel and by the structural loop rules of §3.5.1.

If the limit is exceeded, plan construction fails with `GUNZ_MALFORMED_BYTECODE`.  The plan constructor **shall** verify that the `block_bytes` of each `LOOP` instruction does not cause the parser to read beyond the end of the bytecode. 

If it does, plan construction shall fail with `GUNZ_MALFORMED_BYTECODE`.  Nested `LOOP` instructions are expanded recursively; an inner `LOOP` encountered during expansion is itself expanded before the outer loop's next iteration is processed.  

- Each `PURE_CALL` instruction is **not** executed immediately. Its `callback_id` and arguments are captured as a pending specification. The pending specification persists across intervening non-zone instructions, including `SCAN_RES`, and is attached to the next `ZONE` or `SKIP_ZONE` in execution order. If multiple `PURE_CALL` instructions occur before that next zone, only the last one is retained. The captured callback is later resolved at plan‑construction time using the active library profile, exactly as described for the dynamic lane in §3.5.

A pending `PURE_CALL` that is consumed by a `SKIP_ZONE` is silently discarded during evaluation. Such a pending callback SHALL NOT be resolved at plan‑construction time, and a missing `callback_id` in the active library SHALL NOT cause plan construction to fail for that `SKIP_ZONE`.

 If no subsequent `ZONE` or `SKIP_ZONE` exists after the pending `PURE_CALL` — whether because the program ends with the `PURE_CALL`, or because only non-zone instructions follow — the pending callback is silently discarded and has no effect.

*(Informative)* When a `LOOP` body contains a `PURE_CALL` followed by a `ZONE`, each loop iteration creates a separate `ZONE` instance with its own captured callback. The “only last retained” rule applies only to consecutive `PURE_CALL` instructions without an intervening `ZONE`.

In a static‑lane program, a `SCAN_RES` instruction that appears after the first `ZONE` or `SKIP_ZONE` in the bytecode is malformed; the plan constructor shall reject the program with `GUNZ_MALFORMED_BYTECODE`.

**Plan complexity threshold:** Implementations **SHALL** support at least 65,536 evaluator blocks; they may support more, but must document the exact limit. This minimum ensures that a conformant implementation can handle all standard scan configurations without exhaustion.  
This implementation‑defined evaluator‑block limit is denoted `MAX_STATIC_EVALUATORS` in Appendix A.

#### 3.4.2 Arithmetic & Numerics

- All arithmetic is performed in **integers** in the base time unit determined by `time_unit`. Observable results (block time, jitter, advance regularity) must equal the mathematical integer result whenever representable; otherwise they saturate.

- **Saturation:** Unless otherwise stated, saturation clamps a value to the nearest representable boundary of its destination type (e.g., `UINT32_MAX` for an unsigned 32‑bit field, 255 for a `u8`, 65535 for a `u16`, etc.). For signed integer fields, saturation clamps to the minimum or maximum representable value (e.g., `−32 768` to `32 767` for `s16`). Signed saturation is relevant only for fields that carry signed deltas (`freq_delta_start`) and for the long‑jump sentinel reinterpretation; all other paths use unsigned or exact arithmetic and do not produce signed overflow.

- Floating‑point arithmetic shall not influence observable outputs.

- SIMD implementations must produce bit‑identical output to the scalar implementation.

- **Division:** All divisions in the hot path by plan‑invariant divisors shall produce mathematically exact floor results (or the appropriate rounding as specified). Implementations may use precomputed reciprocal multiplication, Granlund–Montgomery, or any other method that yields bit‑identical results.

- **Ceiling computation:** For positive integers `a` and `b`, `ceil(a / b)` is defined as `(a + b - 1) / b`. To avoid overflow, the addition `a + b - 1` must be performed using a type wide enough to hold the result; for 32‑bit inputs, at least 64‑bit arithmetic shall be used. **For 64‑bit inputs such as `window_duration`, the addition `a + b - 1` shall be performed using 128‑bit unsigned arithmetic to avoid overflow.**

#### 3.4.3 Adaptive Multi‑Resolution Scanning *(Informative)*

The `time_unit` field enables adaptive multi‑resolution scanning without any format changes. An AI agent can run scans at different time‑unit precisions to locate resonance boundaries efficiently.

The recommended iterative procedure is:

1. **Start coarse.** Begin with a large time unit (e.g., milliseconds, `time_unit=3`). Coarse scans are fast and quickly reveal major block‑pattern transitions ("edges" where `N` changes).

2. **Deepen when silent.** If the coarse scan finds no edge over the target frequency zone, increase precision by moving to a finer time unit (e.g., microseconds, `time_unit=6`). Jumping in powers of 1000 (i.e., ±3 in `time_unit`) provides a good balance between dynamic range and scan count.

3. **Ascend incrementally when costly.** Finer scans consume more CPU and memory. After deepening, compare the newly discovered edges and the scan cost with those from the previous coarser scan. If the cost has increased disproportionately without gaining sharper edges, step back **one level** to the immediately coarser power of ten (e.g., from `time_unit=9` back to `time_unit=6`). Re‑evaluate at that level before deciding whether to retreat further.

4. **Verify upward.** When an edge is found at a fine resolution, repeat the scan at the next coarser resolution (one step up) to confirm that the edge is still detectable. If it disappears, the feature is only visible at that fine scale, and the agent should remain at that level (possibly extending the measurement window via `long_term_scan` and chained windows to gather more data).

5. **Wait and re‑probe.** If no edge appears even after multiple deepening steps, the agent may keep the finest affordable time unit and prolong the observation window. A constant that the AI could not predict may emerge after accumulating sufficient statistics over time.

This iterative deepening is a core design pattern for GUNZ‑based tuning: the format does not change, the maps remain deterministic, and the AI agent simply writes multiple scans with different `time_unit` values, comparing their `.gunzmap` and `.gunzstats` outputs to converge on the optimal operating point.

#### 3.4.4 Negative Cache & Plan Rejection

- If the plan cache supports negative entries, a compilation failure is recorded to avoid repeated attempts.
- A `ZONE` with `freq_high < freq_low`, or any frequency equal to `0`, must be rejected with `GUNZ_MALFORMED_BYTECODE`.  Additionally, any zone that violates the grid‑alignment requirement of §3.3 must be rejected with `GUNZ_MALFORMED_BYTECODE`.

#### 3.4.5 Deferred Operations in Static Lane

In a static‑lane program, `ORACLE`, `EXPORT_ORACLE`, `EXPORT`, `IMPORT`, and `STREAM` are **not** executed during plan construction.  Instead, they are captured in the order they appear in the bytecode and appended to a deferred‑operation queue, together with the current `library_id`.

- `ORACLE` captures the system state (multiplier, rounding mode, delta override, `effective_step`, and any pending `PURE_CALL` specification) and the instruction operands, including `object_id`.
- `EXPORT_ORACLE` captures the `object_id` and the reserved operand (which must be zero).

After the resonance map has been generated from all evaluated zones, the runtime executes the deferred queue in this deterministic order:
1. All captured `ORACLE` queries are executed with their frozen state; each result is stored in the object table at the given `object_id`.
2. All captured `EXPORT_ORACLE` instructions are executed, writing the CQR data from the object table to a file.
3. The remaining deferred operations (`EXPORT`, `IMPORT`, `STREAM`) are processed as originally specified.

If any `ORACLE` query fails (e.g., due to invalid constraints or memory exhaustion), the runtime shall abort the deferred queue immediately, discard any remaining pending operations, and return the error code to the caller.  If an `EXPORT_ORACLE` references an `object_id` that has not been populated, the runtime fails with `GUNZ_INVALID_OBJECT`.

*(Informative)* The deferred queue is executed in three fixed phases: all `ORACLE` queries, then all `EXPORT_ORACLE` operations, then map‑manipulation operations (`EXPORT`, `IMPORT`, `STREAM`). This order is fixed regardless of the original bytecode program order. It guarantees that CQR data is available before any export that may consume it. Implementations SHALL NOT execute deferred operations in raw program order across phases. The three phases are fixed as described; within each phase, operations SHALL execute in capture order.

This deferred execution applies only to Full‑profile static‑lane programs; Minimal‑profile implementations reject `IMPORT`, `STREAM`, `ORACLE`, and `EXPORT_ORACLE` at load time per §1.2 and will never encounter these opcodes.  

If no zones were evaluated and the map is empty, a valid map consisting only of a header and the canonical map data checksum over the 64‑byte header is written by `EXPORT`.

### 3.5 Dynamic Lane Execution

The Dynamic Lane is a simple virtual machine that processes bytecode programs not meeting the Static Lane criteria. It executes instructions sequentially, collecting zones and producing a `ZoneBatch` for subsequent evaluation. Implementations that do not support dynamic programs (i.e., that reject all bytecode containing dynamic lane opcodes) remain conformant.

**VM state:**

- `pc` – program counter.
- `state` – mutable copy of header parameters.
- `zone_list` – an ordered list of zones encountered during execution. Zones are appended in the order their `ZONE` instructions appear in the bytecode. Each `ZONE` **or `SKIP_ZONE`** instruction captures the current parameter state (`library_id`, multiplier, rounding mode, delta pair, and any pending `PURE_CALL` specification) at the moment the instruction is executed.  This captured state is used when evaluating the zone (or generating placeholder entries for a skipped zone).
- `loop_stack` – stack of active dynamic‑lane loop frames, as defined in §3.5.1. Initially empty.
- `fuel` – remaining fuel (signed 64‑bit). The canonical initial fuel for conformance testing is **10,000**. This value is deliberately modest to keep the conformance suite lightweight and deterministic. Production deployments may select a fuel limit appropriate to their orchestration complexity and must document it as an implementation‑defined parameter. The fuel limit gates only the bytecode interpreter; it does not constrain the downstream resonance evaluator, which is bounded separately by `max_scan_iterations` per zone, `max_eval_iterations` per candidate, and `total_max_scan_iterations` per plan. The separation of fuel (VM orchestration) and iteration limits (evaluator) is intentional.

The `effective_step` is a program‑wide constant, set by the last `SCAN_RES` instruction appearing before the first `ZONE` or `SKIP_ZONE` (or defaulting to 1 if none).  It applies uniformly to all zones and is not individually captured per zone.

**Library parameter consistency.**

The runtime SHALL compute `reference_params` exactly once, before VM execution begins, by merging the bytecode header with the library profile specified by the header’s `library_id`:

- if the header `library_id` is non‑zero, use that library;
- otherwise use no library.

If the header `library_id` is non‑zero and missing from the library table, VM execution SHALL fail immediately with `GUNZ_INVALID_LIBRARY`.

`reference_params` SHALL NOT be recomputed after any `LIBREF`.

When executing `LIBREF`, before applying the switch and before resetting mutable overrides, the VM SHALL compute the effective evaluator parameters that would result from merging the bytecode header with the newly active library.

If that parameter set differs from `reference_params` in any of the following:
- `quantum`
- `mult_num`
- `mult_den`
- `jitter_window_radius`
the VM SHALL halt immediately with `GUNZ_INVALID_LIBRARY`.


`LIBREF` may therefore change callback resolution and other non‑evaluator library metadata, but it SHALL NOT change the effective evaluator parameter set within one run.

`effective_step` is not library‑supplied; it is program‑wide from `SCAN_RES`.

Different libraries referenced by one program MAY have different `callback_abi_version` values. Each resolved callback SHALL match its own library’s declared `callback_abi_version`.

For the purposes of this comparison, `jitter_window_radius` SHALL be compared using it's resolved effective values after §3.10 merging.
`jitter_window_radius` SHALL be compared by effective radius:
- `10000` if the stored scale factor is `0`
- `stored_value × 1000` otherwise
Therefore two libraries whose raw `jitter_window_radius` values are `0` and `10` are equivalent for this check, because both resolve to an effective radius of `10000`.

*(Informative)* `SKIP_ZONE` captures the full mutable state for uniformity with `ZONE`; only the `effective_step` is used when generating placeholder entries.

*(Normative)*  The static check forbidding `SCAN_RES` after the first zone (see §2.3.3.9) is enforced by the bytecode loader before VM execution begins.  The dynamic‑lane VM does not need to perform this check at runtime.

For programs that will be classified as Dynamic Lane, the bytecode loader MAY statically detect loops that violate the structural rules of §3.5.1, such as an inner loop whose body extends beyond the enclosing body, and reject such programs earlier. This is an optimisation only; the normative runtime requirement remains that structurally invalid loop nesting is malformed.

**Fuel mapping (normative) – Full-profile and Dynamic‑Lane‑supporting Minimal‑profile:**  
Every plan that uses the Dynamic Lane **SHALL** embed the exact fuel table shown in this section. The table is immutable and must match the specification; an implementation may not substitute a different table. Fuel costs exist solely to guarantee that dynamic‑lane programs halt within a finite number of operations; they do not reflect CPU time or resource consumption.

**Minimal‑profile note:** If a Minimal‑profile implementation supports the Dynamic Lane, it **SHALL** implement full fuel accounting as described in this section and **SHALL NOT** omit fuel checks.  The initial fuel for Minimal‑profile dynamic‑lane conformance is the same canonical value of **10 000**.  This guarantees that the same bytecode produces the same map on all conformant implementations.  If the implementation does **not** support the Dynamic Lane, fuel accounting may be entirely omitted.  Conformance to the Minimal profile does not require fuel enforcement for static‑lane‑only implementations.

| Opcode | Cost Class | Canonical Fuel |
|--------|------------|----------------|
| `HALT` | LOW | 1 |
| `LOOP` | LOW | 1 |
| `ZONE` | HIGH | 100 |
| `SKIP_ZONE` | LOW | 1 |
| `EXPORT` | HIGH | 100 |
| `IMPORT` | HIGH | 100 |
| `STREAM` | MEDIUM | 10 |
| `PURE_CALL` | HIGH | 100 |
| `ORACLE` | HIGH | 100 |
| `SCAN_RES` | LOW | 1 |
| `ADVANCE` | MEDIUM | 10 |
| `ROUND` | LOW | 1 |
| `DELTA` | LOW | 1 |
| `LIBREF` | HIGH | 100 |
| `EXPORT_ORACLE` | HIGH | 100 |

**Fuel consumption semantics:**  
For all opcodes **except `HALT`**, the VM performs the pre‑execution fuel check: before each instruction is executed, the VM checks whether `fuel < instruction_cost`. If so, the VM halts with `GUNZ_FUEL_EXHAUSTED` and **the instruction is not executed**. Otherwise, the instruction is fully executed, and *after* execution, `fuel` is decremented by the instruction's cost.

**HALT fuel semantics:** HALT always executes. If `fuel > 0`, it is decremented by 1 after execution. If `fuel == 0`, it executes without decrementing. The `fuel_consumed` field in `.gunzmeta` shall reflect the actual decrement.

**Pseudo‑code for fuel consumption:**

```
if (opcode != HALT && fuel < cost) {
    return GUNZ_FUEL_EXHAUSTED;
}
execute(opcode);
if (opcode != HALT) {
    fuel -= cost;
} else if (fuel > 0) {
    fuel--;
}
```

### 3.5.1 Dynamic‑Lane Loop Execution

Nested `LOOP` instructions are permitted in the Dynamic Lane. The VM SHALL maintain a stack of active loop frames. Each frame records:

- `remaining` — number of iterations remaining
- `body_start` — byte offset of the first instruction in the loop body
- `body_end` — byte offset immediately after the loop body

On encountering a `LOOP` instruction with operands `count` and `block_bytes`, the VM SHALL:

1. Verify that `count > 0`.
2. Verify that `block_bytes > 0`.
3. Verify that `block_bytes ≤ 65535`.
4. Let `next_PC = PC + 5`, where `PC` is the byte offset of the `LOOP` opcode itself. The `LOOP` instruction is exactly 5 bytes: one opcode byte, two `count` bytes, and two `block_bytes` bytes.
5. Let `body_start = next_PC`.
6. Let `body_end = next_PC + block_bytes`.
7. Verify that `body_end ≤ bytecode_length`.
8. Push the frame `(remaining = count, body_start, body_end)` onto the loop stack.
9. Continue execution at `body_start`.

The loop body consists of bytes `body_start` through `body_end − 1` inclusive. `body_end` is exclusive.

The loop body SHALL contain a sequence of complete instructions ending exactly at `body_end`. If instruction decoding would require reading beyond `body_end`, the program SHALL be rejected with `GUNZ_MALFORMED_BYTECODE`.

When execution reaches `body_end`, the frame examined is the current top of the loop stack:

- `remaining` SHALL be decremented by one.
- If `remaining > 0`, the VM SHALL continue execution at `body_start`.
- If `remaining == 0`, the VM SHALL pop the frame and continue execution at `body_end`.

If the VM halts for any reason while loop frames are active — including `HALT`, fuel exhaustion, or an opcode validation failure — the loop frame stack SHALL be discarded and no further loop iterations SHALL be executed.

The body of every inner `LOOP` SHALL be entirely contained within the body of each enclosing `LOOP`. If an inner loop body would extend beyond the enclosing loop’s `body_end`, the program SHALL be rejected with `GUNZ_MALFORMED_BYTECODE`. Equality of an inner loop’s `body_end` with the enclosing loop’s `body_end` is allowed.

If execution reaches `bytecode_length` without encountering `HALT`, the VM SHALL halt successfully, as if a `HALT` instruction had been executed.

**Zone ordering.**  
Zones SHALL be appended to `zone_list` in VM execution order, including repeated executions inside loop bodies. Each execution of a `ZONE` or `SKIP_ZONE` captures the VM parameter state independently, exactly as if that instruction had appeared inline multiple times.

All zones produced by loop executions remain subject to the strict disjointness and grid‑alignment requirements of §3.3. Duplicate or overlapping zones are detected when the complete ordered zone list is validated after the VM halts. If the zone list contains duplicate or overlapping zones, the program SHALL be rejected with `GUNZ_MALFORMED_BYTECODE`, and no map SHALL be emitted.

**Pending `PURE_CALL` consumption.**  
When a `ZONE` or `SKIP_ZONE` consumes a pending `PURE_CALL` specification, the pending specification SHALL be cleared immediately after capture.

A pending `PURE_CALL` does not persist beyond the first subsequent `ZONE` or `SKIP_ZONE`, including across loop iterations.

**State‑changing opcodes inside loops.**  
`ADVANCE`, `ROUND`, `DELTA`, and `LIBREF` execute normally inside loop bodies. Their effects apply to subsequent instructions and subsequent iterations according to their existing semantics.

**Fuel.**  
Fuel SHALL be charged using the canonical fuel table for:

- each `LOOP` instruction encountered,
- every execution of every instruction inside a loop body, per iteration.

Inner `LOOP` instructions therefore consume fuel separately on each execution.

*(Informative)* With this model, nested loops remain deterministic and bounded by the VM fuel limit. The resulting ordered zone list and final map are bit‑identical across conformant implementations. For programs whose loop bodies contain only Static‑Lane opcodes, the zone list is also equivalent to the Static‑Lane expansion of the same loops.

**VM Opcode Validation:**  
Before executing an `ADVANCE` instruction, the VM shall verify that `mult_num ≠ 0` **and** `mult_den ≠ 0`. If either is zero, the VM shall halt immediately and return `GUNZ_MALFORMED_BYTECODE`. This check prevents a hardware divide‑by‑zero fault in the resonance evaluator.

 Before executing a `LIBREF` instruction, the VM shall verify that the `library_id` exists in the library table. If the ID is not present, the VM shall halt immediately and return `GUNZ_INVALID_LIBRARY`.

 After a successful `LIBREF`, before any subsequent instruction is executed, the VM SHALL apply the override resets specified in §2.3.2: `ADVANCE` is cleared, `ROUND` is cleared, and `DELTA` is reset to `(0,0)`. A pending `PURE_CALL` specification is preserved.


If a plan reaches `GUNZ_ITERATION_LIMIT_EXCEEDED` **and** the VM fuel is also exhausted, the runtime must return `GUNZ_ITERATION_LIMIT_EXCEEDED` (the evaluator limit takes precedence).

The VM shall verify that `arg_count ≤ 16` for every `PURE_CALL` before dispatch. If the check fails, the bytecode is malformed and shall be rejected with `GUNZ_MALFORMED_BYTECODE`.

After halting (either `HALT` or fuel exhaustion), the accumulated zones, each with their own captured state, are evaluated using the **Resonance Evaluator** (§3.11) to produce map entries. **The resulting partial map shall be returned to the caller; `GUNZ_FUEL_EXHAUSTED` is informational and does not discard the map.** The dynamic lane itself does not perform interleaved scanning; it merely collects zones with their states and defers evaluation to the same evaluator used by the static lane. `SKIP_ZONE` zones are marked as skipped and produce placeholder entries directly without evaluation.

**`PURE_CALL` in the Dynamic Lane:** 
When the VM encounters a `PURE_CALL` instruction, the callback is **not** invoked immediately. The `callback_id` and its arguments are captured as part of the mutable VM state, exactly like the multiplier, rounding mode, and delta pair. When a subsequent `ZONE` or `SKIP_ZONE` instruction is executed, the captured callback specification is attached to that instruction. 

If multiple `PURE_CALL` instructions are issued before a `ZONE`, only the most recent one is captured; the earlier ones are overwritten. At plan‑construction time, the runtime resolves the `callback_id` using the library profile that was active (via the current `library_id`) when the `ZONE` was issued, obtaining the function pointer and output size as described in §3.7. The callback is then executed by the evaluator during the zone's scan. This ensures that all `PURE_CALL` invocations remain deterministic and are bound before any scanning begins.  

*(Note: The library profile used to resolve the callback is the one active at the moment the subsequent `ZONE` (or `SKIP_ZONE`) instruction is executed, not the library active when the `PURE_CALL` instruction itself was encountered.  A `LIBREF` issued between `PURE_CALL` and the next zone will change the resolution target.)*

A pending `PURE_CALL` consumed by a `SKIP_ZONE` is silently discarded during evaluation. Such a pending callback SHALL NOT be resolved at  plan‑construction time, and a missing `callback_id` in the active library SHALL NOT cause plan construction to fail for that `SKIP_ZONE`.

If a pending `PURE_CALL` is preserved across `LIBREF` and the newly active library does not define the captured `callback_id`, plan construction SHALL fail with `GUNZ_INVALID_LIBRARY`.

**ORACLE and EXPORT_ORACLE in the Dynamic Lane:**  
When the VM encounters an `ORACLE` instruction, it captures a snapshot of the current system state (multiplier, rounding mode, delta override, `effective_step`, and any pending `PURE_CALL` specification) and the instruction operands, including `object_id`.  The instruction is appended to a deferred‑operation queue.  Fuel for the instruction (100) is deducted at capture time.  

When the VM encounters an `EXPORT_ORACLE` instruction, it captures the `object_id` and the reserved operand, and appends it to the same deferred‑operation queue.  Fuel (100) is deducted immediately.  

After the VM halts and the resonance map has been produced from all zones, the runtime processes the deferred‑operation queue in this exact order:

1. All captured `ORACLE` queries are executed with their frozen state; results stored in the object table at the recorded `object_id`.

2. All captured `EXPORT_ORACLE` instructions are executed, writing the CQR files.

3. Other deferred operations (`EXPORT`, `IMPORT`, `STREAM`) are processed as per the existing rules.

If any `ORACLE` query fails, the queue is aborted, subsequent pending operations are discarded, and the error is returned to the caller.

*(Informative)* The deferred queue is executed in three fixed phases: all `ORACLE` queries, then all `EXPORT_ORACLE` operations, then map‑manipulation operations (`EXPORT`, `IMPORT`, `STREAM`). This order is fixed regardless of the original bytecode program order. It guarantees that CQR data is available before any export that may consume it. Implementations SHALL NOT execute deferred operations in raw program order across phases. The three phases are fixed as described; within each phase, operations SHALL execute in capture order.

**Map‑manipulation and streaming opcodes in the Dynamic Lane:** 
When the VM encounters `EXPORT`, `IMPORT`, or `STREAM`, the instruction is **not** executed immediately. Instead, the opcode and its operands are captured and appended to a deferred‑operation queue, together with the current `library_id`. The queue is maintained in program order. After all zones have been evaluated and the map has been generated, the runtime processes the deferred queue in order: `EXPORT` writes the generated map to the specified object; `IMPORT` loads an external map into the runtime object table; `STREAM` resolves the `callback_id` using the active library profile at the time the `STREAM` instruction was captured, and installs the callback for batched map output during the subsequent `EXPORT` operations. 

- If a `STREAM` appears multiple times, only the most recently captured `callback_id` (in program order) is active.

- If a deferred operation references an `object_id` that has not been populated, the runtime shall fail with `GUNZ_INVALID_OBJECT`.

- If any deferred operation fails, the runtime shall abort the queue immediately, discard any remaining pending operations, and return the failure code to the caller. The fuel cost for each deferred opcode is deducted at the time the instruction is encountered, not when the operation is performed.

- If both fuel exhaustion and iteration‑limit exceedance occur simultaneously, the runtime shall report `GUNZ_ITERATION_LIMIT_EXCEEDED` (the evaluator limit takes precedence). The partially generated map is still returned.

### 3.6 Callback ABI (Normative)
All callbacks conform to:

```c
typedef GUNZ_Result (*GUNZ_Callback)(
    const uint32_t *args,
    uint8_t         arg_count,
    void           *output
);
```

- `args`, `arg_count` – as passed from bytecode. `arg_count` is an 8‑bit unsigned integer; the maximum allowed value is 16. Values greater than 16 shall cause the bytecode to be rejected with `GUNZ_MALFORMED_BYTECODE`.
- `output` – A caller‑owned buffer of exactly `output_size` bytes, where `output_size` is the per‑callback size declared in the library profile.  The runtime allocates this buffer before each `PURE_CALL` invocation.  Its alignment is implementation‑defined but must be at least pointer‑width (e.g., 4 or 8 bytes).  The buffer is valid only for the duration of the invocation and must not be retained by the callback.
- The `callback_abi_version` in the library profile must match the callback's ABI version. If a mismatch is detected during plan construction, plan construction fails with `GUNZ_INVALID_LIBRARY`.

#### 3.6.1 Streaming Callback Contract *(Normative)*
A callback registered via the `STREAM` opcode must satisfy the general callback ABI of §3.6 and the streaming callback contract defined in this section. Full `PURE_CALL` purity restrictions do not apply to streaming callbacks, subject to the limitations defined below.

 A streaming callback is not subject to the full `PURE_CALL` purity restrictions of §3.7. However, when the bytecode header’s `sandboxed_callbacks_required` flag is set, the runtime SHALL execute the streaming callback in a sandboxed environment satisfying the isolation, determinism, resource-limit, and memory-access-safety requirements of §3.7. If such sandboxing cannot be provided, the program SHALL be rejected with `GUNZ_INVALID_LIBRARY`.

**Arguments (`args`):**
- `args[0]` — `batch_size` (u32): number of map entries in this batch.
- `args[1]` — `total_entries` (u32): cumulative number of entries written so far (including this batch).  Wraps modulo 2³².
- `args[2]` — reserved; must be 0.

No more than 3 arguments are passed (`arg_count = 3`).  The runtime must set these values before each invocation.

**Output buffer (`output`):**
The buffer is of size `output_size` bytes as declared in the library profile.  The runtime writes exactly `batch_size × 16` bytes of map‑entry data (packed in the canonical little‑endian format of §4.2) into the buffer.  The runtime shall choose `batch_size` such that `batch_size × 16 ≤ output_size`.  The runtime may use any batch size satisfying this bound; smaller batches are permissible.  The callback may read this data to process or forward the entries.  **The callback must treat the output buffer as read‑only.  Any attempt to modify it is a violation of the streaming contract.**

A streaming callback with declared `output_size < 16` cannot hold any map entry.

The runtime SHALL NOT validate the streaming output size when the `STREAM` instruction is captured or processed.

When a deferred `EXPORT` operation is executed and a streaming callback is active for that `EXPORT`, the runtime SHALL validate the active callback’s declared `output_size`.

If `output_size < 16`, that `EXPORT` SHALL fail with `GUNZ_INVALID_LIBRARY`,and the deferred queue SHALL abort according to the normal deferred-operation error rules.

If no `EXPORT` follows the last active `STREAM`, the invalid streaming configuration SHALL NOT cause rejection.

*(Informative)* Streaming `output_size` validation is intentionally deferred until the associated deferred `EXPORT`. This keeps failure timing deterministic across conformant implementations. An invalid streaming configuration may therefore remain undetected until scan evaluation completes, or entirely undetected if no subsequent `EXPORT` uses the callback.

**Return value:**
- `GUNZ_OK` — the batch was consumed successfully.
- `GUNZ_CALLBACK_FAILED` — the streaming session is aborted; the runtime shall stop the evaluator and return this code to the caller.

**Timing constraint:**
 The callback must complete within a deterministic, constant‑time budget relative to the batch size (i.e., O(1) per entry).  It must not block on external I/O; the runtime is responsible for asynchronous data transfer.

### 3.7 PURE_CALL Definition

A `PURE_CALL` callback must satisfy:

- No side effects (I/O, memory allocation, locks, atomics, thread‑local mutation, heap allocation).
- Does not read mutable global state.
- Memory accesses depend only on arguments and immutable data (including the Environment Snapshot, if bound).
- Execution complexity depends only on arguments and immutable data.

**Sandboxing requirement (Full-profile only):**  
If the bytecode header sets the `sandboxed_callbacks_required` flag (bit 7), and the implementation claims the Full profile, the runtime **shall** execute every `PURE_CALL` in a sandboxed environment that physically enforces the purity constraints. A conformant sandbox must provide the following guarantees:

1. **Isolation:** No access to the host filesystem, network, or devices.
2. **Determinism:** Execution must be deterministic; no access to sources of non‑determinism such as hardware clocks or random devices. The sandboxed environment **must** disallow any source of nondeterminism (e.g., `rdtsc`, `gettimeofday`, `rand`).
3. **Resource limits:** CPU and memory usage must be bounded.
4. **No persistent state:** No modifications to persistent storage or external state.
5. **No side effects:** No I/O, no system calls except those explicitly permitted by the purity constraints.

The sandbox must guarantee that the **same** callback invoked with the same arguments always returns the same `GUNZ_Result` and writes identical output bytes.

**Memory‑access safety:** 
The sandbox must also guarantee memory‑access safety: callbacks may only read from memory that is immutable for the duration of the call (e.g., read‑only segments, the Environment Snapshot), their own isolated local call stack, and the provided `args` array. Reading from any external, shared, or host‑level mutable memory constitutes a violation of purity. Writing is permitted only to the `output` buffer (which is owned by the caller and valid for the duration of the invocation). For streaming callbacks registered via `STREAM`, the `output` buffer is also a permitted read region during the invocation; however, **writing to the output buffer by a streaming callback is forbidden and shall cause `GUNZ_SANDBOX_VIOLATION`**. Any attempt to read or write outside these permitted regions shall cause the sandbox to abort the call, returning `GUNZ_SANDBOX_VIOLATION`.

**Minimal-profile note:** 
Minimal‑profile implementations do not implement `PURE_CALL`. The opcode is rejected at load time with `GUNZ_MALFORMED_BYTECODE`, as required by §1.2. No purity enforcement or sandboxing is performed.

Any sandboxing mechanism that satisfies these properties is acceptable. Examples include, but are not limited to:

- A WebAssembly runtime with no host imports and deterministic timers.
- A separate process per callback with a seccomp‑bpf profile denying network and file I/O, and cgroup CPU/memory limits.
- A kernel‑enforced seccomp profile plus namespace isolation.
- A Firecracker microVM with a minimal, deterministic guest.
- A gVisor sandbox configured for pure execution.

The runtime must record in `.gunzmeta` the sandbox type and an attestation (see §4.6 and §4.10). If the flag is set and the runtime cannot provide a conformant sandbox, it shall reject the program with `GUNZ_INVALID_LIBRARY`.  `GUNZ_INVALID_LIBRARY` is also used when sandboxing is required but unavailable. 

*A reference sandbox implementation is planned for inclusion in the conformance suite; until then, implementers must verify that their chosen sandbox guarantees deterministic execution.*

If the flag is not set, the runtime may still sandbox callbacks, but is not required to do so. However, a map produced with **unsandboxed** callbacks shall **not** be considered a canonical map (§4.6); its `.gunzmeta` must record `"callback_sandboxed": false`, and its `session_id` should be `null` or indicate a non‑canonical experiment. 

**For production multi‑tenant environments, sandboxing should be mandatory regardless of the flag; the flag exists to allow programs to explicitly request sandboxing where the operator's default policy may not enforce it.**

*Base conformant implementations are not required to support sandboxed callbacks or environment snapshots; those are optional extensions for multi‑tenant production environments. A minimal implementation may reject any program with the sandboxed_callbacks_required flag set and still be conformant.*

During plan construction, each `PURE_CALL` reference is resolved to a direct function pointer and its associated `output_size` is captured from the library profile.  Both the function pointer and the output size are embedded immutably in the plan.

**Environment Snapshot (normative, optional):**  
To enable deterministic conditional orchestration using only `PURE_CALL`, the runtime provides an immutable **Environment Snapshot** object that may be bound into the plan at construction time. A snapshot is a canonical, signed, immutable structure containing any external state the `PURE_CALL` may read (hardware capabilities, prior scan statistics, library metadata). `PURE_CALL` callbacks may read only the provided snapshot and their explicit `args`. The snapshot is part of the plan's canonical identity; plans built with different snapshots are distinct. 

If a program requires environment data not present in the snapshot, plan construction shall fail with `GUNZ_INVALID_LIBRARY`. The snapshot format and signing rules are defined in §4.7. *Support for environment snapshots is optional for base conformance.* The snapshot **must** be bound to the plan at construction time; any later modification of the snapshot invalidates the plan (plan must be discarded).

**Key management:**
 The runtime must expose a public key via `GUNZ_GetSnapshotVerificationKey`. The public key is returned as a raw 32‑byte Ed25519 public key. The private signing key must be rotated at least annually.

**Error handling:**
 If a `PURE_CALL` returns `GUNZ_CALLBACK_FAILED` or `GUNZ_SANDBOX_VIOLATION`, the entire `ExecutionPlan_Run` shall abort immediately and the runtime shall return that error code to the caller. No further zones are evaluated, and any partial map output is discarded.

**Attestation signature note:**
 During the attestation procedure (§4.10), the `attestation_signature` field must be set to an empty string (`""`) before canonicalisation. The empty string value must be **present** in the JSON object during canonicalisation; do not omit the field. Implementations **MUST** ensure that the empty string is serialised as `""`, not omitted or dropped by the JSON library. (Full-profile only; Minimal may omit the field.)

### 3.8 Recovery

After any error, the runtime must return to a valid baseline: all pending scans aborted, arena rewound, ring‑buffer state consistent, no dangling pointers. Recovery is idempotent and does not increase retained memory after repeated failures. Allocation failure must be detected before any partial object becomes visible.

### 3.9 Runtime Object Table

The runtime maintains a private object table that maps 32‑bit `object_id` values to internal resources (arena buffers, file handles, network streams, etc.).

- **Maximum entries:** Implementation‑defined; must be at least 256.  Implementations **SHOULD** enforce a configurable maximum number of simultaneously live objects to prevent denial‑of‑service.  If an allocation would exceed this maximum, the runtime **SHALL** return `GUNZ_ARENA_EXHAUSTED`.

- **Lifetime:** Objects persist until explicitly released. A runtime object is considered **referenced** if any executing plan, pending callback, or ongoing asynchronous operation holds its `object_id`. Once all references have been dropped, the object may be released and its ID reused. The mechanism for tracking references is implementation‑defined (e.g., reference counting, garbage collection). *A recommended technique to avoid use‑after‑free is to embed a generation counter in the high bits of each `object_id`; the runtime increments the counter on each allocation and rejects requests that reference an old generation.*

 The runtime SHALL use generation counters or an equivalent mechanism to prevent a stale `object_id` from becoming valid again after the ID is reused.

- **Invalid IDs:** Using an ID that has not been allocated or has been released shall cause the operation to return `GUNZ_INVALID_OBJECT`. The runtime must not perform any action when this error is raised.

- **Duplicate IDs:** The runtime must not allocate the same ID to two different resources simultaneously.

- **Null object:** ID 0 is reserved and never valid.

Unless otherwise stated, a successful write to an `object_id` SHALL first validate or construct the new object, then atomically replace the existing mapping.

On failure, the existing object SHALL remain unchanged.

If generation counters are used, installing a new object SHALL increment the generation counter for that ID at the moment of replacement. This includes `EXPORT`, `IMPORT`, `ORACLE`.

The object table is accessed only by the deferred‑operation processor, which runs after all worker threads have completed and does not require internal synchronisation.  No concurrent access to the object table occurs during parallel zone evaluation.

### 3.10 Library Table

The runtime maintains an immutable mapping from `library_id` (u16) to `LibraryProfile` values, as defined in §4.1. This table is populated before any `ExecutionPlan` is constructed.

**Parameter merging:** When building a plan, the effective system parameters are formed by taking the bytecode header fields and replacing any zero‑valued field (or designated sentinel) with the corresponding value from the library profile. Specifically:

- If `quantum == 0`, use the library quantum.

- If `mult_num == 0` **or** `mult_den == 0`, the multiplier (both numerator and denominator) is taken entirely from the library profile.

- `round_mode` is used as given (0 is a valid value). `round_mode` is never library‑supplied. The bytecode header’s `round_mode` field is authoritative in all contexts. The library compiler SHALL NOT emit a `rounding` field in conformant library profiles. If a runtime receives a library profile that contains `rounding` — for example from a legacy or nonconforming source — it SHALL ignore that field. A library profile’s `rounding` metadata has no effect on evaluator arithmetic, map output, plan validation, or callback resolution.

- If the library profile does not specify `jitter_window_radius`, or specifies `jitter_window_radius = 0`, the default radius **10000** (21 points, ±0.1 Hz) is used. The stored value is the scale factor; the actual radius = `jitter_window_radius × 1000`.

- Other header fields have no library‑supplied defaults.

**Library profile validation:**  
A library profile must itself satisfy `quantum ≥ 1`, `mult_num ≠ 0`, and `mult_den ≠ 0`. If a library profile violates any of these invariants, plan construction shall fail with `GUNZ_INVALID_LIBRARY`.  

After merging, `quantum` must be ≥ 1 and both `mult_num` and `mult_den` must be non‑zero. If any of these conditions fails (e.g., because the bytecode and the library both specified zero), plan construction fails with `GUNZ_INVALID_LIBRARY`.

`library_id = 0` is reserved for "no library"; the header must supply all parameters and no substitution occurs. When `library_id = 0`, the program may omit any `LIBREF` instruction; the absence of a library is not an error. A missing library entry causes plan construction to fail with `GUNZ_INVALID_LIBRARY`.

The `callback_abi_version` in each library profile applies to all callbacks **in that library**. Any resolved callback whose ABI version does not match its own library’s declared version causes plan construction to fail with `GUNZ_INVALID_LIBRARY`.

Different libraries referenced by one program MAY have different `callback_abi_version` values.

### 3.11 Resonance Evaluator (Core Scanning Algorithm)

The resonance evaluator computes the metrics (`block_time_inaccuracy`, `jitter`, `advance_regularity`, `peak_advance_regularity`, `stability_width`) for each frequency candidate in a zone. All computations are performed with integer arithmetic in the base time unit.

**Inputs:**
- A zone `[freq_low, freq_high]` in 10⁻⁵ Hz units, along with the system parameters: `quantum`, `target_ticks`, `mult_num`/`mult_den`, `round_mode`, `hold_cycles`, `sep_cycles`.

- `reference_block_time` – the ideal total block time the system is intended to achieve, expressed in the same base time unit as the header. The `reference_block_time` is stored in the map header as a `u32` and is always expressed in the base time unit defined by `time_unit`. It is **not** in seconds, milliseconds, or any other unit unless `time_unit` is set accordingly.  
 
**Block time:** 
- It is the total duration of one complete cycle of the target process, measured from the start of the first tick to the end of the final tick (including any hold or separation cycles).

- It is the quantity the scanner compares against `reference_block_time` to determine how closely a given frequency aligns with the desired timing. 

- It must be present in every plan. If the user or AI agent does not supply it explicitly at plan‑construction time, the runtime **shall** apply the deterministic guessing rule (Rule GUNZ_REF_GUESS) to compute a seed value.  
  
**Rule GUNZ_REF_GUESS (normative):** 
 For the purpose of Rule GUNZ_REF_GUESS, the runtime SHALL perform the global iteration pre-pass as an analysis-only pass before evaluation begins. This pre-pass SHALL NOT evaluate any candidates or produce map entries.

  1. Take the midpoint frequency of the first `ZONE` in bytecode order that is included by the global iteration pre-pass, computed as `(freq_low + freq_high) / 2` using ordinary integer division (truncating toward zero). Excluded `ZONE`s SHALL be ignored for this purpose. The addition SHALL be performed using 64-bit unsigned arithmetic to prevent 32-bit overflow.
  
  2. Run the full block simulation (Step 3 of this algorithm) at that single frequency using the effective system parameters and any active overrides.
  
  3. The resulting `total_time` (including `hold_cycles` and `sep_cycles`) becomes the seed `reference_block_time`.  

  - If the block simulation at the midpoint frequency either fails or produces a `total_time` that exceeds `UINT32_MAX`, the runtime SHALL attempt the simulation at `freq_low` of the first included `ZONE` in bytecode order.

  - If that also fails or produces a `total_time > UINT32_MAX`, it SHALL attempt the simulation at `freq_high` of the first included `ZONE` in bytecode order.

  - If all three frequencies produce a `total_time > UINT32_MAX` or fail to produce a valid `total_time`, plan construction SHALL fail with `GUNZ_INVALID_LIBRARY`.

  - If any fallback succeeds and the resulting `total_time ≤ UINT32_MAX`, it becomes the seed `reference_block_time`, and `reference_source` is set to `2` (guessed).
 
  - If at least one `ZONE` is included by the global iteration pre-pass and the user supplies an explicit `reference_block_time` of `0`, plan construction SHALL fail with `GUNZ_INVALID_LIBRARY`.
A non-zero `reference_source` requires `reference_block_time > 0`; see the normative consistency rule in §4.2.1.


**If the bytecode contains no `ZONE` instructions:**  
 
  - If the user supplies an explicit `reference_block_time`, the map header's `reference_source` SHALL be set to `1` (explicit), consistent with §4.2.1.  
 
  - If the user supplies an explicit `reference_block_time` of `0`, plan construction SHALL fail with `GUNZ_INVALID_LIBRARY`, because a non-zero `reference_source` requires `reference_block_time > 0`.

  - If no explicit `reference_block_time` is provided, the `reference_block_time`SHALL default to `0`, and the map header's `reference_source` SHALL be set to `0` (not applicable).

  - If the map is non‑empty, for example because it contains `FLAG_SKIPPED` placeholders or type‑0 long‑jump entries from `SKIP_ZONE` instructions, it remains a valid non‑empty map.
 
 The provenance of the reference (explicit, guessed, or calibrated) is recorded in the map header's `reference_source` field (§4.2.1). The value actually used is recorded in the map header and the `.gunzmeta` file (§4.6).  
 
**If the bytecode contains one or more `ZONE` instructions but no `ZONE` is included by the global iteration pre-pass:**

  - If the user supplies an explicit `reference_block_time` greater than `0`, the map header's `reference_source` SHALL be set to `1` (explicit).
 
  - If no explicit `reference_block_time` is provided, the map header SHALL use: `reference_source = 0` and `reference_block_time = 0` because no candidate evaluation occurred.

  - If the user supplies an explicit `reference_block_time` of `0`, plan construction SHALL fail with `GUNZ_INVALID_LIBRARY`, because a non-zero `reference_source`
requires `reference_block_time > 0`.
 
  - The guessing rule SHALL NOT be applied to an excluded zone.

**If the computed or user‑supplied `reference_block_time` exceeds `UINT32_MAX`, plan construction SHALL fail with `GUNZ_INVALID_LIBRARY`.**
 The user must choose a coarser `time_unit` or adjust the target so that the reference value fits within the `u32` field.  

  *Note:* All time values in the evaluator, including `reference_block_time`, are expressed in the base time unit defined by `time_unit`. No conversion to seconds is performed.

- `effective_step` – the program‑wide dense‑scan step size in 10⁻⁵ Hz units, as defined in §3.3.

- `map_type` – from the map header: `0` = standard, `1` = detrimental. The map header also provides separate detrimental thresholds for jitter and advance regularity. `map_type`, `detrimental_jitter_threshold`, and `detrimental_advance_regularity_threshold` are plan‑construction inputs only. They are not set by bytecode opcodes, and they are not defined by library profiles. Bytecode programs use the values supplied by the surrounding `ExecutionPlan`; the bytecode ISA has no opcode for these parameters.

- An optional **explicit delta pair** `(d_lo_ov, d_hi_ov)` with a boolean flag indicating whether the override is active. If the flag is true, the evaluator uses the override values for the block‑time sum only; it does **not** alter the computation of `N` or `N_hi`.  
 
 *(Informative)* The delta override allows you to change how much work each cycle contributes while keeping the exact same timing pattern and cycle count. It is useful for exploring "what‑if" scenarios in any discrete‑clock system where the per‑step magnitude can be tuned independently of the step rate.  

  *(Normative)* After applying the override, the resulting `block_time` is guaranteed to be an integer multiple of `quantum` by construction (the formula multiplies an integer sum by `quantum`).

- If `long_term_scan` is active, a **measurement window duration** `window_duration` (a `u64` in the **same base time unit as the header**) is supplied at plan construction and embedded in the evaluator block. The normative maximum `window_duration` is **`2⁶⁴ − 1`** base‑time units. 
 
  *Rationale:*  The evaluator already uses 128‑bit accumulators for all temporal sums (§3.4.2, §3.11 step 3), and the per‑candidate `max_eval_iterations` limit prevents unbounded simulation.  The previous 32‑bit cap was a conservative safety measure; raising it to 64 bits allows multi‑hour observation windows at nanosecond precision without sacrificing determinism or safety.  Implementations that support `long_term_scan` must ensure that the per‑candidate iteration limit (`max_eval_iterations`) is set appropriately for the chosen window.  
  The `window_duration` value as a `u64` integer must not exceed `2⁶⁴−1`; no additional scaling is applied. Plan construction **SHALL** reject a request where `window_duration > 2⁶⁴−1` and return `GUNZ_INVALID_LIBRARY`.

- `jitter_window_radius` – the effective radius, in 10⁻⁵ Hz units, for the jitter‑point window. This value is resolved at plan construction time per §3.10: if the library profile specifies a non‑zero `jitter_window_radius`, the effective radius is `stored_value × 1000`; otherwise the default **10000** (21 points, ±0.1 Hz) is used. The resolved radius is always a multiple of 1000.


**Evaluator‑skipped candidates (normative).**
An *evaluator‑skipped candidate* is a candidate that Phase 1 cannot evaluate, for any of the following reasons:

- zero continuous advance,
- N‑search failure,
- `N` exceeding `MAX_N`,
- long‑term `max_eval_iterations` exhaustion,
- no valid jitter points.

An evaluator‑skipped candidate is emitted as a normal map entry with saturated sentinels, `FLAG_INVALID` set, `FLAG_AVOID` set, and `stability_width = 0`. It SHALL NOT be marked `FLAG_SKIPPED`.

`FLAG_SKIPPED` is reserved for candidates intentionally not evaluated because they belong to a `SKIP_ZONE` or to an inter‑zone gap. It SHALL NOT be used for evaluator‑skipped candidates.

In Phase 2, the term *skipped candidate* denotes any candidate that is not an evaluated plateau member:

- evaluator‑skipped candidates (`FLAG_INVALID`)
- intentionally skipped placeholders (`FLAG_SKIPPED`)

These candidates SHALL NOT be used as stability‑interval centers or members.
They act as hard boundaries: no stability interval may extend across one.

Long‑jump entries are gaps, not candidates.

For every evaluator‑skipped candidate, regardless of which skip path is taken, both `FLAG_CENTRAL_ABOVE` and `FLAG_CENTRAL_BELOW` SHALL be clear on the emitted saturated‑skipped entry.

**Algorithm:**

The evaluator proceeds in two phases:

**Phase 1 — Dense scan.** The zone is sampled at `freq_candidate = freq_low, freq_low + effective_step, …` up to and including `freq_high`. For each `freq_candidate`:

1. **Compute cycle time.**  

``` 
   `T = 10^(time_unit + 5) / freq_candidate` (64‑bit unsigned integer division; for `time_unit ≤ 12` the numerator fits safely in 64 bits). For `time_unit ≥ 10`, implementations are encouraged to compute the numerator in 128‑bit before division to maintain future‑compatibility with extended ranges.  
   *(Note: `10^(time_unit+5)` converts the frequency expressed in 10⁻⁵ Hz to the base time unit (seconds × 10^−time_unit).)*  
   Compute the **continuous deltas** that define the temporal pattern of `d_hi` cycles:  
   `d_lo_cont = T / quantum` (floor), `d_hi_cont = d_lo_cont + 1`.
``` 

2. **Jitter window evaluation.**  
 
``` 
   Let `R = jitter_window_radius`. The jitter offsets Δ are generated as:  
   `Δ = -R, -R+1000, -R+2000, …, +R`.  

   For each Δ, compute:

     `freq_jitter = (i64)freq_candidate + Δ`

   using at least 64‑bit signed arithmetic.

   If `freq_jitter ≤ 0`, that jitter point is skipped and does not contribute to the sample count.
``` 
For forward compatibility, if a future revision allows `freq_candidate = 0` or otherwise removes the guarantee that the offset `Δ = 0` is valid, the implementation SHALL handle the no‑valid‑point case by marking the candidate with saturated sentinels, setting `FLAG_AVOID`, setting `FLAG_INVALID`, and setting `stability_width = 0`.

 The candidate is a hard boundary in Phase 2 and has no `.gunzstats` record.

Under the current bounds, this case cannot occur.
 
   For each valid jitter point, compute `T_jitter` from `freq_jitter`. The block simulation SHALL then use `T_jitter` in place of `T`, recomputing `d_lo_cont`, `d_hi_cont`, `adv_lo_cont`, and `adv_hi_cont` from `T_jitter`, and proceed through Step 3.

   *(The `jitter` field is stored as a `u8` and saturates at 255 base‑time units.  For coarse time units such as seconds (`time_unit = 0`), this saturation limit may be reached even for moderately irregular scans.  Users should choose a `time_unit` that keeps expected jitter values within the representable range, or consult the raw `.gunzstats` file for full‑precision data.)*  

   Advance regularity is computed from the counts `N_lo` (where `N_lo = N − N_hi`) and `N_hi` using a closed‑form multiset variance. Each advance value (in ticks) is scaled by 100, yielding two values `a = 100 × adv_lo` and `b = 100 × adv_hi`. **The values `a` and `b` SHALL always be `100 × adv_lo_cont` and `100 × adv_hi_cont`, regardless of whether a `DELTA` override is active. The `DELTA` override affects only the block‑time sum; it does not alter advance regularity.** The advance regularity for this jitter point is the population standard deviation of the multiset consisting of `N_lo` copies of `a` and `N_hi` copies of `b`, computed via the integer standard deviation algorithm of §4.5.3. **This per‑point value remains full‑precision (in ticks × 100).**  

**Averaging and saturation:**
The full‑precision per‑point advance regularity values across all valid jitter points are averaged using half‑to‑even rounding. For storage in the map entry, this average is saturated to 65535 and written to the `advance_regularity` field. The maximum of the full‑precision per‑point values (before averaging) is saturated to 65535 and stored in `peak_advance_regularity`.

All saturation occurs after the full‑precision computations and does not affect  `block_time_inaccuracy` or `jitter`.

**Long‑term mode aggregation:**
 When `long_term_scan` is active, the `jitter` and `advance_regularity` for a candidate are computed as follows:  

   – For each valid jitter point, evaluate the sequence of temporal blocks exactly as described in Step 3 (long‑term mode). This yields, for each jitter point, a set of total block times and per‑cycle advance values.  

   – **Jitter:** 
Collect *all* **total block times** (`total_time_i`, raw block time plus hold/sep contribution) from *all* valid jitter points across the entire measurement window into a single multiset. The candidate's `jitter` is the population standard deviation of that combined multiset, computed via §4.5.3.  

   – **Advance regularity:** 
For each jitter point, collect all per‑cycle advance values (each expressed as `a = 100 × adv_lo` or `b = 100 × adv_hi`) from all blocks evaluated in the temporal window into a single multiset. Compute the population standard deviation of that combined multiset using the algorithm of §4.5.3. **This full‑precision value (ticks × 100) is the per‑jitter‑point advance regularity.**  

Then average these full‑precision per‑point values across all valid jitter points, using half‑to‑even rounding. This full‑precision average is:
- saturated to `65535` and stored in `advance_regularity`;
- used as the `advance_regularity` input to the derived `advance_regularity_btu` computation for detrimental‑threshold comparison.

The maximum of the full‑precision per‑point values (before averaging) is saturated to `65535` and stored in `peak_advance_regularity`.

   *(Note: In long‑term mode, `peak_advance_regularity` is the maximum of the per‑jitter‑point pooled aggregates, not the maximum of individual per‑block values.  For per‑block worst‑case analysis, the `.gunzmeta` file may provide `resonance_quality.max_per_block_advance_regularity` when computed by the implementation.)*  

   **Per‑block advance regularity (optional).**
  For each valid jitter point, and for each block evaluated within that jitter point, the scanner **MAY** compute the advance regularity of that single block.  The per‑block advance regularity is the population standard deviation of the per‑cycle advance values within that block, computed using the same two‑valued multiset closed‑form of §4.5.3.  The scanner **MAY** maintain a running maximum of these per‑block values across all blocks and all jitter points for a given candidate.  If this maximum is recorded, it shall be stored in the metadata field `resonance_quality.max_per_block_advance_regularity` (see §4.6).

   *(Informative) Without a drift model that varies block parameters across the measurement window, every block produces identical per‑block advance regularity.  In that case `max_per_block_advance_regularity` will equal the pooled advance regularity already stored in the map entry.  The metric becomes diagnostically useful when combined with a drift model (GUNZ‑DRIFT) that introduces block‑to‑block variation.*  

   This reduction ensures the map reflects the worst‑case behaviour across both spatial and temporal dimensions.

   *Note on saturation:* 
The per‑point values remain full‑precision throughout the aggregation; only the final stored fields are clamped to 16‑bit range. Raw, full‑precision statistics are preserved in the optional `.gunzstats` file.

3. **Discrete simulation of a single block.**  
   Given the **continuous deltas** `d_lo_cont`, `d_hi_cont`:
   - Compute the **continuous advances**: `adv_lo_cont = (d_lo_cont * mult_num) / mult_den` (floor), `adv_hi_cont` similarly. Use 128‑bit intermediates. *(Division by zero cannot occur because `mult_den` is required to be non‑zero at plan construction.)*

   - If `max(adv_lo_cont, adv_hi_cont) == 0`, set saturation sentinels, set `FLAG_AVOID`, set `FLAG_INVALID`, and skip.

   - **Computing `N`:** 
     A conformant implementation **SHALL** determine `N` by the following method:  
     Start from the closed‑form estimate `N₀ = ceil(target_ticks / max(adv_lo_cont, adv_hi_cont, 1))`.  
     If `N₀ > MAX_N`, mark candidate saturated with all metric fields set to their saturated sentinel values, set `FLAG_AVOID`, set `FLAG_INVALID`, and set `stability_width = 0`; do not enter the search loop. Increment `N` monotonically (by 1) from `N₀`.  At each `N`, compute `N_hi` via the rounding procedure below. 
     If `N_hi` is within `[0, N]` **and** the actual total tick advance `(N − N_hi) × adv_lo_cont + N_hi × adv_hi_cont` reaches or exceeds `target_ticks`, accept this `N` and stop.  
     If `N_hi` is outside `[0, N]` or the advance is insufficient, continue to the next `N`.  
     The search must proceed up to `MAX_N = 2³¹ − 1`.  If no `N` satisfying both conditions is found, mark the candidate with saturated sentinels, set `FLAG_AVOID`, set `FLAG_INVALID` and set `stability_width = 0`.  
     The monotonic N‑search is bounded **only** by `MAX_N = 2³¹ − 1`. The plan’s `max_eval_iterations` SHALL NOT be applied as a bound on the N‑search in non‑long‑term scans.  
     An implementation MAY use an internal shortcut that provably yields identical candidate classification, including `N`, `N_hi`, validity flags, saturated sentinels, `FLAG_AVOID` status, and `FLAG_INVALID` status, for all inputs. No conformant implementation SHALL reject a candidate solely because the monotonic search required more than `max_eval_iterations` steps.
   
   - The computed `N` must be validated by computing the actual total advance using the derived `N_hi`, and must not exceed `MAX_N = 2³¹ − 1`. If the computed `N` exceeds `MAX_N = 2³¹ − 1`, the candidate is marked with saturated sentinels, `FLAG_AVOID` is set, `FLAG_INVALID` is set, and the candidate is skipped. This condition does **not** cause `GUNZ_ITERATION_LIMIT_EXCEEDED`.  The evaluator emits a normal entry with all metric fields set to their saturated sentinel value, `FLAG_INVALID` and `FLAG_AVOID` set.

   - `R = round(N * T / quantum) * quantum` (128‑bit for `N*T`). The rounding function uses the current `round_mode`.

   - `Q = R / quantum`; compute `N_hi = Q − N*d_lo_cont`.  
 
     The product `N * d_lo_cont` and the subtraction `Q − N * d_lo_cont` SHALL be computed using 128‑bit unsigned arithmetic. 
 
     If `N_hi` is within `[0, N]`, let `N_lo = N − N_hi` and check that `N_lo * adv_lo_cont + N_hi * adv_hi_cont ≥ target_ticks`. If the advance is insufficient, or if `N_hi` is outside `[0, N]`, the candidate is invalid: set saturated sentinels, set `FLAG_AVOID`, set `FLAG_INVALID`, and skip the remaining steps for this candidate.
   
   - **Block time computation:**  
     If an explicit delta override is **not** active: `block_time = R`.  
     If an override **is** active: `block_time = ((N − N_hi) * d_lo_ov + N_hi * d_hi_ov) * quantum`. **This computation MUST be performed using 128‑bit unsigned arithmetic before the result is stored, to prevent integer overflow.**

   - **Long‑term zero raw block time:**  
     In **long‑term mode only**, after `block_time` has been computed, if `block_time == 0`, the candidate SHALL be treated as evaluator-skipped: saturated sentinels, `FLAG_AVOID` set, `FLAG_INVALID` set, `stability_width = 0`, and no block repetition SHALL be attempted.

   - **`total_time` computation:**  
     `total_time = block_time + (hold_cycles + sep_cycles) * T`. **The multiplication `(hold_cycles + sep_cycles) × T` and the subsequent addition shall be performed using 128‑bit unsigned arithmetic.** The absolute difference `|total_time − reference_block_time|` is then computed in 128‑bit arithmetic before being saturated to `UINT32_MAX` and stored in `block_time_inaccuracy`.
   
   - In **long‑term mode**, the evaluator repeats the block simulation until the cumulative block time (excluding hold/sep) reaches or exceeds `window_duration`.  For each block `i`, the per‑block total time is computed as  
     ```
     total_time_i = block_time_i + (hold_cycles + sep_cycles) * T_i
     ```  
     where `T_i` is the cycle time for that block.  The long‑term total time `total_time_lt` is the arithmetic mean of these per‑block total times, computed with half‑to‑even division:  
     ```
     total_time_lt = round_half_even( sum(total_time_i) / block_count )
     ```  
     The `block_time_inaccuracy` field is then `|total_time_lt − reference_block_time|`, saturated to `UINT32_MAX`.  

The division `round_half_even( sum(total_time_i) / block_count )` SHALL be performed in **256‑bit unsigned integer arithmetic**, preserving the full precision of the 256‑bit numerator. The rounding rule of §4.5.1 applies.

The sum `sum(total_time_i)` used in the long-term mean SHALL be accumulated in a 256-bit unsigned integer.


     If `max_eval_iterations` is exhausted before `window_duration` is reached, the candidate shall be marked with saturated sentinels, set `FLAG_AVOID`, set `FLAG_INVALID`; no partial average is emitted. The same `max_eval_iterations` (derived from `quantum` as specified in §3.4.1) applies to all candidates in the zone.

     Consequently, the long‑term aggregated metrics will be identical to those of a single‑block scan.  Long‑term mode is designed to be combined with a drift model to reveal temporal instability; used alone, it provides no additional information beyond a standard scan.

     **The cumulative block time used to compare against `window_duration` shall be accumulated in a 128‑bit unsigned integer to ensure determinism across the full normative window range.**

   - **Memory efficiency (normative):** 
All per‑candidate temporary data (block time accumulators, jitter accumulators, variance intermediates) **must** be stored in the `ScratchArena` and reused across blocks. Implementations shall **not** allocate separate per‑block buffers.

- **Skipped candidate handling:**
For any candidate skipped for any reason — zero advance, N‑search failure, exceeded `MAX_N`, long‑term `max_eval_iterations` exhaustion, or no valid jitter points — the evaluator SHALL mark the candidate with saturated sentinels, set `FLAG_AVOID`, set `FLAG_INVALID`, set `stability_width = 0`, and clear both `FLAG_CENTRAL_ABOVE` and `FLAG_CENTRAL_BELOW`.

Skipped candidates are not successfully evaluated and therefore have no `.gunzstats` record.

In Phase 2, skipped candidates are hard boundaries. They are never used as stability‑interval centers or members.

No saturated‑skipped candidate SHALL carry `FLAG_SKIPPED`.

Every saturated‑skipped candidate that is emitted as a normal map entry SHALL carry both `FLAG_AVOID` and `FLAG_INVALID`.

- **Central‑direction assignment:**
For every evaluated candidate, the evaluator SHALL set the central‑direction flags using the central total time, which is the total time computed at jitter offset Δ = 0 (i.e., at the original candidate frequency `freq_candidate`).

- Non‑long‑term scan:
  the central total time is the single‑block `total_time` computed at Δ = 0.

- Long‑term scan:
  the central total time is `total_time_lt` computed at Δ = 0.

No other jitter offset may be used for central‑direction assignment.

Assignment:

- central total time > `reference_block_time`:
    set `FLAG_CENTRAL_ABOVE`; clear `FLAG_CENTRAL_BELOW`.

- central total time < `reference_block_time`:
    set `FLAG_CENTRAL_BELOW`; clear `FLAG_CENTRAL_ABOVE`.

- central total time == `reference_block_time`:
    clear both flags.

This assignment SHALL be performed before final map‑entry consolidation and before any attached `PURE_CALL` is invoked.


**Three‑Way Metric Model**

GUNZ does not compute a single scalar quality score. Instead, each evaluated candidate carries three independent lower‑is‑better metrics.

For these metrics, the **central total time** is:

- non‑long‑term scan: single‑block `total_time` at jitter offset Δ = 0;
- long‑term scan: `total_time_lt` at jitter offset Δ = 0.

This is the same central total time used for `FLAG_CENTRAL_ABOVE` and `FLAG_CENTRAL_BELOW`.

1. **`block_time_inaccuracy`**

   The absolute deviation of the candidate’s central total time from `reference_block_time`, expressed in base time units.

   *Usefulness:* This is the primary indicator of how closely the timing matches the desired target. It is directly comparable across scans with the same `time_unit`.

   Because it is an absolute value, it loses the sign of the deviation. The central‑direction flags `FLAG_CENTRAL_ABOVE` and `FLAG_CENTRAL_BELOW` preserve whether the central total time was above or below `reference_block_time`.

2. **`jitter`**

   The population standard deviation of total block times across all valid jitter offsets in the window, expressed in base time units.

   *Usefulness:* This captures spatial sensitivity: how much the block time changes when the operating frequency is perturbed slightly. Low jitter indicates a plateau‑like region; high jitter indicates a sharp resonance edge or unstable neighbourhood.

3. **`advance_regularity`**

   The average per‑cycle advance consistency across the jitter window, expressed in ticks × 100.

   *Usefulness:* This quantifies how evenly the discrete clock advances are distributed within a block. Irregular advance patterns can cause internal timing stress, even if the total block time is accurate.

`peak_advance_regularity` is a diagnostic maximum and does not participate in ranking.

`stability_width` is a fourth independent map field. It is not one of the three lower‑is‑better metrics. It records the physical total‑time plateau width defined in §3.11 Phase 2, is higher‑is‑better, and SHALL NOT be combined with the three metrics by the core evaluator.

All stored map‑entry values are saturated:

- `block_time_inaccuracy` saturates at `UINT32_MAX`;
- `jitter` saturates at `255`;
- `advance_regularity` and `peak_advance_regularity` saturate at `65535`.

Full‑precision values remain available in `.gunzstats` or `.gunzstatz` when present.

 `PURE_CALL` post‑processing does not alter the three stored metrics or any map flag. Callback writes are ignored for map generation.

Detrimental `FLAG_AVOID` marking in the core uses only `jitter` and the derived `advance_regularity_btu` thresholds. `block_time_inaccuracy` does not have a core detrimental threshold; it is primarily a ranking metric. External tools may define their own inaccuracy thresholds.

Because the metrics have different units and physical meanings, the core specification does not combine them into a scalar score. Ranking, trade‑off, and Pareto analysis are performed by external tools such as GUNZ‑DEWASTER, using application‑specific policy.


**Candidate post‑processing (if a `PURE_CALL` is attached).**

If the zone has an attached `PURE_CALL` (captured from the bytecode and resolved at plan‑construction time), the evaluator **SHALL** invoke the callback for each candidate immediately after the following values have been computed:

- `block_time_inaccuracy`
- `jitter`
- `advance_regularity`
- `peak_advance_regularity`
- central‑direction flags
- any detrimental flags

The callback **SHALL NOT** be invoked for candidates skipped because:

- `max(adv_lo_cont, adv_hi_cont) == 0`
- the N‑search failed
- `N` exceeded `MAX_N`
- long‑term `max_eval_iterations` was exhausted
- no valid jitter points remain

Such candidates are emitted directly with saturated sentinels, `FLAG_AVOID` set, and `FLAG_INVALID` set, without callback involvement.

---

**Candidate context structure.**  
The runtime allocates a buffer of exactly `output_size` bytes, as declared in the library profile for the callback. The core candidate context is exactly **16 bytes**.

| Offset | Size | Field | Description |
|--------|------|-------|-------------|
| 0  | u32 | `freq_candidate` | Evaluator‑computed candidate frequency, in 10⁻⁵ Hz units. The evaluator always uses the original candidate frequency for the map entry, ignoring any value written by the callback. |
| 4  | u32 | `block_time_inaccuracy` | Evaluator‑computed value, saturated to `UINT32_MAX`. Callback writes are ignored. |
| 8  | u8  | `jitter` | Evaluator‑computed value, saturated to `255`. Callback writes are ignored. |
| 9  | u8  | `flags` | Evaluator‑computed flags before the callback. Bits 0–3 may include `FLAG_AVOID`. Bits 4–5 contain the central‑direction flags assigned before the callback. Bits 6–7 are reserved and zero. Callback writes are ignored. |
| 10 | u16 | `advance_regularity` | Evaluator‑computed average advance regularity, saturated to `65535`. Callback writes are ignored. |
| 12 | u16 | `peak_advance_regularity` | Evaluator‑computed peak advance regularity, saturated to `65535`. Diagnostic only. Callback writes are ignored. |
| 14 | u16 | `stability_width` | Written as `0` by the evaluator. Final value assigned by Phase 2. Callback writes are ignored. |

The callback receives the original bytecode arguments from the `PURE_CALL` instruction as the `args` parameter, and the candidate context buffer as the `output` parameter.

---

**Callback write policy.**  
The callback MAY read the entire candidate context buffer and MAY write to it as temporary scratch workspace.

**However, the evaluator SHALL ignore all callback writes for map generation.** The canonical map entry uses only the metrics, flags, and stability width computed by the evaluator before the callback was invoked.

In particular, callback writes SHALL NOT affect:

- `FLAG_AVOID`
- `FLAG_SKIPPED`
- `FLAG_INVALID`
- `FLAG_CENTRAL_ABOVE`
- `FLAG_CENTRAL_BELOW`
- `STAB_SATURATED`

The evaluator always uses the original candidate frequency for the map entry, ignoring any value written by the callback to `freq_candidate`.

The callback’s only normative effects on the scan are its return value:

- `GUNZ_OK` — candidate processing continues.
- `GUNZ_CALLBACK_FAILED` — the run aborts immediately.
- `GUNZ_SANDBOX_VIOLATION` — the run aborts immediately under sandboxing.

The `.gunzmap` file SHALL NOT contain any `PURE_CALL`‑modified data.

---

**Companion extension area.**  
A companion specification such as GUNZ‑DRIFT may extend the candidate context buffer with additional fields after offset 16. Such an extension defines the extended layout and any additional callback restrictions.

The core 16‑byte layout remains the mandatory prefix. Companion extensions SHALL NOT redefine or overwrite the first 16 bytes.

Before the callback is invoked, the runtime SHALL zero‑fill all bytes of the `output` buffer that lie beyond the end of the applicable candidate context layout.

For core‑only operation, the applicable layout is the 16‑byte core candidate context. The zero‑fill region begins at offset 16 and continues through `output_size − 1`. The bytes in that region are available to the callback as scratch space, and any writes there SHALL also be ignored by the evaluator for map generation.

When a companion extension is active, the applicable layout is defined by that companion. The zero‑fill region SHALL begin after the end of the extension‑defined candidate context layout and continue through `output_size − 1`.

---

**Post‑callback processing.**  
After the callback returns, the evaluator SHALL discard all modifications made by the callback to the candidate context buffer.

The stored map entry and Phase 2 stability width are derived solely from the evaluator‑computed values that existed before the callback was invoked.

No clamping, score recomputation, or flag restoration is performed. No score exists in the map entry.

If a deployment wishes to preserve callback‑specific observations, that preservation SHALL occur outside the canonical map pipeline. Such data SHALL NOT be serialised into the `.gunzmap` file.


**Explicit delta override semantics (summary):**  
When a `DELTA` instruction is active, the override does **not** change the number of cycles `N` or the count of `d_hi` cycles `N_hi`. Those are always computed from the continuous deltas `d_lo_cont`, `d_hi_cont`, preserving the temporal pattern dictated by the continuous cycle time `T`. The override values `d_lo_ov`, `d_hi_ov` replace only the per‑cycle advance magnitudes in the final block‑time sum, as shown in Step 3. Advance regularity remains based on the continuous advances.


**Phase 2— Physical stability width**

stability_tolerance_time is computed once per map from the map header:

    stability_tolerance_time =
        max(quantum, round_half_even(reference_block_time / 1_000_000))

where:

- / denotes the exact rational quotient;
- round_half_even is the half‑to‑even integer division defined in §4.5.1;
- stability_tolerance_time is expressed in base time units;
- stability_tolerance_time is constant for the whole map.

For maps containing evaluated candidates, reference_block_time SHALL be non‑zero, so the division is well‑defined. No‑scan maps have no evaluated candidates and therefore no Phase 2 computation.

For each evaluated candidate c, its central total time T_c is:

- non‑long‑term scan: single‑block total_time computed at jitter offset Δ = 0.
- long‑term scan: total_time_lt computed at jitter offset Δ = 0.

The plateau computation uses full‑precision central total times. It SHALL NOT use the saturated block_time_inaccuracy field.

The evaluated‑candidate array is the list of candidates in ascending frequency order, excluding:

- FLAG_SKIPPED candidates,
- FLAG_INVALID candidates,
- long‑jump gaps.

For an evaluated candidate c, the plateau is the maximal contiguous run of evaluated candidates containing c such that for every candidate i in that run:

    | T_i − T_c | ≤ stability_tolerance_time

A run is contiguous if consecutive candidates in the run are adjacent in the global frequency grid with no skipped candidate, invalid candidate, or long‑jump gap between them.

The plateau is constructed by expanding left and right from c in the evaluated‑candidate array until the tolerance condition fails or a hard boundary is reached.

FLAG_SKIPPED candidates and FLAG_INVALID candidates are not centers or members, but act as hard boundaries.

Long‑jump entries are gaps, not candidates. They contain no evaluated candidates, and therefore also act as hard boundaries: a stability plateau SHALL NOT extend across a long‑jump entry.

Sparse‑omitted perfect intervals are evaluated candidates and MAY be plateau members if their central total times satisfy the tolerance.

The stability width is:

    stability_width =
        (freq_candidate[right] − freq_candidate[left]) // 10

where // is floor division on non‑negative integers, as defined in the Notation Box. The result is expressed in 0.0001 Hz units and saturated to 65535.

If right == left, stability_width = 0.

Informative: This definition replaces the previous score‑based stability width and the time_unit < 9 zero‑width rule. Stability width is now derived from central total time alone and is meaningful at all time_unit values.

**Saturation flag:** 
If the pre‑saturation stability width exceeds 65535, the stored width is 65535 and `STAB_SATURATED` is set. If the pre‑saturation width equals 65535, the flag is cleared (the width is exactly representable). A cleared flag with a width of 65535 means "exactly 6.5535 Hz," not "unknown."

**Derived advance‑regularity threshold value (normative).** 
Before detrimental‑mode marking, the evaluator SHALL compute:

```text
advance_regularity_btu =
    round_half_even(
        (advance_regularity × mult_den × quantum)
        /
        (mult_num × 100)
    )
```

The division `/` denotes the exact rational quotient; `round_half_even` is the half‑to‑even integer division defined in §4.5.1, where `advance_regularity` is the full‑precision per‑candidate average computed in Step 2, not the saturated `u16` map‑entry field.  
The result is expressed in base time units and SHALL be used only for the detrimental advance‑regularity threshold comparison.

**Detrimental mode marking.**
When `map_type = 1`, an evaluated interval SHALL be marked `FLAG_AVOID` if:

- its `jitter` ≥ `detrimental_jitter_threshold`, **or**
- its `advance_regularity_btu` ≥ `detrimental_advance_regularity_threshold`.

Detrimental `FLAG_AVOID` marking SHALL use the full‑precision `jitter` computed in Step 2 and the full‑precision converted `advance_regularity_btu` computed from the full‑precision average advance regularity. It SHALL NOT use the saturated `u8`/`u16` map‑entry fields.

For `map_type = 0`, detrimental marking is inactive.

Zero is a plan‑construction shorthand only. Before evaluation, any zero threshold is resolved to the saturation limit of the corresponding field:

- `detrimental_jitter_threshold = 0` resolves to `255`
- `detrimental_advance_regularity_threshold = 0` resolves to `65535`

The evaluator uses the resolved value. The map header stores the resolved value; zero is never stored.

This marking SHALL be applied after Phase 2 and before:

- `SparseMapBuilder` emission,
- sparse emission if enabled,
- and final map‑entry consolidation.

**Final Map entry consolidation:** 
After the map‑assembly pipeline defined in §3.3 has completed, consecutive normal entries with identical metrics and flags SHALL be merged into a single entry. Its `run_length` equals the number of merged candidates. Merging `n` consecutive candidates produces `run_length = n`. Only the first entry in the run contributes a `freq_delta_start`; subsequent merged candidates do not. A normal entry with `freq_delta_start > 0` SHALL begin a new consolidation run and SHALL NOT be merged into the preceding run. Consolidation SHALL NOT merge across such a positive-delta boundary.

Final consolidation SHALL be the last step of the map assembly pipeline: it is applied after gap insertion, and after sparse emission if sparse emission is enabled.
Internal zone‑local grouping, if used, SHALL be reversible and SHALL NOT be visible to gap insertion or sparse emission.
Long‑jump entries are not normal entries and SHALL NOT be merged.

**Skipped zones:**
A `SKIP_ZONE` is represented in the final map by the global special-zone boundary insertion phase of §3.3.

Per-thread `SparseMapBuilder`s SHALL NOT emit skipped-zone placeholders, skipped-zone long-jumps, or skipped-zone alignment long-jumps.
The global merge/gap-detection phase SHALL process a skipped zone only through the special-zone cursor defined in §3.3.

If a `SKIP_ZONE` is also marked excluded by the global iteration pre-pass, the excluded-zone rules of §3.3 SHALL take precedence, and no skipped-zone
representation SHALL be emitted for it. A `FLAG_SKIPPED` placeholder emitted for a skipped zone SHALL have `freq_delta_start = 0`, as specified in §3.3.

**Large zone clamping:**  
If a zone’s candidate count (computed as `(freq_high − freq_low) / effective_step + 1`) exceeds the plan’s `max_scan_iterations`, the evaluator SHALL evaluate only the first `max_scan_iterations` candidates in ascending frequency order, starting at `freq_low`. The remaining candidates are not evaluated.

After emitting the evaluated portion as unconsolidated candidate intervals, the evaluator SHALL emit one or more long‑jump entries covering the skipped remainder. The total gap is:

```
gap = (freq_high + effective_step)
       − (freq_low + max_scan_iterations × effective_step)
```

or equivalently:

```
gap = (freq_high − freq_low)
       − (max_scan_iterations − 1) × effective_step
```

These long‑jump entries SHALL carry type `0`. In the absolute-frequency merge phase, this advances `global_merge_current` to `freq_high + effective_step`, the first grid frequency after the zone. **If this gap exceeds `max_lj_gap`, the evaluator SHALL emit a sequence of long‑jump entries, each with a gap of at most `max_lj_gap`, until the total gap is covered.**

Per‑zone truncation alone does not cause an error return. The evaluator continues with subsequent zones. If the global iteration pre‑pass has excluded any zone, the evaluator still returns `GUNZ_ITERATION_LIMIT_EXCEEDED` after all included zones finish.

 **Global iteration limit enforcement.**  
 Before parallel evaluation begins, the runtime shall perform a single‑threaded pre‑pass to determine which zones can be evaluated within the global iteration budget.  This pre‑pass guarantees that the set of evaluated and excluded zones is entirely deterministic and independent of thread scheduling.

1. **Effective candidate count.** For each zone, compute `candidates(zone)`.
   – If the zone is a `SKIP_ZONE`, `candidates = 0`.
   – For a `ZONE`, `candidates = min( (freq_high − freq_low) / effective_step + 1,  max_scan_iterations )`.
   *`effective_step` is the program‑wide effective step size as established by the last `SCAN_RES` before the first zone (defaulting to 1 if 0 or absent).*
   The division is integer division (floor).  Because `freq_low ≤ freq_high` and zones are grid‑aligned, the result is exact and non‑negative.
2. **Deterministic ordering.** Sort the zones by ascending `freq_low` (the zones are already strictly disjoint, so ties cannot occur).
3. **Budget walk.** Walk the sorted list with a running total `consumed`, initialised to 0.  For each zone in order:
  – If `consumed + candidates(zone) ≤ total_max_scan_iterations`, mark the zone as **included** and add its candidate count to `consumed`.
  – Otherwise, mark the zone as **excluded** and stop the walk; all subsequent zones in the ordered list are also excluded.

 After the pre‑pass completes, the runtime spawns worker threads only for the included zones.
 – Each included zone proceeds through its **normal evaluation**, including its own `max_scan_iterations` truncation if applicable.  No further global‑budget checks are required within the zone.

Excluded zones SHALL be processed exclusively by the §3.3 Special-zone
boundary insertion subsection. No separate excluded-zone emission rules apply
in this section.

*(Informative)* The resulting representation is one or more type-0 long-jump entries. When `global_merge_current < freq_low`, the emitted sequence covers
both the inter-zone gap and the excluded zone as a single unevaluated interval. No separate `FLAG_SKIPPED` or alignment entry is emitted before that sequence.

Because an excluded-zone sequence starts at `global_merge_current` immediately before the excluded zone, the generic gap-detection phase treats the boundary
as `Δ == effective_step`, and no separate inter-zone gap entry is inserted. For the exact ordering, splitting, and cursor rules, see §3.3.

*(Informative)* The total gap for an excluded zone is:

```
  `gap_total = freq_high + effective_step − global_merge_current`
```

 When one or more zones are excluded, the evaluator shall return `GUNZ_ITERATION_LIMIT_EXCEEDED` after all included zones finish evaluation.

 *(Informative)*  Stopping at the first zone that does not fit is a deliberate design choice; it makes the mechanism simple and predictable.  An alternative scheme that skips unfitting zones and continues checking later ones would be equally deterministic, but it is **not** conformant under this specification.  Because exclusion is determined by a sequential budget walk that stops at the first non‑fitting zone, a `SKIP_ZONE` that appears after an excluded `ZONE` will also be excluded, even though it costs zero iterations.  This is a consequence of the deterministic ordering rule and ensures that the map's spatial coverage is predictable.

**Long-term header/entry consistency:**
The map header's `long_term_scan` field (offset 39) is the sole authoritative source for whether a map was produced in long‑term mode. There is no per‑entry flag for this information. A conformant decoder shall use the header field to determine the mode for all entries in the map.

## 4. GUNZ‑LIB (Libraries & Maps)

### 4.1 Library Profiles

- **`library_id`** — 16‑bit.
- **`generation`** — 64‑bit monotonic, assigned **only by the offline library compiler**.
- **`solver_version`** — 32‑bit.
- **`callback_abi_version`** — 32‑bit; a single global version for all callbacks in this library. The fingerprint hashes this value once.

- **`callback_id` uniqueness:**
  All `callback_id` values within a library profile must be unique.

- **`callback_output_size`** —
  For each `callback_id`, the library profile **SHALL** provide a `u32` output size.

  - For a regular `PURE_CALL`, this is the exact size of the `output` buffer. The callback may read and write this buffer as temporary scratch space; all writes are ignored for map generation.
  - For a streaming callback registered via `STREAM`, this is the size of the buffer that the runtime will fill with map entry data; the callback may read but must not modify it.

  The runtime **must** allocate a buffer of exactly this size for every invocation that targets the callback.

  If a sandboxed callback writes beyond this size, the sandbox **SHALL** abort the call and return `GUNZ_SANDBOX_VIOLATION`.

  In a non‑sandboxed execution, the runtime still allocates this exact size; the callback author is responsible for not exceeding it.

  For any `callback_id` that will be attached to a `ZONE` via the `PURE_CALL` mechanism, the declared `output_size` **SHALL** be at least 16 bytes — the size of the candidate context structure defined in §3.11 Step 5.

  Plan construction shall fail with `GUNZ_INVALID_LIBRARY` if a `PURE_CALL` is bound to a `ZONE` and the resolved callback has an `output_size` smaller than 16.

  The 16‑byte minimum applies only when the callback is bound to a `ZONE`, i.e. when it will be invoked per candidate.

  A `PURE_CALL` captured and attached to a `SKIP_ZONE` is silently discarded during evaluation; such a callback is not subject to the minimum.

- *(Informative)*
  A companion extension may define additional candidate context fields and impose a larger minimum `output_size`. In particular, GUNZ‑DRIFT requires a minimum `output_size` of 36 bytes for callbacks marked `drift_aware`.

  Core‑only implementations that do not support the companion SHALL enforce the core 16‑byte minimum and are not required to validate companion‑specific larger minimums.

- **Clock quantum and advance multiplier** —
  A conformant library profile SHALL supply:

  - `quantum` — u32; clock granularity in the base time unit.
  - `mult_num` — u32; advance multiplier numerator.
  - `mult_den` — u32; advance multiplier denominator.

  These are merged with the bytecode header under §3.10.

  Before and after merging, `quantum ≥ 1`, `mult_num ≠ 0`, and `mult_den ≠ 0`; any violation SHALL fail plan construction with `GUNZ_INVALID_LIBRARY`.

- **`jitter_window_radius`** — u8.
  If absent or set to `0`, the default radius **10000** — 21 points, ±0.1 Hz — is used.

  The value stored is the scale factor; the actual radius is:

  ```
  jitter_window_radius × 1000
  ```

  When a non‑zero value is specified, it must be in the range **1‑255**.

  The resulting radius is always a multiple of 1000.

- *(Informative)*
  Library rounding is intentionally not used. The bytecode header’s `round_mode` field is authoritative in all contexts.

- **Library profile validity** —
  A library profile is valid only if:

  ```
  quantum ≥ 1
  mult_num ≠ 0
  mult_den ≠ 0
  ```

  Profiles that violate these invariants shall be rejected during plan construction with `GUNZ_INVALID_LIBRARY`.

- **Compiler determinism** —
  The reference offline library compiler must produce byte‑identical libraries from identical source inputs.

  Other compilers may be used provided they reproduce the reference output.

### 4.2 Map Encoding

- All integers are little‑endian.
- Sparse intervals are tightly packed; no padding.
- Every map entry is exactly **16 bytes**. The fields are ordered to place all multi‑byte integers on their natural alignments:

| Offset | Size | Field | Description |
|--------|------|-------|-------------|
| 0  | s16  | `freq_delta_start`      | For normal entries: frequency offset (10⁻⁵ Hz units), relative to the decoder’s current frequency. For long‑jump entries: `u16` type tag. |
| 2  | u16  | `run_length`            | Number of consecutive candidates covered. A normal entry always has `run_length ≥ 1`. `0` is reserved for the long‑jump sentinel. |
| 4  | u32  | `block_time_inaccuracy` | Absolute difference between total block time and `reference_block_time`, saturated to `UINT32_MAX`.  This field holds the unsigned absolute difference `|total_time − reference_block_time|`.  The exact `total_time` **cannot** be reconstructed from the map entry alone; only the deviation magnitude is preserved.  For the precise total time, consult the raw per‑candidate data in the companion `.gunzstats` file.  Unit: base time unit. |
| 8  | u8   | `jitter`                | Total block‑time jitter (raw block time plus hold/sep contribution, base time unit). |
| 9  | u8   | `flags`                 | Interval flags (see below). |
| 10 | u16  | **`advance_regularity`** | **Average per‑cycle advance consistency (ticks × 100), saturated to 65535.** |
| 12 | u16  | **`peak_advance_regularity`** | **Peak advance regularity across the jitter window (ticks × 100), saturated to 65535.** |
| 14 | u16  | `stability_width`       | Stability region width (0.0001 Hz units). |

**Interval flags (u8):**

| Bit | Name | Description |
|-----|------|-------------|
| 0   | `STAB_SATURATED`  | Set when pre‑saturation stability width > 6.5535 Hz; not set for exactly 6.5535 Hz. |
| 1   | `FLAG_AVOID`     | Detrimental resonance. |
| 2 | `FLAG_SKIPPED` | Not evaluated because the zone was skipped. |
| 3 | `FLAG_INVALID` | Saturated‑skipped candidate; no `.gunzstats` record exists. |
| 4 | `FLAG_CENTRAL_ABOVE` | central block_time deviation direction, before any `PURE_CALL` post-processing, was strictly greater than `reference_block_time`. |
| 5 | `FLAG_CENTRAL_BELOW` | central block_time deviation direction, before any `PURE_CALL` post-processing, was strictly less than `reference_block_time`. |
| 6 | (reserved) | Must be 0. |
| 7 | (reserved) | Must be 0. |

For any normal map entry:

- `FLAG_SKIPPED` and `FLAG_AVOID` are mutually exclusive.
- `FLAG_SKIPPED` and `FLAG_INVALID` are mutually exclusive.
- `FLAG_INVALID` SHALL be set only together with `FLAG_AVOID`. A normal entry with `FLAG_INVALID` set and `FLAG_AVOID` clear is malformed and SHALL be rejected with `GUNZ_MALFORMED_BYTECODE`.

A normal entry with `FLAG_INVALID` set SHALL have `stability_width = 0`. Decoders SHALL reject any normal map entry with `FLAG_INVALID` set and `stability_width != 0`, even if `STAB_SATURATED` is clear.

A normal entry with `FLAG_INVALID` set SHALL have `STAB_SATURATED` clear. Decoders SHALL reject any normal map entry where `FLAG_INVALID` and `STAB_SATURATED` are both set.

`FLAG_INVALID` entries follow the same `run_length` rules as other normal entries: `run_length` is the number of consecutive candidates covered, and must be at least `1`.

`FLAG_CENTRAL_ABOVE` and `FLAG_CENTRAL_BELOW` are central‑direction flags.
They SHALL be set only on normal evaluated entries.

At most one of them SHALL be set.

- `FLAG_CENTRAL_ABOVE` set, `FLAG_CENTRAL_BELOW` clear:
  central total time (original, before `PURE_CALL`) is strictly greater than `reference_block_time`.

- `FLAG_CENTRAL_BELOW` set, `FLAG_CENTRAL_ABOVE` clear:
  central total time (original) is strictly less than `reference_block_time`.

- both clear:
  central total time is exactly equal to `reference_block_time`, or the entry does not represent a meaningful central timing sample.

Conformance:

- A conformant decoder SHALL reject a normal entry where both `FLAG_CENTRAL_ABOVE` and `FLAG_CENTRAL_BELOW` are set.

- A `FLAG_SKIPPED` placeholder SHALL have both central‑direction flags clear.

- A `FLAG_INVALID` entry SHALL have both central‑direction flags clear.

No additional consistency requirement is imposed between the central‑direction flags and the stored `block_time_inaccuracy` field, because `block_time_inaccuracy` is an absolute magnitude and the central‑direction flags preserve the original sign of the deviation.

A `FLAG_SKIPPED` placeholder SHALL have:

- `block_time_inaccuracy = 0`
- `jitter = 0`
- `advance_regularity = 0`
- `peak_advance_regularity = 0`
- `stability_width = 0`
- `STAB_SATURATED` clear

Long‑jump entries do not have interval flags. Bytes 8–15 are a single gap and SHALL NOT be inspected for flag bits. Only `freq_delta_start` is validated as the long‑jump type tag.

Before any normal map entry is serialized:

If `FLAG_SKIPPED` or `FLAG_INVALID` is set on that entry, then both `FLAG_CENTRAL_ABOVE` and `FLAG_CENTRAL_BELOW` SHALL be clear.

This rule applies regardless of any earlier local assignment and overrides any prior value written to bits 4‑5 for skipped or invalid entries.

**Long jump entry:**
A long‑jump entry is identified by the sentinel:

```
run_length == 0 && block_time_inaccuracy == 0
```

Under this sentinel, the fields are reinterpreted as follows:

- `freq_delta_start` (offset 0–1) is a **`u16` long‑jump type tag**:
  - `0` — unevaluated placeholder gap.
  - `1` — sparse‑omitted perfect‑resonance interval.
  - `2–65535` — reserved.
- Bytes 8–15 are a little‑endian `s64` gap, giving the total frequency gap in 10⁻⁵ Hz units. The gap SHALL be strictly positive and an exact multiple of `effective_step`.

No individual metric fields within bytes 8–15 are interpreted separately. A decoder shall treat the entry as a gap based solely on the sentinel and the type tag.

Under the long‑jump sentinel, the same two bytes are interpreted as an unsigned `u16` type tag; under all other entries they are a signed `s16` delta.

Decoders SHALL reject a long‑jump entry whose `freq_delta_start` is not `0` or `1` with `GUNZ_MALFORMED_BYTECODE`.

Decoders SHALL reject a long‑jump entry with type `1` if the map header’s `sparse_map` bit is `0` with `GUNZ_MALFORMED_BYTECODE`.

The gap encoded in a long‑jump entry SHALL be strictly positive and an exact multiple of `effective_step`. A decoder that encounters a long‑jump entry with a zero or negative gap shall reject the map with `GUNZ_MALFORMED_BYTECODE`.

The computation of `max_lj_gap` SHALL use the resolved `effective_step` stored in the map header, not the bytecode `SCAN_RES` operand `step_freq`.

```
max_lj_gap = ((2⁶³ − 1) // effective_step) × effective_step
```

The computation of `max_lj_gap` SHALL use at least 64‑bit unsigned arithmetic. 128‑bit arithmetic MAY be used.

Every long‑jump gap SHALL be an exact multiple of `effective_step`, and no single long‑jump gap SHALL exceed `max_lj_gap`. When a required gap exceeds `max_lj_gap`, the generator SHALL emit multiple long‑jump entries, each with a gap of `max_lj_gap` except the final entry, which SHALL carry the remaining multiple of `effective_step`.

**Gap overflow splitting (normative).**

Let `G` be the required total long‑jump gap. `G` SHALL be a positive exact multiple of `effective_step`. The generator SHALL use the following algorithm:

```
while G > max_lj_gap:
    emit long-jump with gap = max_lj_gap
    G = G − max_lj_gap

if G > 0:
    emit long-jump with gap = G
```

The sum of the emitted gaps SHALL equal the original required gap. No zero‑gap final entry is emitted. This rule applies to every long‑jump emission path.

**Decoder current frequency.** After processing a map entry, the decoder maintains a current frequency pointer, initially `base_freq`. The serialized decoder current frequency SHALL be maintained using at least 64-bit unsigned arithmetic, matching the absolute-frequency merge phase in §3.3. For a normal entry, the starting frequency is `current + freq_delta_start`. For a long‑jump entry, `freq_delta_start` is the type tag and SHALL NOT be used in frequency reconstruction; the long‑jump starts at `current`. The long‑jump interval covers candidates from `current` through `current + gap − effective_step` inclusive, as defined in §3.3.



The following rules SHALL be applied identically by all decoders:

- For a normal entry with `run_length = n` and starting frequency `s`, the decoder advances current to:
  ```
  current = s + n × effective_step
  ```
  This is the first grid frequency after the covered run.
- For a long‑jump entry, the decoder first reads and validates `freq_delta_start` as the long‑jump type tag, then advances current by the decoded gap.
- For a `FLAG_SKIPPED` placeholder entry, the decoder advances current by `run_length × effective_step`.

A decoder SHALL reject any normal entry whose computed start frequency is less than the decoder’s current frequency. Such an entry would overlap already‑decoded territory.

Writers SHALL ensure that the `freq_delta_start` of every normal entry is non‑negative. A negative value would cause the entry to overlap already‑decoded territory and is invalid.

**Sparse map emission:**
When `sparse_map` is set in the map header, intervals omitted because all quantitative metrics are zero, the stability width is zero, `FLAG_AVOID` is clear, **both central‑direction flags are clear**, (and the entry is not a long‑jump or skipped zone) have their frequency span (`run_length × effective_step`) accumulated into the next emitted entry's `freq_delta_start`, preserving spatial continuity. The generator maintains a running accumulator of the total gap (in 10⁻⁵ Hz) that has been omitted by sparse consolidation.  The accumulator shall be a **128‑bit signed integer** (`s128`).

In a sparse map, every **evaluated normal entry** with `freq_delta_start > 0` SHALL have `freq_delta_start` an exact multiple of `effective_step` (10⁻⁵ Hz units).

The sparse emission algorithm consumes the **dense candidate interval stream** produced by Phase 2 and by the gap‑insertion rules of §3.3, **before** final run‑length consolidation.

That stream contains:

- unconsolidated evaluated candidate intervals,
- `FLAG_INVALID` normal entries,
- `FLAG_SKIPPED` placeholder intervals,
- long‑jump gap entries.

Sparse omission and accumulator logic SHALL be applied only to ordinary evaluated candidate intervals that qualify for omission under this section. `FLAG_INVALID`, `FLAG_SKIPPED`, and long‑jump entries are processed by their dedicated branches defined below.

The output of sparse emission is then passed through the normal map‑entry consolidation rules of §3.11.

The dense candidate interval stream consumed by sparse emission is the absolute-frequency stream produced by §3.3 after gap insertion.

In this absolute stream:

- ordinary evaluated candidate intervals, `FLAG_SKIPPED` placeholders, and `FLAG_INVALID` normal entries carry `absolute_start` and `absolute_end`;

- long-jump entries carry a type tag (`0` or `1`) and a decoded gap;

- no interval carries a meaningful serialized `freq_delta_start`.

Therefore, for every interval entering sparse emission:

```
  `original_freq_delta_start(interval) = 0`
```

A positive `freq_delta_start` on an evaluated normal entry is produced **only by the sparse emission algorithm**, during final serialization after sparse omission has been applied, and never pre-exists in the dense absolute-frequency stream.

**Normative emission algorithm:**
```
accumulator = 0   // s128, in 10⁻⁵ Hz units
for each candidate interval in order:
      if the interval is omitted (all quantitative metrics zero, stability width zero, FLAG_AVOID clear, both central-direction flags clear, not a long-jump, not skipped):
        accumulator = accumulator + (interval.run_length × effective_step)
    else if the interval is a long‑jump:
        // Flush any accumulated omitted gap before the long‑jump
        while accumulator > max_lj_gap:
            emit long‑jump with type 1, gap = max_lj_gap
            accumulator = accumulator − max_lj_gap
        if accumulator > 0:
            emit long‑jump with type 1, gap = accumulator
            accumulator = 0
        emit entry immediately
    else if the interval is a FLAG_SKIPPED placeholder:
        while accumulator > max_lj_gap:
            emit long‑jump with type 1, gap = max_lj_gap
            accumulator = accumulator − max_lj_gap
        if accumulator > 0:
            emit long‑jump with type 1, gap = accumulator
            accumulator = 0
        emit placeholder with freq_delta_start = 0
        accumulator = 0
    else if the interval is a FLAG_INVALID entry:
        // FLAG_INVALID entries are evaluator-skipped normal entries;
        // they cannot carry sparse-omitted intervals.
        while accumulator > max_lj_gap:
            emit long‑jump with type 1, gap = max_lj_gap
            accumulator = accumulator − max_lj_gap
        if accumulator > 0:
            emit long‑jump with type 1, gap = accumulator
            accumulator = 0
        emit FLAG_INVALID entry with freq_delta_start = 0
        accumulator = 0
    else:
        while accumulator > max_lj_gap:
            emit long‑jump with type 1, gap = max_lj_gap
            accumulator = accumulator − max_lj_gap
        delta = original_freq_delta_start(interval) + accumulator
        if delta > 32767 or delta < -32768:
            emit long‑jump with type 1, gap = accumulator
            accumulator = 0
            delta = original_freq_delta_start(interval)
        interval.freq_delta_start = delta
        emit interval
        accumulator = 0

// After all intervals, reduce accumulator and flush any remaining gap
while accumulator > max_lj_gap:
    emit long‑jump with type 1, gap = max_lj_gap
    accumulator = accumulator − max_lj_gap
if accumulator > 0:
    emit long‑jump with type 1, gap = accumulator
    accumulator = 0
```
The branch `if delta > 32767 or delta < -32768` is required for overflow prevention. Because `original_freq_delta_start(interval)` is `0` and the accumulator is non‑negative, the negative sub‑condition is currently unreachable. It is retained for defensive future compatibility.

All long‑jump entries emitted by the sparse‑map accumulator overflow reduction, including the final flush, SHALL carry type `1` because they represent folded‑away perfect intervals.

`FLAG_INVALID` entries SHALL be emitted with `freq_delta_start = 0` and SHALL act as flush boundaries for the sparse accumulator.

Long‑jump entries that represent unevaluated gaps — `SKIP_ZONE` regions, truncated zone remainders, iteration‑budget excluded zones, or inter‑zone gaps — SHALL carry type `0`.

**Canonical generation rule:** Decoders must accept long‑jump entries. Generators SHALL emit long‑jump entries when:
- the required `freq_delta_start` would overflow the signed 16‑bit range, or
- the gap represents an unevaluated interval whose candidate count exceeds 65535, or
- the sparse accumulator would exceed `max_lj_gap`.

Smaller unevaluated gaps SHALL be represented by `FLAG_SKIPPED` entries, except where §3.3 or §3.11 explicitly requires a type‑0 long‑jump entry for that gap.

The following table is normative:

| Map `sparse_map` | Entry form | Meaning |
|------------------|------------|---------|
| `0` | Evaluated normal entry, `freq_delta_start > 0` | Malformed |
| `0` | `FLAG_SKIPPED` placeholder, `freq_delta_start > 0` | Malformed |
| `0` | `FLAG_INVALID` entry, `freq_delta_start > 0` | Malformed |
| `0` | Long‑jump type `0` | Unevaluated gap |
| `0` | Long‑jump type `1` | Malformed |
| `1` | Evaluated normal entry, `freq_delta_start > 0` | Sparse‑omitted perfect interval precedes this entry |
| `1` | `FLAG_SKIPPED` placeholder, `freq_delta_start > 0` | Malformed |
| `1` | `FLAG_INVALID` entry, `freq_delta_start > 0` | Malformed |
| `1` | Long‑jump type `0` | Unevaluated gap |
| `1` | Long‑jump type `1` | Sparse‑omitted perfect interval |
| `0` or `1` | `FLAG_INVALID` entry, `freq_delta_start = 0` | Normal entry representing evaluator-skipped saturated candidates |


### 4.2.1 Map Header

The map header is exactly **64 bytes**. All integers are little‑endian. Reserved bytes SHALL be zero.

| Offset | Size | Field | Description |
|--------|------|-------|-------------|
| 0–3 | u32 | `base_freq` | Base frequency, in 10⁻⁵ Hz units. The `base_freq` field SHALL be set to the starting frequency of the first map entry after all per‑thread `SparseMapBuilder`s have been merged in ascending order. This equals the minimum `freq_low` among all zones, including those excluded by the iteration budget, which still produce a long‑jump entry at that frequency. If the program contains at least one `ZONE` or `SKIP_ZONE`, even if every such zone is excluded by the iteration pre‑pass, `base_freq` SHALL be the minimum `freq_low` among those zones. If the program contains no `ZONE` or `SKIP_ZONE` instructions at all, `base_freq` SHALL be `0`. An empty map is a map with no entries. Its `base_freq` SHALL be `0`. |
| 4–7 | u32 | `reference_block_time` | Ideal block time, expressed in the base time unit. All time values in this header are expressed in the same base time unit as the rest of the map. Must satisfy the consistency rule with `reference_source` below. |
| 8–11 | u32 | `quantum` | Clock granularity in base time units. The stored value is the merged effective `quantum`. SHALL be ≥ 1. Decoders SHALL reject a map where `quantum == 0`, returning `GUNZ_MALFORMED_BYTECODE`. |
| 12–15 | u32 | `target_ticks` | Ticks to reach. SHALL be ≥ 1. Decoders SHALL reject a map where `target_ticks == 0`, returning `GUNZ_MALFORMED_BYTECODE`. |
| 16–19 | u32 | `mult_num` | Advance multiplier numerator. SHALL be non‑zero. Decoders SHALL reject a map where `mult_num == 0`, returning `GUNZ_MALFORMED_BYTECODE`. |

#### Additional Normative Notes

- **Threshold canonical representation:**
  Writers SHALL always store resolved effective thresholds. Value `0` is not a valid stored threshold and SHALL NOT be emitted. Decoders SHALL reject threshold `0`, returning `GUNZ_MALFORMED_BYTECODE`.

  For `map_type = 0`, detrimental thresholds are inactive. Writers SHALL store `detrimental_jitter_threshold = 255` and `detrimental_advance_regularity_threshold = 65535`, regardless of user input.

  The shorthand value `0` is permitted only in library profiles and plan construction inputs. The evaluator receives resolved non‑zero thresholds.
  The map header always stores resolved non‑zero thresholds. Therefore, the terms “input threshold” and “stored threshold” denote, respectively, the
  pre‑resolution shorthand and the post‑resolution map value.

- **Header self‑sufficiency:**
  The header now stores all evaluator inputs needed to reproduce the core timing model: `quantum`, `target_ticks`, `mult_num`, `mult_den`, `round_mode`, `hold_cycles`, `sep_cycles`, and `window_duration`. Together with `reference_block_time`, any decoder can compute `stability_tolerance_time` directly from the map.

*Note – Maps without scanning:*
A map with `reference_source = 0` has `reference_block_time = 0`. Such maps may be imported. This version defines no built‑in map‑combination operation; any future combining operation must define its own compatibility rules.

 A `reference_source = 0` map is not automatically empty:
 a program containing only `SKIP_ZONE` instructions performs no scanning but can still produce a non-empty map containing `FLAG_SKIPPED` placeholders or corresponding type-0 long-jump entries.

A no-scan map may have:
- `reference_source = 1` and a user-supplied `reference_block_time`, or
- `reference_source = 0` and `reference_block_time = 0`.


*(Informative)* A `map_type = 0` map produced by an older or non‑conforming writer may store other non‑zero threshold values and remains decodable. Such a map is not canonical under this version, but it can still be imported and used as long as all other header and entry rules are satisfied.

If sparse emission was requested but no intervals qualified for omission, the map is dense. Writer SHALL set `map_flags.sparse_map = 0`.

### 4.3 Integrity & Fingerprint

**Canonical map data checksum:**

Mandatory XXH3‑64 over the canonical map data:
The `xxh3_64` field contains the XXH3‑64 checksum computed as follows:

1. Start with a byte buffer containing, in order:
   - the 64‑byte map header,
   - all 16‑byte map entries.
2. Set the 8 bytes of the `xxh3_64` field, offset 48–55, to zero within this buffer.
3. Compute XXH3‑64 with seed 0 over the entire buffer.
4. Store the result in the `xxh3_64` field.

This checksum provides accidental-corruption detection and content identity. It is not a cryptographic integrity mechanism and SHALL NOT be interpreted as tamper-evident or adversarially secure.

A decoder SHALL zero the `xxh3_64` field, recompute the checksum over the same canonical bytes, and compare with the stored value before any header semantic validation or entry processing. A mismatch results in `GUNZ_INVALID_LIBRARY`.

The canonical map data is the raw, unsalted `.gunzmap` file bytes. It consists exactly of the 64‑byte map header, and all 16‑byte map entries. No other bytes are permitted in the file.

Dynamic‑lane fingerprint salting does not alter these bytes and SHALL NOT be applied before checksum computation.

For an empty map, the checksum is computed over the 64‑byte header only; no entry bytes are included.

The fingerprint is computed after the map header has passed all reserved‑field checks.

  **Fingerprint (global identity):**

The XXH3‑128 map fingerprint is computed with seed 0 over the canonical little‑endian serialization, without padding, of the following fields in this exact order:

  ```
    base_freq                         (u32, offsets 0–3)
    reference_block_time              (u32, offsets 4–7)
    quantum                           (u32, offsets 8–11)
    target_ticks                      (u32, offsets 12–15)
    mult_num                          (u32, offsets 16–19)
    mult_den                          (u32, offsets 20–23)
    round_mode                        (u8,  offset 24)
    hold_cycles                       (u8,  offset 25)
    sep_cycles                        (u8,  offset 26)
    time_unit                         (u8,  offset 27)
    jitter_window_radius              (u8,  offset 30)
    map_flags                         (u8,  offset 31)
    map_type                          (u8,  offset 32)
    detrimental_jitter_threshold      (u8,  offset 33)
    detrimental_advance_regularity_threshold (u16, offsets 34–35)
    map_version                       (u16, offsets 36–37)
    reference_source                  (u8,  offset 38)
    long_term_scan                    (u8,  offset 39)
    effective_step                    (u32, offsets 40–43)
    window_duration                   (u64, offsets 56–63)
  ```

 The `xxh3_64` field (bytes 48–55) is excluded from the fingerprint input, as it is the canonical map data checksum, not a parameter that defines the scan.

  Both XXH3‑64 and XXH3‑128 checksums are stored as raw little‑endian byte sequences. When rendered as a hexadecimal string, the integer is displayed in **big‑endian** byte order (most‑significant byte first), matching universal convention.  The raw binary storage remains little‑endian.

Reserved bytes at offsets 28–29 are not included. `evaluated_candidate_count` at offsets 44–47 is not included because it is derived from the entry stream, not an evaluator input parameter. Its integrity is already covered by the canonical map data checksum `xxh3_64`.

For programs executed in the Dynamic Lane, the map fingerprint is salted to preserve provenance.

The salt is derived from the original bytecode:

- Compute the bytecode’s XXH3-128 fingerprint over the complete bytecode stream using seed 0.
- The salt is the lower 64 bits of that fingerprint, taken from the first 8 bytes of the raw little-endian XXH3-128 output, interpreted as a little-endian `u64`.

The fingerprint input buffer is the canonical header field sequence defined above, excluding `xxh3_64`.

For dynamic-lane maps, before computing the XXH3-128 map fingerprint:

1. XOR the salt, interpreted as a little-endian `u64`, with the first 8 bytes of that buffer:

   - bytes 0-3: `base_freq`
   - bytes 4-7: `reference_block_time`

2. Compute XXH3-128 over the modified buffer.

The raw `.gunzmap` header bytes SHALL remain unchanged during fingerprint computation. The map fingerprint SHALL NOT be computed as a hash of the raw `.gunzmap` file header.

The canonical map data checksum `xxh3_64` remains self-contained and is not affected by dynamic-lane fingerprint salting.

Static-lane map fingerprints are unsalted and are computed directly over the canonical header field list defined above. Dynamic-lane map fingerprints are salted as described above to preserve provenance.

The XXH3-128 map fingerprint is used for provenance identity and global map identity. It SHALL be recorded in `.gunzmeta`.

For content-only identity and content-based deduplication, implementations SHALL use the self-contained `xxh3_64` checksum only. Map-content deduplication SHALL NOT require bytecode identity.

On a plan-cache hit, the runtime shall compare the canonical bytecode; on mismatch, invalidate. That bytecode comparison applies to plan-cache entries only and does not apply to map-content deduplication.

After any mutation, the canonical map data `xxh3_64` checksum and the appropriate XXH3‑128 fingerprint SHALL both be recomputed.

### 4.4 Dense‑Scan Semantics

`SCAN_RES` step size `step_freq`; default 1 (10⁻⁵ Hz).  A value of 0 is equivalent to 1.  The effective step size is recorded in the map header as described in §4.2.1.  Step sizes up to 2³²−1 are supported.
**Normative cap:** The effective step size shall not exceed 2³²−1.  If a larger step is requested, plan construction shall fail with `GUNZ_INVALID_LIBRARY`.
**Minimal‑Profile restriction:** A Minimal‑Profile implementation shall not use a step size that exceeds 65535.  If the effective step size would otherwise exceed 65535, plan construction shall fail with `GUNZ_INVALID_LIBRARY`.

Counted loop with the plan’s `max_scan_iterations` (minimum `2^24`). Candidate positions advance by `effective_step`. When clamped, the skipped remainder after the first `max_scan_iterations` candidates is emitted as one or more type‑0 long‑jump entries, split according to §4.2 when necessary.

### 4.5 Normative Integer Arithmetic

#### 4.5.1 Half‑to‑Even Integer Division

For non‑negative integers `a` (dividend) and `b` (divisor, `b > 0`), the result `q = a / b` rounded to the nearest integer, with ties broken to the nearest even integer, is computed as:

```
q = floor(a / b)
r = a - q * b
if 2*r == b:          // exact tie
    if q is odd: q = q + 1
else if 2*r > b:      // closer to q+1
    q = q + 1
```

All standard deviation and derived‑metric calculations that use this division operate exclusively on non‑negative quantities. A normative division SHALL use half‑to‑even rounding unless the clause defining that division explicitly specifies another rounding rule. In case of conflict, the specific clause takes precedence over this general rule. The rounding modes `ceil` and `truncate` provided in the header are defined by standard integer arithmetic (`ceil` rounds toward positive infinity, `truncate` rounds toward zero) and are not subject to the tie‑breaking rule above.

*(Informative)* The specification assumes availability of a 128‑bit unsigned integer type with native multiplication, division, and remainder.  On platforms without native `unsigned __int128`, an implementation may emulate these operations using a pair of 64‑bit integers, provided that the emulated division and remainder produce results bit‑identical to those of a native 128‑bit operation for all inputs within the normative ranges.

**Implementation warning – anti‑pattern:**
Implementations **MUST NOT** substitute the common C idiom `(val + 50) / 100` for rounding division by 100, as that implements round‑half‑up and will produce non‑conforming results on exact `.50` ties. The division must strictly follow the half‑to‑even algorithm above. The following C snippet shows a correct implementation:

```c
// Correct half‑to‑even division by 100
u128 prod = (u128)val;
u128 q    = prod / 100;
u128 r    = prod % 100;
if (r > 50 || (r == 50 && (q & 1) != 0)) {
    q += 1;
}
```

**Rounding mode precedence (normative).**

| Computation | Rounding rule |
|-------------|----------------|
| `T = 10^(time_unit + 5) / freq_candidate` | Fixed floor |
| `d_lo_cont = T / quantum` | Fixed floor |
| `adv_lo_cont = (d_lo_cont × mult_num) / mult_den` | Fixed floor |
| `adv_hi_cont = (d_hi_cont × mult_num) / mult_den` | Fixed floor |
| `N₀ = ceil(target_ticks / max(adv_lo_cont, adv_hi_cont, 1))` | Fixed ceil |
| `long_term_max_eval = ceil(window_duration / T_min)` | Fixed ceil |
| `R = round(N × T / quantum) × quantum` | Header `round_mode` |
| `Q = R / quantum` | Exact; result integer by construction |
| `max_lj_gap = ((2⁶³ − 1) // effective_step) × effective_step` | Fixed floor |
| Candidate / gap divisions where both operands are exact multiples of `effective_step` | Exact integer division; no rounding |
| `advance_regularity_btu` | Fixed half‑to‑even, independent of `round_mode` |
| Variance numerator division `V / n²` | Fixed half‑to‑even |
| `total_time_lt` mean division | Fixed half‑to‑even |
| Standard deviation `isqrt_rounded(var)` | Canonical integer square root rounding |
| Stability width `span / 10` | Fixed truncation toward zero |

#### 4.5.2 Integer Square Root with Rounding

**`isqrt_rounded(x)`** returns the integer `r` that minimises the distance `|r² − x|`.  For integer inputs, no ties can occur; the result is the unique integer closest to the true square root.  The half‑to‑even tie‑break rule is not applicable and may be omitted. This function is the canonical integer square root used in all normative computations.

#### 4.5.3 Integer Standard Deviation (Normative Algorithm)

All standard deviation values in the map are computed using the following deterministic integer algorithm. The algorithm is exact when using the mandated accumulator widths; no alternative formula is permitted except the algebraically identical two‑value closed‑form for advance regularity.

Let the data values be `x₀, …, xₙ₋₁` (all non‑negative 128‑bit integers).

1. Compute the sum using a **128‑bit unsigned** accumulator:
   `S = Σ xᵢ` (exact).

2. Compute the sum of squares using a **256‑bit unsigned** accumulator:
   `S2 = Σ (xᵢ)²` (exact, using 128‑bit multiplication for each term, then extended to 256‑bit).

3. Compute the variance numerator using a **256‑bit unsigned** accumulator:
   `V = n · S2 − S²` (exact; both `S²` and `n·S2` are 256‑bit).

4. Compute the integer variance using the half-to-even division defined in §4.5.1:
   `var = round_half_even(V / n²)`
 
    This yields the population variance σ².

5. Compute the integer standard deviation using the canonical integer square root, per §4.5.2:
   `σ = isqrt_rounded(var)`
 
   The result `σ` is the standard deviation in the same unit as the input values.

**Accumulator width relaxation (informative for implementers):**
The algorithm as defined uses 128‑bit and 256‑bit intermediates to guarantee exactness for all possible inputs up to the normative maximums. An implementation **may** use narrower intermediates (e.g., 128‑bit for the variance numerator) **if and only if** it can mathematically prove that the resulting standard deviation is bit‑identical to the output of the algorithm above for all inputs within the normative bounds. The burden of proof rests with the implementer; a conformant test suite will expect bit‑identical results.

*(Informative)* The normative evaluator bounds on `MAX_N`, `window_duration`, and `jitter_window_radius` ensure that the number of samples and each sample value keep the 128‑bit sum `S` within range. This algorithm is not intended as a general‑purpose unbounded standard deviation function.

**Fixed‑point scaling for advance regularity:**
Advance regularity samples are provided in ticks × 100 (i.e., the actual tick values multiplied by 100). The standard deviation output is therefore also in ticks × 100.
For detrimental threshold comparison, the evaluator SHALL convert the full‑precision average advance regularity to base time units using the formula for `advance_regularity_btu` defined in §3.11. That conversion multiplies by `mult_den × quantum` and divides by `mult_num × 100`, using half‑to‑even rounding.
This derived value is used only for the detrimental advance‑regularity threshold.

**Permitted optimisation for two‑valued multisets (advance regularity):**
For the special case where the multiset contains only two distinct values `a` and `b`, with multiplicities `n_a` and `n_b` (and `n = n_a + n_b`), implementations may compute the variance directly as `var = n_a·n_b·(a − b)² / n²` using 256‑bit integer arithmetic, since this formula is algebraically identical to the general sum‑of‑squares method and yields the same rounded result. No other alternative variance algorithm is permitted. **The division by n² in the closed‑form variance computation must use the half‑to‑even rounding defined in §4.5.1; truncating integer division will produce incorrect results.**

### 4.6 Map Companion Metadata File (`.gunzmeta`)

Every time a scan map is produced by Phase 1/Phase 2 of a plan, a Full-profile implementation SHALL also write a companion metadata file with the same base name and extension `.gunzmeta`.

For the purpose of this section, a map produced by a plan that contains no included `ZONE` instructions — for example a map consisting only of `FLAG_SKIPPED` placeholders, type‑0 long‑jump entries, or an empty map — is still considered a scan map, because it is produced by that plan's execution, not derived from existing maps.

Derived maps are maps produced by companion or future post‑processing operations that consume existing maps.

No built‑in operation produces derived maps. The derived‑map metadata requirements are reserved for future companion specifications or external post‑processing tools.

For derived maps:

- `.gunzmeta` is optional.

- If present, it SHALL contain at least:
  - `gunz_version`
  - `map_fingerprint`
  - `creation_timestamp`
  - `derived_from`, an array of the input map fingerprints
  - `operation`, a string identifying the derivation operation
  - `callback_sandboxed = false`

The following scan‑map fields SHALL be omitted for derived maps:

- `plan_parameters`
- `scan_zones`
- `bytecode_fingerprint`
- `metric_extremes`
- `stability_tolerance_time`

Minimal‑profile implementations (see §1.2) are exempt from this requirement.

**Purpose** – captures the exact evaluator configuration, scan parameters, environmental context, and AI‑facing feedback signals. Not required for map import; enables reproduction, audit, and autonomous decision‑making.

The fingerprint is computed over the entire file bytes, from the first byte of the `magic` field through the end of the file, using `XXH3‑128` with seed 0. For `.gunzstatz`, this includes the compressed delta stream. For zero‑candidate statistics files, the fingerprint is computed over the file bytes consisting only of magic and candidate count. |
| `scan_cost` | object | Optional ; record of scan resource usage. Some fields are deterministic and reproducible; others are explicitly non‑deterministic and informational only. Containing: <br> – `cpu_time_ms` (u64, optional) – non‑deterministic. SHALL NOT be included in canonical attestation metadata. <br> – `evaluator_iterations` (integer; non‑negative) <br> – `candidates_evaluated` (integer; non‑negative) <br> – `windows_chained` (integer; non‑negative). Implementation‑defined telemetry for Phoenix‑style window chaining. Its exact meaning and computation are not prescribed by this specification. It SHALL NOT be used for reproducibility or fingerprinting, and SHALL be omitted from canonical attestation metadata. <br> – `fuel_consumed` (u64; fuel units, reflecting the actual HALT decrement) <br> – `elapsed_time_ms` (u64, optional) – elapsed real time of the scan from start to finish, as measured by a monotonic system clock.  This value is **not** deterministic; identical scans may produce different measurements. <br> – `memory_high_water_mark_bytes` (u64, optional) – peak arena memory used during the scan. <br> The fields `cpu_time_ms`, `elapsed_time_ms`, and `memory_high_water_mark_bytes` are non‑deterministic and informational only. They SHALL NOT be used for reproducibility or fingerprinting, and SHALL be omitted from canonical attestation metadata. |
| `resonance_quality` | object | Optional ; deterministic summary of scan findings.  The following optional fields **MAY** be present: <br> – `max_per_block_advance_regularity` (integer) – The largest per‑block advance regularity observed across all blocks and candidates in the scan, expressed in ticks × 100.  Computed as described in §3.11.  Zero or absent if not computed.  Without drift, this value equals the per‑jitter‑point pooled advance regularity. |
| `system_info` | object | Optional ; host machine details. Informational and non-deterministic. SHALL NOT be included in canonical attestation metadata. |
| `stability_tolerance_time` | integer | Optional ; Derived plateau tolerance used for `stability_width`. Informational only. Must match `max(quantum, round_half_even(reference_block_time / 1_000_000))`. See Derived stability tolerance field. |


**Derived stability tolerance field**
If `stability_tolerance_time` is present, it SHALL be computed as:

    stability_tolerance_time =
        max(quantum, round_half_even(reference_block_time / 1_000_000))

where:
- `quantum` is the value from the map header,
- `reference_block_time` is the value from the map header,
- the division `reference_block_time / 1_000_000` denotes the exact rational quotient,
- `round_half_even` is the half‑to‑even integer division defined in §4.5.1.

The result is expressed in base time units.

This field is informational only. The authoritative inputs remain `quantum` and `reference_block_time`, which are stored in the 64‑byte map header.

If `stability_tolerance_time` is present and does not match the formula above, the `.gunzmeta` file is malformed and SHALL be rejected.

- For **scan maps**, the keys listed in the table above are mandatory, except as explicitly stated elsewhere.
- For **derived maps**, `.gunzmeta` is optional.

If no `PURE_CALL` callback was invoked during a scan:
- `callback_sandboxed` SHALL be `true` for a canonical map.
- `sandbox_type` SHALL be the string `"none"`.
- `attestation_signature` SHALL NOT be required.
- `runtime_id` SHALL NOT be required.

The condition that all callbacks were sandboxed is vacuously true.

*(Companion extension)* When the optional GUNZ‑DRIFT companion is active, the `.gunzmeta` file MAY also contain the fields defined in GUNZ‑DRIFT §5.3:

- `drift_velocity_max`
- `drift_confidence_min`
- `drift_block_extremes`
- `drift_fragile_candidates`
- `drift_fragility_threshold`

These fields are optional and do not affect the `.gunzmap` checksum, the map fingerprint, or `stats_fingerprint`.
The canonical identity of a map is its XXH3‑128 map fingerprint. The `.gunzmeta` attestation signature covers the metadata instance, including `creation_timestamp`, and is therefore not expected to be identical across repeated identical scans. Map fingerprint reproducibility is unaffected.

| `central_exact_count` | integer | count | Number of evaluated candidates with both central‑direction flags clear. |


All three core metrics are lower‑is‑better:

- `_min` records the best observed stored value.
- `_max` records the worst observed stored value.

The `*_min` and `*_max` values are taken from the saturated map‑entry representations:

- `block_time_inaccuracy` saturates at `UINT32_MAX`.
- `jitter` saturates at `255`.
- `advance_regularity` saturates at `65535`.

Full‑precision values remain available in `.gunzstats` / `.gunzstatz`.

`central_above_count`, `central_below_count`, and `central_exact_count` SHALL either all be present or all be omitted. If any one is present, the invariant below applies.

Invariant:

    central_above_count + central_below_count + central_exact_count
        == evaluated_candidate_count

where `evaluated_candidate_count` is the map header field at offsets 44‑47.

If the invariant does not hold, the `.gunzmeta` file is malformed and SHALL be rejected.  
This invariant is normative for writers. A decoder cannot verify it from the `.gunzmap` alone; verification requires the corresponding `.gunzstats` or equivalent Phase 1 evaluation data.

Scope:

`metric_extremes` SHALL be computed over all Phase 1 successfully evaluated candidates, before `PURE_CALL` post‑processing, before sparse omission, and before final map‑entry consolidation.

The following are excluded:

- `FLAG_SKIPPED` entries,
- `FLAG_INVALID` entries,
-  long‑jump entries.

Sparse‑omitted perfect intervals are evaluated candidates and SHALL be included.

If no candidate was successfully evaluated, `metric_extremes` SHALL be omitted.

For derived maps, `metric_extremes` SHALL be omitted.

`scan_zones[].max_jitter` and `scan_zones[].max_advance_regularity` are per‑zone summaries. `metric_extremes` is a global summary. Both are optional and neither is authoritative over the `.gunzmap` header or `.gunzstats`.

For `map_type = 0`, `plan_parameters.detrimental_jitter_threshold` SHALL be recorded as `255`, and `plan_parameters.detrimental_advance_regularity_threshold` SHALL be recorded as `65535`.

These are the canonical values actually written to the map header; any user-supplied detrimental thresholds are ignored for evaluator behaviour and header storage when `map_type = 0`.

 When `long_term_scan == 0`, `window_duration` SHALL be `0` in both the map header and `plan_parameters`. When `long_term_scan == 1`, `window_duration` SHALL match the plan’s window duration, including the permitted degenerate value `0`.

*Per‑candidate values are available in the companion `.gunzstats` file. Summaries may be placed in `scan_zones` or `resonance_quality`.*

For long-term scans, `plan_parameters.max_eval_iterations` is not authoritative. The authoritative value is per-zone and stored in the corresponding `scan_zones` entry. `plan_parameters.window_duration` SHALL be present so that per-zone values can be derived and verified.

### 4.7 Environment Snapshot Format (Normative, Optional)

An Environment Snapshot shall be encoded as a **CBOR** (RFC 8949) map with the following keys, sorted according to the Core Deterministic Encoding Requirements of RFC 8949 §4.2.1.

 RFC 8949 §4.2.1 states:
 
 *“Map keys MUST be sorted in the bytewise lexicographic order of their deterministic encodings. In particular, if two keys have different lengths, the shorter one sorts earlier; if two keys have the same length, the one with the lower value in bytewise lexicographic order sorts earlier.”*
 
 For the snapshot’s top-level text keys, the resulting normative CBOR order is:

 1. `stats` (encoded length prefix `0x65`)
 2. `metadata` (encoded length prefix `0x68`)
 3. `signature` (encoded length prefix `0x69`)
 4. `timestamp` (encoded length prefix `0x69`)
 5. `capabilities` (encoded length prefix `0x6c`)
 6. `snapshot_version` (encoded length prefix `0x70`)

 Within the `metadata` and `stats` submaps, keys shall also be ordered by the same deterministic rules.

**Verification model (normative).** A snapshot that is not canonical CBOR as defined above SHALL be rejected with `GUNZ_INVALID_LIBRARY` before signature verification or payload‑hash computation. The runtime SHALL NOT silently canonicalise a non‑canonical snapshot before verification.

Legacy snapshots that are not canonical CBOR, if supported, SHALL be converted to canonical CBOR and re-signed with a currently valid runtime key before being presented for verification. Such conversion SHALL occur outside the verification path and SHALL produce a new snapshot payload.

Legacy snapshots that are already canonical CBOR and signed with a still-recognised historical key SHALL be verified normally. The runtime MAY require such snapshots to be re-signed with the current key before they are used in new plans.

The snapshot's identity for plan construction is its payload hash: **`XXH3‑128`** of the CBOR bytes excluding `"signature"`, represented as a 32‑character hexadecimal string. Two snapshots with different payload hashes are distinct. The runtime shall validate the signature before binding the snapshot into a plan; an invalid signature shall cause plan construction to fail with `GUNZ_INVALID_LIBRARY`. *Support for environment snapshots is optional for base conformance.*

*(Informative)* GUNZ 5.0.0 defines `timestamp` in milliseconds. Earlier revisions may have used seconds. Snapshot consumers should treat timestamps from pre‑5.0.0 snapshots accordingly.

**Key management:** The runtime must expose a public key via `GUNZ_GetSnapshotVerificationKey`. The public key is returned as a raw 32‑byte Ed25519 public key (type `uint8_t[32]`). The private signing key must be rotated at least annually.

To preserve long‑term reproducibility, the runtime **SHALL** retain all previously active public keys for the lifetime of any plan or snapshot that references them.  When validating a snapshot’s signature, the runtime **SHALL** test it against every known valid key (current and historical).  If a key is retired, the runtime **MAY** require snapshots signed with that key to be re‑signed with the current key before they can be used in new plans.

### 4.8 Raw Statistics Companion File (`.gunzstats`)
 
 The runtime may emit a raw statistics file for any scan.  When `long_term_scan` is active, emitting the file is strongly recommended.  When drift computation is enabled (as defined by the GUNZ‑DRIFT companion extension), the file **shall** be emitted, regardless of scan mode.
 
 All `.gunzstats` files use a fixed **96‑byte** record format.  The file begins with a 4‑byte magic number `0x475A4C04` (little‑endian), followed by a 4‑byte little‑endian `candidate_count` giving the total number of records in the file.  This is the **only** valid magic number for raw statistics files.  A conformant decoder shall reject any `.gunzstats` file whose magic is not `0x475A4C04` with `GUNZ_MALFORMED_BYTECODE`.
 
**File structure:**
 
| Offset | Size | Field |
|--------|------|-------|
| 0 | u32 | `magic` `0x475A4C04` |
| 4 | u32 | `candidate_count` |
| 8 | … | sequence of 96‑byte records |

If `candidate_count == 0`, the file contains only `magic` and `candidate_count`. No 96‑byte records follow. The file size SHALL be exactly 8 bytes.
If `candidate_count == 0`, a conformant decoder SHALL verify that the file size is exactly 8 bytes. If the file contains any additional bytes, the decoder SHALL reject the file with `GUNZ_MALFORMED_BYTECODE`.

For any `.gunzstats` file, a conformant decoder SHALL reject the file if its size is not exactly `8 + candidate_count × 96` bytes, regardless of whether `candidate_count` is zero.

### Candidate scope and alignment pass (normative)

`.gunzstats` contains one record for every candidate successfully evaluated by Phase 1, regardless of whether that candidate was later omitted from the map by
sparse emission.

Evaluator-skipped candidates carrying `FLAG_INVALID` are not successfully evaluated and therefore have no `.gunzstats` record.
The following map elements do **not** represent evaluated candidates and have no `.gunzstats` record:

- `FLAG_SKIPPED` entries,
- type‑0 long‑jump entries,
- normal entries with `FLAG_INVALID` set.

Type‑1 long‑jump entries and positive `freq_delta_start` on evaluated normal entries in a sparse map represent sparse‑omitted perfect intervals that **were evaluated**. Those omitted intervals therefore **do** have `.gunzstats` records.

**Precondition.** The map SHALL have been fully decoded and validated according to §4.2 and §6 before this alignment pass is performed. All header reserved bits, entry flag combinations, long‑jump type and gap divisibility rules, and normal‑entry delta rules SHALL have already been enforced.

**Map dependency precondition.** `.gunzstats` alignment SHALL be performed only in conjunction with the corresponding `.gunzmap` file. The `effective_step` used throughout this section SHALL be resolved from that map’s header, as specified in §4.2.1.

Alignment SHALL NOT be attempted from a `.gunzstats` file alone, because the file does not contain `base_freq`, `effective_step`, or the map entry geometry required for frequency reconstruction.

**Exact‑multiple precondition.** Both long‑jump `gap` and positive `freq_delta_start` SHALL already have been validated as exact multiples of `effective_step` by the map decoder. The divisions below are exact integer divisions, not validation mechanisms.

**Alignment pass.**

Alignment SHALL be performed as a single forward pass over the decoded map entry stream, using the same resolved `effective_step` as map decoding.

Let `current` be the decoder frequency pointer, initially `base_freq`.

For each map entry, in order:

1. **`FLAG_SKIPPED` entry:**
   – Emit `0` records.
   – Advance `current` by `run_length × effective_step`.

2. **Normal entry with `FLAG_INVALID` set:**
   – These entries are skipped only for record pairing; they still advance the decoder current for map frequency decoding.
   – Emit `0` records.
   – Advance `current` by `run_length × effective_step`.

3. **Type‑0 long‑jump entry:**
   – Emit `0` records.
   – Advance `current` by the gap.

4. **Type‑1 long‑jump entry:**
   – Emit `gap / effective_step` records.
   – These records correspond to candidates:
     ```
     current, current + effective_step, …, current + gap − effective_step
     ```
   – Advance `current` by `gap`.

5. **Evaluated normal entry:**
   – Let `start = current + freq_delta_start`.
   – If `freq_delta_start > 0`:
     - If `map_flags.sparse_map != 1`, reject the map with `GUNZ_MALFORMED_BYTECODE`.
     - Emit `freq_delta_start / effective_step` omitted evaluated records.
     - These records correspond to candidates:
       ```
       current, current + effective_step, …, start − effective_step
       ```
   – Emit `run_length` records for the entry itself.
   – Advance `current` to `start + run_length × effective_step`.

6. **Any other entry:**
   – Reject the map with `GUNZ_MALFORMED_BYTECODE`.

After the map entry stream is exhausted:

```
total_emitted_records SHALL equal candidate_count
```

If not, the `.gunzstats` file is inconsistent with the map and SHALL be rejected with `GUNZ_MALFORMED_BYTECODE`.

 **Frequency reconstruction note.** Normal entries with `FLAG_INVALID` set SHALL still advance the decoder’s current frequency by `run_length × effective_step` during `.gunzstats` alignment. They are skipped only for record pairing, not for map frequency decoding.

**Record format** – packed 96‑byte records, one per candidate, in map order:

| Offset | Size | Field | Description |
|--------|------|-------|-------------|
| 0  | u64 | `block_count` | Number of temporal blocks evaluated. |
| 8  | u128 | `sum_block_time` | Sum of **raw** block times (base time units, before adding hold/sep contribution). |
| 24 | u128 | `sum_block_time_sq` | Sum of squares of raw block times. |
| 40 | u16 | `count_adv_lo` | Number of short advances (total across all blocks and jitter points).  **Saturated to 65535** if the true count exceeds the representable range. |
| 42 | u16 | `count_adv_hi` | Number of long advances.  Saturated to 65535 if needed. |
| 44 | u16 | `a` | Per‑cycle short advance (`100 × adv_lo_cont`) at the original candidate frequency (jitter offset Δ = 0).  **Saturated to 65535 if the product exceeds the u16 range.** |
| 46 | u16 | `b` | Per‑cycle long advance (`100 × adv_hi_cont`) at the original candidate frequency.  Saturated to 65535 if needed. |
| 48 | s16 | `drift` | Per‑candidate drift. SHALL be zero when drift computation is disabled. When GUNZ‑DRIFT is active, SHALL be the signed half‑to‑even mean of the per‑jitter‑point drift values defined by GUNZ‑DRIFT §4. |
| 50 | s16 | `drift_max` | Maximum per-jitter-point drift after the temporal averaging defined by GUNZ‑DRIFT §4. Zero when drift is disabled. |
| 52 | s16 | `drift_min` | Minimum per-jitter-point drift after the temporal averaging defined by GUNZ‑DRIFT §4. Zero when drift is disabled. |
| 54 | u16 | `valid_jitter_points` | Number of valid jitter offsets that contributed to the candidate’s aggregates. This SHALL be at least `1` for every `.gunzstats` record. Skipped saturated candidates are not represented in `.gunzstats` and therefore have no stored `valid_jitter_points` value. |
| 56 | u64 | `advance_regularity_full` | Per‑candidate full‑precision average of per‑jitter‑point advance regularity (ticks × 100), **before** saturation to 65535. <br> If the implementation does not record this value, it SHALL write `UINT64_MAX`. <br> If the implementation records the value, it SHALL write the true value, saturated to `UINT64_MAX − 1`. The value `0` is a valid recorded value and SHALL be written as `0`. <br> A stored value of `UINT64_MAX − 1` may represent either the exact value or a saturated true value. Consumers should not assume exactness unless the scan metadata indicates otherwise. |
| 64 | u128 | `sum_total_block_time` | Sum of **total** block times (raw + hold/sep contribution) across all blocks and jitter points. |
| 80 | u128 | `sum_total_block_time_sq` | Sum of squares of total block times. |

`a` and `b` are diagnostic reference values. They are always the continuous advances derived from `adv_lo_cont` and `adv_hi_cont`. They are not affected by a `DELTA` override.

`count_adv_lo` and `count_adv_hi` are diagnostic and may saturate to `65535`. The authoritative full-precision per-candidate advance regularity value is `advance_regularity_full`. These saturated counts are not sufficient to recompute the advance regularity variance.

In a non‑long‑term scan, `block_count` SHALL equal `valid_jitter_points`: exactly one temporal block is evaluated per valid jitter point. This remains true when GUNZ‑DRIFT is active.

In a long‑term scan, `block_count` is the total number of temporal blocks evaluated across all valid jitter points and may be greater than `valid_jitter_points`.

The same rule applies to the 96‑byte records in both `.gunzstats` and `.gunzstatz`; the compressed format changes only encoding, not field semantics.

When drift is not enabled, the `drift`, `drift_max`, and `drift_min` fields in every `.gunzstats` record SHALL be written as zero.
When drift is enabled, these fields SHALL be computed as defined by the GUNZ‑DRIFT companion specification. Per‑block and per‑jitter‑point drift values remain full precision; only the final per‑candidate `drift`,`drift_max`, and `drift_min` fields are saturated to the signed 16‑bit range `[−32768, 32767]` immediately before storage.

Raw per‑block drift extremes are not stored in `.gunzstats`. When the GUNZ‑DRIFT companion is active and long‑term scan is active, they MAY be stored in `.gunzmeta` as the optional `drift_block_extremes` object defined by GUNZ‑DRIFT §5.3.

**Saturation of cumulative statistics accumulators.**
The four accumulated fields `sum_block_time`, `sum_block_time_sq`, `sum_total_block_time`, and `sum_total_block_time_sq` are stored as unsigned 128‑bit integers.
Before storage, each field SHALL be saturated to `2¹²⁸−1` if its exact value would exceed that bound.
No wrapping, modular reduction, trapping, or implementation‑defined overflow behaviour is permitted for these stored fields.
This saturation applies to both `.gunzstats` and `.gunzstatz` records.

All time values are in the base time unit.  The total number of records is exactly `candidate_count`.  The file size in bytes is `8 + candidate_count × 96`.

### 4.9 Compressed Statistics File (`.gunzstatz`)
 
 Optional compressed version of `.gunzstats` using delta encoding with run‑length and LEB128.  The file uses the same 96‑byte record structure as the uncompressed file, but a **distinct magic number** `0x475A4C05` to allow unambiguous identification of the compressed format.

**File structure:**
 
| Offset | Size | Field |
|--------|------|-------|
| 0  | u32 | `magic` `0x475A4C05` |
| 4  | u32 | `candidate_count` |
| 8  | u32 | `anchor_freq_raw` — Present only when `candidate_count > 0`. Writers SHALL set this field to `0`. Decoders SHALL read and ignore it. Reserved for future use. |
| 12 | 96 bytes | `anchor_record` — Present only when `candidate_count > 0`. Contains the first candidate’s statistics, all 96 bytes. |
| 108 | … | compressed delta stream — Present only when `candidate_count > 0`. |
 
When `candidate_count == 0`, `anchor_freq_raw`, `anchor_record`, and the compressed delta stream are absent. The file consists only of `magic` and `candidate_count` and has exactly 8 bytes.
If `candidate_count == 0`, a conformant decoder SHALL verify that the file size is exactly 8 bytes. If the file contains any additional bytes, the decoder SHALL reject the file with `GUNZ_MALFORMED_BYTECODE`.

For any `.gunzstatz` file, a conformant decoder SHALL reject the file if it ends prematurely or contains trailing bytes after the expected number of candidate records has been decoded.

**Anchor record fields (96 bytes, in order):**
 
The anchor record contains the same fields as the uncompressed record, in the order listed in §4.8 (offsets 0–95).

**Compression algorithm:**
 
For each subsequent candidate (after the anchor), compute signed deltas of the **fourteen** active fields.  For each delta‑encoded field of bit width `w`, let `current` and `previous` be the raw `w`‑bit values of that field. The unsigned modular difference is:

`delta_u = (current − previous) mod 2^w`

The signed delta to encode is the two’s‑complement signed interpretation of `delta_u`, encoded with signed LEB128.

On decoding, the signed delta is read as signed LEB128, converted back to an unsigned `w`‑bit value using modulo `2^w`, and then added to the previous field value modulo `2^w`. The resulting `w`‑bit value is stored back into the field.

This rule applies identically to unsigned and signed fields.

A **two‑byte little‑endian bitmask** (u16) defines which fields have non‑zero deltas:
 
| Bit | Field |
|-----|-------|
| 0 | `block_count` |
| 1 | `sum_block_time` |
| 2 | `sum_block_time_sq` |
| 3 | `count_adv_lo` |
| 4 | `count_adv_hi` |
| 5 | `a` |
| 6 | `b` |
| 7 | `drift` |
| 8 | `drift_max` |
| 9 | `drift_min` |
| 10 | `valid_jitter_points` |
| 11 | `advance_regularity_full` |
| 12 | `sum_total_block_time` |
| 13 | `sum_total_block_time_sq` |
| 14‑15 | (reserved, must be 0) |
 
– If the bitmask is zero (all deltas zero), emit the two‑byte zero mask followed by a run length `R` encoded as **unsigned LEB128**. `R` is the number of consecutive candidates, beginning at the current candidate index, that are identical to the previously emitted record. `R` SHALL be at least `1`.
– Otherwise, emit the non‑zero two‑byte bitmask and, for each set bit (0‑13), emit the signed delta for that field encoded as **signed LEB128**.
 
**Decoding algorithm:**
 
1. Read the magic.  If not `0x475A4C05`, reject with `GUNZ_MALFORMED_BYTECODE`.
2. Read `candidate_count`.
   If `candidate_count == 0`, the decoder SHALL stop after reading `magic` and `candidate_count`. It SHALL NOT read `anchor_freq_raw`, an anchor record, or any compressed delta stream.
3. If `candidate_count > 0`, read `anchor_freq_raw` and the 96‑byte `anchor_record`.  Store this as the previous record.
4. For each subsequent candidate (2 to `candidate_count`):
   - Read a **u16** `mask` (2 bytes, little‑endian).
   - If `mask == 0x0000`: read an unsigned LEB128 run length `R`.
     `R` is the number of consecutive candidates beginning at the current candidate index that are identical to the previously emitted record. `R` SHALL be at least `1`.
     The decoder SHALL output the previous record exactly `R` times.
     After emitting the run, the decoder SHALL advance its candidate index by `R`.
     A zero‑mask record with `R = 0` is malformed; decoders SHALL reject it with `GUNZ_MALFORMED_BYTECODE`.
     A zero‑mask record whose `R` exceeds the number of remaining candidates (`candidate_count − i + 1`) is malformed; decoders SHALL reject it with `GUNZ_MALFORMED_BYTECODE`.
   - Otherwise: copy the previous record, and for each bit `b` set in `mask` (0‑13), read a signed LEB128 delta. For each delta, convert it to an unsigned `w`‑bit value using modulo `2^w`, add it to the corresponding field in the copied record modulo `2^w`, and store the result. Store the updated record as the new previous record.  Bits 14‑15 shall be zero; a non‑zero value causes the decoder to reject the file with `GUNZ_MALFORMED_BYTECODE`.

For a delta-encoded field of bit width `w`, the decoded signed LEB128 value SHALL be within the range:

```
  [-2^(w-1), 2^(w-1)-1]
```

If the decoded signed value is outside this range, the decoder SHALL reject the file with `GUNZ_MALFORMED_BYTECODE`.

This check is in addition to the minimal-byte-length validation.

Normative pseudocode:

```
i = 2
while i <= candidate_count:
    read mask
    if mask == 0:
        R = read_unsigned_leb128()
        require R >= 1
        require R <= candidate_count - i + 1
        emit previous_record exactly R times
        i = i + R
    else:
        decode current record from mask and deltas
        emit updated_record
        previous_record = updated_record
        i = i + 1
```
### Post‑decompression alignment (normative)

The compressed delta stream is a representation of the same **96‑byte record sequence** defined in §4.8. After a conformant decoder has fully decoded the compressed delta stream, the resulting record sequence SHALL be treated as if it had been read from an uncompressed `.gunzstats` file.

Before any map pairing, candidate‑count validation, or frequency reconstruction is attempted, the alignment pass specified in §4.8 **“Candidate scope and alignment pass (normative)”** SHALL be performed against the corresponding `.gunzmap`.

The decoded record sequence from `.gunzstatz` SHALL then be paired and validated using the result of that pass.

This includes, without exception:

- resolution of `effective_step` from the corresponding `.gunzmap` header,
- the positive‑`freq_delta_start` dense‑map rejection rule,
- the exact‑multiple preconditions,
- every per‑entry record‑emission rule,
- the final equality check:

```
total_emitted_records SHALL equal candidate_count
```

If `candidate_count == 0`, the decoded record sequence is empty. The alignment pass SHALL still be performed, with zero emitted records. The final equality check reduces to:

```
0 == candidate_count
```

No separate or abbreviated alignment algorithm is permitted for `.gunzstatz`. The alignment pass is identical for raw `.gunzstats` and decoded `.gunzstatz` data.

**LEB128 encoding (normative – Full profile only):**
For Full‑profile implementations that emit `.gunzstatz` files, the signed LEB128 encoding defined below is mandatory. The signed LEB128 encoding uses the **minimum** number of bytes; the most‑significant bit of the final byte must match the sign of the value (i.e., bit 6 = sign bit). Decoders must reject over‑long encodings.

**Minimal-profile note:** Minimal‑profile implementations may omit `.gunzstatz` entirely, or may use any lossless compression method. Conformance to the Minimal profile does not require LEB128 support.

- **Unsigned LEB128:** The value is split into groups of 7 bits (least significant first). For each group except the last, bit 7 is set to 1; for the last group, bit 7 is 0. No zero‑extension beyond the minimum necessary bytes.
- **Signed LEB128:** The integer is treated as a signed two's‑complement value. Encoding proceeds identically to unsigned LEB128, except that after the final byte, the most significant bit (bit 6 of that byte) must equal the sign bit of the value, and any higher‑order bits beyond the final byte are sign‑extended during decoding. This follows the DWARF/WebAssembly convention.

**Signed LEB128 examples:**

| Value | Encoded bytes |
|-------|---------------|
|   0   | `0x00` |
|   1   | `0x01` |
|  -1   | `0x7F` |
|  -2   | `0x7E` |

**Minimal‑encoding validation (normative).**

After decoding a signed LEB128 value `v` from `n` complete bytes, the decoder SHALL compute the canonical minimal byte length `m` for `v`:

```
m = smallest positive integer such that
    -2^(7m-1) <= v <= 2^(7m-1)-1
```

If `n > m`, the encoding is over‑long and the decoder SHALL reject the file with `GUNZ_MALFORMED_BYTECODE`.

A truncated LEB128 sequence, where the terminating byte is missing before the end of the available data, is malformed and SHALL be rejected with `GUNZ_MALFORMED_BYTECODE`.

The same minimality validation applies to unsigned LEB128 run lengths, using:

```
m = smallest positive integer such that
    v < 2^(7m)
```

and rejecting if `n > m`.

The minimal‑length computation SHALL be performed using integer arithmetic wide enough to represent `2^(7m-1)` without overflow, for the largest `m` that can occur in the file. For `.gunzstatz`, this requires at least 256‑bit arithmetic when computing the range bound for 128‑bit values.

### 4.10 Attestation Procedure (Normative, Full-profile only)

When a map is produced with `callback_sandboxed = true` and the implementation claims the Full profile, the runtime shall generate an Ed25519 attestation signature and record it in the `.gunzmeta` file. The attestation procedure defined in this section applies only when at least one `PURE_CALL` callback was invoked. For a no-callback canonical map:

- `callback_sandboxed` SHALL be `true`.
- `sandbox_type` SHALL be `"none"`.
- `attestation_signature` SHALL NOT be required.
- `runtime_id` SHALL NOT be required.

 The procedure is:

1. Construct the `.gunzmeta` JSON object as specified in §4.6, with the `attestation_signature` key present but set to an empty string (`""`).Omit `cpu_time_ms`, `elapsed_time_ms`, `memory_high_water_mark_bytes`, `windows_chained`, `system_info`, and any field explicitly marked non-deterministic. Do not omit deterministic fields such as `metric_extremes` or `stability_tolerance_time`; they SHALL be included in canonical attestation metadata if present.
2. Canonicalise the JSON object according to **RFC 8785 (JSON Canonicalization Scheme)**, which defines key ordering, whitespace removal, number formatting, and Unicode normalisation (NFC). The `attestation_signature` field must be present with the value `""` during canonicalisation. Do not omit the field; the empty string must be present in the JSON object. During canonicalisation the `attestation_signature` key **must** be present with the JSON string value `""`; the field may not be omitted, even if empty.
3. Compute the Ed25519 signature over the canonicalised UTF‑8 bytes using the runtime's private attestation key. The signature algorithm is **pure Ed25519** (no pre‑hashing). The public key size is 32 bytes; the signature size is 64 bytes.
4. Base64‑url‑encode the signature (without padding) and store the resulting string as the value of `attestation_signature`.
5. The runtime must provide a mechanism to export its public attestation key (e.g., an API call `GUNZ_GetAttestationPublicKey` or a well‑known file) so that external verifiers can validate the signature.

If signature verification fails, the map SHALL be considered non‑canonical. The recorded `callback_sandboxed` value SHALL NOT be relied upon, because the failed attestation does not establish whether callbacks were sandboxed.

**Minimal-profile note:** Minimal‑profile implementations may omit attestation entirely. If omitted, the `attestation_signature` field need not be present in `.gunzmeta`.

The attestation signature covers only the canonical `.gunzmeta` JSON, not the `.gunzmap` binary file. Detection of accidental map data corruption is provided solely by the canonical map data checksum `xxh3_64`, which is not cryptographic and does not provide tamper evidence.

If a deployment requires tamper-evident map integrity, it SHALL apply an external signature or keyed MAC over the canonical map data. Such a mechanism is outside the core GUNZ 5.0.0 format.

*(Informative)* `system_info` is host-environment telemetry, not evaluator configuration or map identity. It is excluded from canonical attestation metadata because it can vary between machines and hosts.

Canonical attestation metadata may still include `creation_timestamp`; therefore the attestation signature is not intended to be identical across repeated runs.
Its purpose is to bind the metadata instance, including its provenance, sandboxing status, and evaluator configuration.

## 5. GUNZ‑NET (Future)

GUNZ‑NET is a planned companion specification for automated map exchange, deduplication, and network‑scale coordination. It is not part of the GUNZ 5.0.0 core standard. In the meantime, `.gunzmap` files carry their own accidental-corruption checksum and can be shared directly.

**Versioning policy:** Any future `GUNZ‑NET` revision shall preserve backward compatibility of the existing fields; new fields will be added only in a reserved extension space.

## 6. Conformance (Normative)

A compliant implementation **SHALL**:

### Evaluator arithmetic and metrics

- Reject any `.gunzmap` file whose size is not exactly `64 + entry_count × 16`.
- Use the corrected `N_hi` formula (`N_hi = Q − N*d_lo_cont` with `Q = R / quantum`), and mark candidates with `FLAG_AVOID` and `FLAG_INVALID` if `N_hi` falls outside `[0, N]` or if the actual total tick advance (`N_lo * adv_lo_cont + N_hi * adv_hi_cont`) is less than `target_ticks`.
- Determine `N` using the closed‑form estimate and refined search specified in §3.11 step 3. An alternative internal search is permitted only if it provably yields identical candidate classification, including `N`, `N_hi`, validity flags, saturated sentinels, `FLAG_INVALID`, and `FLAG_AVOID` status.
- If `N₀ > MAX_N`, mark the candidate saturated and skip the search loop.
- Use continuous deltas `d_lo_cont` and `d_hi_cont` for determining `N` and `N_hi`; apply explicit delta overrides only to the block‑time sum. The resulting block time SHALL be an integer multiple of `quantum`.
- Use 64‑bit division for `T` and 128‑bit intermediates where required.
- The non‑long‑term N‑search SHALL be bounded only by `MAX_N = 2³¹ − 1`. It SHALL NOT be terminated early solely because the search step count exceeds `max_eval_iterations`.
- A precomputed `N_max` based on continuous advances SHALL NOT be treated as authoritative for rejecting or accepting a candidate. It MAY be used only as an internal optimisation if it provably produces bit‑identical candidate classifications.
- Enforce `time_unit ≤ 12` and `window_duration` bounded to a normative maximum of ≤ 2⁶⁴ − 1 base‑time units.
- Guarantee evaluator loops are bounded by `max_scan_iterations` and `total_max_scan_iterations`. For long‑term scans, `max_eval_iterations` bounds temporal block repetition. The non‑long‑term N‑search is bounded only by `MAX_N`.
- Compute standard deviations exclusively with the algorithm of §4.5.3 or the algebraically identical two‑value closed form.
- The core evaluator SHALL NOT compute or store any scalar score.
- Compute `stability_width` using the physical plateau definition in §3.11 Phase 2.
- Use full‑precision central total times for Phase 2; the saturated `block_time_inaccuracy` field SHALL NOT be used.
- Always supply a `reference_block_time`. If the user does not provide one, apply the guessing rule (§3.11) deterministically, using midpoint, then `freq_low`, then `freq_high` as fallbacks. If the bytecode contains no `ZONE` instructions and no explicit `reference_block_time` is provided, `reference_block_time` SHALL default to `0`. Record provenance in `reference_source`. If the value exceeds `UINT32_MAX`, plan construction fails with `GUNZ_INVALID_LIBRARY`.
- Support all four rounding modes defined for `round_mode` and apply the selected mode consistently in all division steps that depend on it.
- Store all per‑candidate temporary data in `ScratchArena` and reuse it; do not allocate separate per‑block buffers.
- Generate the jitter window from `jitter_window_radius` as specified, including the default behaviour when stored value is 0, and skip jitter points where `freq_candidate + Δ ≤ 0`.
- Compute full‑precision metrics before saturation: `block_time_inaccuracy` saturates to `UINT32_MAX`, `jitter` to `255`, `advance_regularity` and `peak_advance_regularity` to `65535`.
- For long‑term scans, derive `max_eval_iterations` as `ceil(window_duration / quantum)` using 128‑bit unsigned arithmetic, saturated to `2⁶⁴ − 1`. A user‑supplied `max_eval_iterations` SHALL be ignored.
- If a `PURE_CALL` is attached, invoke it once per evaluated candidate as described in §3.11 step 5. The core candidate context is exactly 16 bytes. The callback MAY read and write the context buffer as scratch space, but the evaluator SHALL ignore all callback writes for map generation. The callback’s only normative effects are its return value. The callback SHALL NOT be invoked for candidates skipped due to zero advance, N‑search failure, `MAX_N` exceeded, long‑term exhaustion, or no valid jitter points.

### Map generation

- Emit long‑jump entries for large gaps, clamped scan regions, wide `SKIP_ZONE` intervals, and inter‑zone gaps. All long‑jump gaps SHALL be strictly positive and exact multiples of `effective_step`.
- A trailing long‑jump SHALL be emitted if the sparse‑map accumulator is non‑zero after the last entry.
- Merge sparse intervals according to the normative emission algorithm in §4.2. All sparse accumulator long‑jump entries carry type `1`; all unevaluated long‑jump entries carry type `0`.
- Sparse omission and accumulator logic SHALL apply only to ordinary evaluated candidate intervals. `FLAG_INVALID`, `FLAG_SKIPPED`, and long‑jump entries are processed by their dedicated branches.
- Group consecutive candidates into a single entry only when all metrics (including `stability_width`) and flags are identical. `run_length` equals the number of merged candidates.
- Set `map_version = 0x0062` in the map header.
- Set `base_freq` to the minimum `freq_low` among all zones (including excluded), or `0` if empty.
- Set `map_flags` correctly: bit 0 and bits 2–7 SHALL be `0`; bit 1 must match the map’s sparseness. If sparse emission produced no omissions, `map_flags.sparse_map` SHALL be `0`.
- Set `reference_source` to the correct provenance; writers SHALL enforce `reference_source ≤ 3`.
- Set `long_term_scan` (offset 39) to 1 iff the scan was long‑term, else 0.
- Use the aligned 16‑byte entry layout.
- Handle run‑length overflow by splitting entries when `run_length` reaches 65535. The subsequent entry MUST have `freq_delta_start = 0`.
- Compute the XXH3‑128 map fingerprint as specified in §4.3. For dynamic‑lane maps, apply the bytecode‑derived salt.
- Set bit 0 of `flags` when stability width would exceed 65535 before saturation.
- Excluded zones SHALL be represented as specified in §3.11. The gap is computed from `global_merge_current` and `effective_step`; the old `(freq_high − freq_low) + step_freq` formula SHALL NOT be used.
- Generators SHALL use `max_lj_gap` as the per‑entry maximum when splitting long‑jump gaps.
- Generators SHALL ensure every emitted long‑jump gap is a multiple of `effective_step`.
- `max_lj_gap` SHALL be computed using the resolved `effective_step`.
- During the absolute‑frequency merge phase, a long‑jump entry starts at `global_merge_current`. In final serialised form, it starts at the decoder’s current frequency. `freq_delta_start` is the type tag only.
- Every `FLAG_SKIPPED` placeholder SHALL have `freq_delta_start = 0`.
- In sparse emission, any `FLAG_SKIPPED` placeholder SHALL act as a flush boundary for the sparse accumulator.
- Sparse emission SHALL operate on the dense candidate interval stream produced after Phase 2 and gap insertion, and before final run‑length consolidation.
- Map assembly SHALL follow the pipeline order defined in §3.3.
- For `map_type = 0`, writers SHALL store the default resolved detrimental thresholds `255` and `65535`.
- Detrimental‑mode `FLAG_AVOID` marking SHALL be applied after Phase 2 and before `SparseMapBuilder` emission, sparse emission, and final consolidation.
- Writers SHALL store effective `quantum`, `target_ticks`, `mult_num`, `mult_den`, `round_mode`, `hold_cycles`, `sep_cycles`, and `window_duration` in the map header.
- Writers SHALL set `window_duration = 0` when `long_term_scan == 0`.
- Writers SHALL set reserved bytes 28 and 29 to zero.

### Detrimental mode

- Apply separate thresholds for jitter and advance regularity.
- Use full‑precision `jitter` and full‑precision converted `advance_regularity_btu` for threshold comparison; SHALL NOT use saturated map‑entry fields.
- Treat a zero threshold as a plan‑construction shorthand resolved to the saturation limit of the respective field. The map header SHALL store the resolved non‑zero threshold.

### Import and export

- On import, validate the imported map’s `time_unit` against the plan’s `time_unit` and `map_version` against the runtime’s pinned `map_version`. Any mismatch fails with `GUNZ_INVALID_LIBRARY`.
- Validate the canonical map data checksum on import and decode by zeroing `xxh3_64` and recomputing over the 64‑byte header and all entries. Reject on mismatch.
- Reject any `.gunzmap` file whose size is not exactly `64 + entry_count × 16`.
- Use `xxh3_64` for content identity and deduplication; use XXH3‑128 map fingerprint for provenance identity.
- Maps containing legacy threshold‑zero values SHALL NOT be imported until those thresholds have been normalised.
- Imported maps SHALL be fully validated according to §4.2.1 and §6, including all header field semantics, `effective_step ≥ 1`, reserved bytes, `evaluated_candidate_count` consistency, and entry‑flag/long‑jump/delta validation.

### Bytecode safety

- Reject bytecode where `round_mode` is 4–255.
- Reject any opcode not listed in the opcode tables (including reserved opcodes).
- Enforce `arg_count ≤ 16` for `PURE_CALL`.
- Enforce `block_bytes ≤ 65535`.
- Reject bytecode with `time_unit > 12` or `target_ticks = 0`.
- Reject bytecode where any `ZONE` has `freq_high < freq_low` or frequency `0`.
- Reject bytecode where any `ZONE` or `SKIP_ZONE` violates grid‑alignment.
- If `sandboxed_callbacks_required` is set and at least one `PURE_CALL` is invoked, the runtime must produce an attestation signature; otherwise reject with `GUNZ_INVALID_LIBRARY`. If no `PURE_CALL` is invoked, no attestation is required.
- Implementations SHALL reject bytecode or map files with versions not exactly matching the runtime’s pinned versions (`0x00040000` for bytecode, `0x0062` for map).
- Oracle opcodes are optional; unsupported companions reject them with `GUNZ_MALFORMED_BYTECODE`.
- `LIBREF` SHALL clear `ADVANCE`, `ROUND`, and `DELTA`, restore effective multiplier/rounding mode, and preserve pending `PURE_CALL`.
- `LIBREF` SHALL halt with `GUNZ_INVALID_LIBRARY` if switching to a library would change the effective evaluator parameter set relative to `reference_params`.
- Reject `DELTA` where `d_lo > d_hi`.
- Evaluate capability‑requiring flags individually; unsupported required capabilities return `GUNZ_INVALID_LIBRARY`.

### Runtime

- Generate `.gunzmeta` and optional statistics files unless Minimal Profile.
- For dynamic‑lane full‑profile maps, `.gunzmeta` SHALL include `bytecode_fingerprint`.
- Implement `.gunzstatz` compression with LEB128 (Full‑profile only).
- Apply initial fuel of 10 000 for conformance testing; production deployments may override.
- Validate Environment Snapshots before binding; retain historical public keys.
- Enforce plan iteration limits at or above normative minimums. Global budget overflow is handled exclusively by the pre‑pass.
- After resolving zero to the default, a positive declared iteration limit below the minimum SHALL fail plan construction with `GUNZ_ITERATION_LIMIT_EXCEEDED`.
- Use RFC 8785 canonical JSON serialisation for attestation signatures.
- If sandboxing is not used and the flag is unset, record `callback_sandboxed = false`; maps are non‑canonical. Voluntary sandboxing may make a map canonical if `callback_sandboxed = true` and other requirements are met.
- Allow `HALT`, including implicit end‑of‑bytecode `HALT`, to execute with `fuel == 0` and return `GUNZ_OK`.
- If both fuel exhaustion and iteration‑limit exceedance occur, report `GUNZ_ITERATION_LIMIT_EXCEEDED` and return the partial map.
- Support `.gunzstats` and `.gunzstatz` file formats. Reject incorrect magic numbers.
- Decoders SHALL reject `.gunzstats` or `.gunzstatz` files with `candidate_count == 0` and size other than 8 bytes.
- `.gunzstats` records SHALL be emitted only for evaluated candidates. `FLAG_SKIPPED` entries and type‑0 long‑jump entries SHALL NOT produce records.
- Every `.gunzstats` record SHALL have `valid_jitter_points ≥ 1`.
- Writers SHALL saturate cumulative statistics accumulators to `2¹²⁸−1` with no wrapping.
- Writers SHALL set central‑direction flags according to the original evaluated candidate and never set both flags on one entry.
- Statistics file alignment and validation SHALL follow §4.8/§4.9.

### Decoder validation

- Decoders SHALL reject a map header where `quantum == 0`, `target_ticks == 0`, `mult_num == 0`, `mult_den == 0`, or `round_mode > 3`.
- Decoders SHALL reject a map header where `time_unit > 12`.
- Decoders SHALL reject a map header where reserved byte 28 or 29 is non‑zero.
- Decoders SHALL reject a map header where any reserved bit in `map_flags` is set.
- Decoders SHALL reject a map header where `map_type > 1`.
- Decoders SHALL reject a map header where `detrimental_jitter_threshold == 0` or `detrimental_advance_regularity_threshold == 0`.
- Decoders SHALL reject a map header where `map_version != 0x0062`.
- Decoders SHALL reject a map header where `reference_source > 3`.
- Decoders SHALL reject a map header violating the `reference_block_time`/`reference_source` consistency rule.
- Decoders SHALL reject a map header where `long_term_scan > 1`.
- Decoders SHALL reject a map header where `effective_step == 0`.
- Decoders SHALL reject a map header where `long_term_scan == 0` and `window_duration != 0`.
- Decoders SHALL NOT reject `window_duration == 0` when `long_term_scan == 1`.
- After full entry decoding, decoders SHALL verify `evaluated_candidate_count` matches the decoded entry stream. If not, reject with `GUNZ_MALFORMED_BYTECODE`.
- Decoders SHALL reject any normal map entry with non‑zero reserved flag bits 6–7.
- Decoders SHALL reject any normal entry where `FLAG_INVALID` is set unless `FLAG_AVOID` is also set and `FLAG_SKIPPED` is clear.
- Decoders SHALL reject any normal entry with both `FLAG_AVOID` and `FLAG_SKIPPED` set.
- Decoders SHALL reject any long‑jump entry with decoded gap zero or negative.
- Decoders SHALL reject any long‑jump entry whose `freq_delta_start` is not 0 or 1.
- Decoders SHALL reject type‑1 long‑jump if `map_flags.sparse_map == 0`.
- Decoders SHALL reject any long‑jump entry whose gap is not an exact multiple of `effective_step`.
- Decoders SHALL reject any long‑jump entry whose gap exceeds `max_lj_gap`.
- Decoders SHALL reject any normal entry where `current + freq_delta_start < current`.
- Decoders SHALL reject sparse‑map evaluated normal entries with positive `freq_delta_start` not an exact multiple of `effective_step`.
- Decoders SHALL reject normal entries with `FLAG_INVALID` set and `freq_delta_start > 0`.
- Decoders SHALL reject normal entries with `FLAG_INVALID` set and `stability_width != 0`.
- Decoders SHALL reject normal entries with both `FLAG_INVALID` and `STAB_SATURATED` set.
- Decoders SHALL reject entries where `run_length == 0` and `block_time_inaccuracy != 0`.
- Decoders SHALL use the header’s `long_term_scan` field as the sole authority for long‑term mode.
- Decoders SHALL treat long‑jump entries as gaps based on the sentinel `run_length == 0 && block_time_inaccuracy == 0`.
- Decoders SHALL reject maps with no entries and `base_freq != 0`.
- Decoders SHALL reject normal entries with both central‑direction flags set.
- Decoders SHALL reject `FLAG_SKIPPED` placeholders with any central‑direction flag set.
- Decoders SHALL reject `FLAG_INVALID` entries with any central‑direction flag set.
- Library profiles SHALL NOT emit rounding metadata; decoders SHALL ignore rounding metadata if encountered.

## 7. Implementation Guidance *(Informative)*

- Canonical map data checksum validation requires access to the complete canonical map bytes. Implementations may buffer the canonical map data or perform a two‑pass validation; streaming entry‑only validation is insufficient.

- Use golden vectors for library validation.

- Batch independent zones for SIMD.

- Precompute reciprocal constants for invariant divisors.

- Use branch‑free evaluator logic and separate specialisations for delta overrides.

- **Vectorisation:**
  Prefer branch‑free integer arithmetic and SIMD intrinsics over lookup tables. On GPU architectures, map one thread per **candidate**, not one thread per jitter point, to eliminate warp divergence.

- Reuse `N` across jitter samples; vectorise the jitter‑point loop where possible.

- Batch map entry writes through a staging buffer.

- Adaptive multi‑resolution scanning (see §3.4.3) is a recommended strategy for efficient resonance discovery.

- **Plateau‑jump optimisation:**
  All Phase 1 metrics (`block_time_inaccuracy`, `jitter`, `advance_regularity`, and `peak_advance_regularity`) and the central total time are step functions of frequency. A conformant implementation may identify intervals where, for every frequency in the interval, all Phase 1 metrics, central total time, central‑direction flags, and the set of valid jitter offsets are invariant.

  Within such an interval, the Phase 1 metrics are identical for every candidate. The implementation may evaluate only one representative per interval, then replicate the Phase 1 results across the entire interval to build a complete candidate array. Phase 2 stability width is then run on the reconstructed array as if every candidate had been individually scanned. The stability width computed for any reconstructed candidate will exactly match the width that would have been obtained from a full scan. This procedure guarantees bit‑identical map output to the normative full‑scan algorithm.

  **Constant‑metric interval:**
  A candidate frequency belongs to a constant‑metric interval if, when the candidate is shifted by any jitter offset Δ in the window, all resulting frequencies produce identical values for every Phase 1 metric:

  - `block_time_inaccuracy`
  - `jitter`
  - `advance_regularity`
  - `peak_advance_regularity`
  - the central‑direction flag assignment
    (`FLAG_CENTRAL_ABOVE`, `FLAG_CENTRAL_BELOW`, or both clear)

  Because `block_time_inaccuracy` is an absolute value, two candidates on opposite sides of `reference_block_time` can share the same inaccuracy. They SHALL NOT be grouped by plateau‑jump unless their central‑direction flags also match.

  Phase 2 stability width and final flags are computed after the Phase 1 array is reconstructed, exactly as in a full scan. The constant‑metric interval definition SHALL NOT include Phase 2 outputs. A candidate frequency belongs to a constant‑metric interval only if, in addition to producing identical Phase 1 metrics, the **set of valid jitter offsets is identical** for every candidate frequency in the interval.

  Because `PURE_CALL` writes are ignored for map generation, the map output is unaffected by callback writes. However, a callback may still return `GUNZ_CALLBACK_FAILED` and abort the run. Therefore, the plateau‑jump optimisation SHALL NOT be applied to a zone with an attached `PURE_CALL` unless the implementation can prove that the callback’s return value is constant across the entire interval. This preserves the observable run status. Phase 2 and final consolidation are still performed normally after reconstruction.

- **Low‑frequency zones:**
  The evaluator gracefully handles zones with frequencies as low as 1 (10⁻⁵ Hz units) by skipping invalid jitter points. The effective number of jitter points may be less than 21 near the low‑frequency limit, which is deterministic and faithful to the physical timing uncertainty at those timescales. Ensure the jitter‑point skipping logic is correctly implemented.

- **Memory efficiency:**
  All per‑candidate temporary data must be stored in the `ScratchArena` and reused across blocks (see the normative requirement in §3.11 step 3). This avoids O(N) memory growth and ensures deterministic resource usage.

- **Phoenix mechanism (resuming AI sessions):**
  The `.gunzmap` and `.gunzmeta` pair, combined with the `session_id` field, allows an AI to treat a completed scan as a memory. All maps sharing the same `session_id` belong to the same exploration. The `chain_sequence` and `chain_next_fingerprint` fields provide ordering within each branch. When a Calibrated Reference (`reference_source = 3`) is used, the map's `reference_block_time` is anchored to a previous measurement, enabling precise iterative refinement.

- **Hibernation (cost‑aware scanning):**
  When the computational cost of generating a new map exceeds the marginal improvement, the system should pause active scanning and hibernate — retaining the current map as its stable operating point. The system may reawaken when a monitor detects rising jitter, advance regularity, or a narrowing stability width.

- **Fuel budget and orchestration:**
  Even with the canonical conformance fuel of 10,000, a dynamic program can orchestrate a scan of tens of millions of candidates by issuing a few wide `ZONE` instructions. This separation of orchestration (fuel‑bound) from evaluation (iteration‑bound) is central to GUNZ's design. The `fuel_consumed` field in `.gunzmeta` allows AI agents to distinguish between logic inefficiency (high fuel, low iterations) and overly ambitious scan zones (low fuel, high iterations).

- **Static complexity estimation:**
  Plan constructors must compute worst‑case iteration counts and reject plans that exceed the plan's declared limits. The long‑term `max_eval_iterations` will be clamped to `2⁶⁴−1`, so extremely large windows may proceed at that bound.

- **Jitter window radius:**
  The default radius of 10000 (21 points, ±0.1 Hz) is recommended for calibration and accuracy work, where fine phase‑transition edges must be captured. For wide‑area search scans where speed is more important than edge sharpness, a smaller radius (e.g., 5000, giving 11 points) may be used without loss of validity; however, narrow stability regions may be missed or under‑estimated.

- **Global iteration limit enforcement** is performed by the single‑threaded pre‑pass described in §3.11. No runtime atomic counter is required for budget allocation; the budget is fixed before worker threads are spawned.

- **Stability‑width algorithm note:**
  The normative definition in §3.11 Phase 2 requires that for each evaluated candidate `c`, every evaluated candidate `i` in the plateau satisfies:

  ```text
  | T_i − T_c | ≤ stability_tolerance_time
  ```

  where `T_i` and `T_c` are full‑precision central total times. Any algorithm that produces the same maximal contiguous runs is conformant. The reference implementation uses a linear‑scan algorithm that expands left and right from each candidate and reuses bounds; do not rely on spread‑based sliding‑window sketches without verifying that the per‑candidate absolute tolerance is satisfied for every point in the interval and that hard boundaries are respected.

- **Degenerate `window_duration = 0`:**
  If `window_duration` is set to `0`, the derived `max_eval_iterations` becomes `0` for every candidate. The evaluator immediately exhausts the iteration limit and marks all candidates with `FLAG_AVOID` and saturated sentinels. The resulting map is structurally valid (the header and checksum are correct) but contains no meaningful resonance data. This behaviour is deterministic; it may be useful for testing the map‑generation pipeline without performing an actual scan. For any non‑zero measurement, supply a positive `window_duration`.

- The non‑long‑term N‑search is bounded only by `MAX_N = 2³¹ − 1`. Because `max_eval_iterations` does not limit that search, a conformant implementation should either use a proven equivalent shortcut or enforce an external resource limit when executing untrusted dynamic‑lane programs.

- **Resource limits for untrusted programs (informative):**
  The non‑long‑term N‑search is bounded only by `MAX_N = 2³¹ − 1` in the normative algorithm. Implementations that execute untrusted dynamic‑lane bytecode SHOULD enforce an external CPU or memory limit per `ExecutionPlan_Run`. If such a limit is exceeded, the implementation SHOULD abort the entire run and return an implementation‑defined resource‑exhaustion status. It SHOULD NOT return a partial map. This preserves bit‑identical output for all completed runs, because aborted runs produce no map.

- **Sparse‑map accumulator overflow example (informative):**
  When `sparse_map` is active and consecutive intervals are omitted, the generator accumulates their run‑lengths into the next emitted entry's `freq_delta_start`. The accumulated offset is limited to ±32767. If adding another omitted interval would exceed that range, the generator first emits a long‑jump entry with type `1` for the accumulated gap, resets the accumulator to zero, and then continues. If the accumulator ever exceeds `max_lj_gap`, the generator automatically splits it into multiple long‑jump entries, each with a gap of `max_lj_gap` except the last, before evaluating the delta. After all entries have been processed, any remaining accumulator is flushed as a final long‑jump entry (or entries) with type `1`. (`max_lj_gap` is defined in §4.2.)

  *Example:* suppose `effective_step = 1` and three omitted intervals have run‑lengths 10 000, 10 000, and 15 000. Under candidate‑count semantics, the accumulated omitted gaps are:

  ```text
  10 000 × 1 = 10 000
  10 000 × 1 = 10 000
  15 000 × 1 = 15 000
  ```

  The running accumulator reaches 20 000 after the first two omissions, then 35 000 after the third. When the next non‑omitted entry is encountered, if `original_freq_delta_start + 35 000` exceeds 32767, the generator first emits a long‑jump entry with type `1` and gap = 35 000, resets the accumulator to zero, and then emits the entry with its original `freq_delta_start`. This preserves the invariant that `freq_delta_start` never exceeds the signed 16‑bit range.

- **Typical worst‑case values (informative):**

  | Zone | Step | Candidates | Approx. map data | Approx. memory (scan) |
  |------|------|------------|------------------|-----------------------|
  | 90 Hz | 10⁻⁵ Hz | 9 000 000 | 144 MiB (unmerged) | ~4 GiB (with jitter buffers) |
  | 30 Hz | 10⁻⁵ Hz | 3 000 000 | 48 MiB | ~1.5 GiB |
  | 1 Hz | 10⁻⁵ Hz | 100 000 | 1.6 MiB | ~80 MiB |

- **Leak detection (optional):** Implementations may provide an API to iterate over all live `ExecutionPlan` objects and log any that have zero references but have not been freed.

### Seed reference, calibrated reference, and the guessing rule

|  | **Seed Reference** (initial intent) | **Calibrated Reference** (discovered truth) |
|---|---|---|
| **Origin** | Supplied by the user or AI agent at the start, or produced by the **guessing rule** (§3.11). May be a rough guess, a theoretical ideal, or an arbitrary starting point. | Derived from a previous GUNZ map: find the candidate with the smallest `block_time_inaccuracy` and compute its actual total block time from the companion `.gunzstats` file (the map entry alone stores only the unsigned deviation, which is insufficient for reconstruction). |
| **Accuracy** | Not expected to match reality. Could be arbitrarily far from observed behaviour. | Empirically anchored in the system's real timing. As close to the physical truth as the scanner's resolution allows. |
| **Role** | Kickstarts the search. Provides an initial anchor so the evaluator has a baseline for measuring deviation. | Serves as the definitive anchor for subsequent fine‑grained scans, optimisation, and cross‑comparison. |
| **Recorded in map** | Stored in the `reference_block_time` field of the map header, with `reference_source` set to `2` if produced by the guessing rule. | Stored in the `reference_block_time` field, with `reference_source` set to `3` (Calibrated Reference). |
| **Fingerprint** | Included in the map's XXH3‑128 identity. | Included in the next map's fingerprint, making the two maps distinct. |

## Appendix C — Rationale for Constants *(Informative)*

The following table provides the engineering rationale for selected normative constants used in **GUNZ 5.0.0**:

| Constant | Value | Justification |
|----------|-------|---------------|
| `jitter_window_radius` default | 10 000 (21 points, ±0.1 Hz) | The 21‑point window provides dense local sampling of the resonance landscape while keeping the scan overhead moderate. The ±0.1 Hz neighbourhood is wide enough to capture phase‑transition edges in typical discrete‑clock engines. |
| `initial_fuel` (conformance) | 10 000 | Chosen to keep the conformance test suite lightweight and deterministic; large enough to allow meaningful dynamic programs without excessive execution time. |
| `MAX_STATIC_EVALUATORS` | ≥ 65 536 | Derived from practical memory limits: with 16‑byte map entries and typical scratch‑arena sizes, a plan with more than 65 536 evaluator blocks would stress embedded systems. The value may be increased by implementations that support larger plans. |
| `max_scan_iterations` (per zone) lower bound | 2²⁴ (16 777 216) | Represents a reasonable worst‑case scan of ~168 Hz at 10⁻⁵ Hz resolution. Exceeding this suggests an AI agent should use multi‑resolution scanning. |
| `window_duration` maximum | ≤ 2⁶⁴ − 1 base‑time units | Ensures that the product of cycle time and window duration never overflows a 128‑bit accumulator in long‑term mode. |
| `max_eval_iterations` clamping | ≤ 2⁶⁴ − 1 | Prevents overflow in the ceiling derivation and sets a firm upper bound for the per‑candidate loop, consistent with 64‑bit counters. |
| `DELTA` override existence | – | Preserves the ability to model engines (such as the RealSpace2 core) where the temporal pattern of cycles is fixed but the effective work per cycle can be independently varied. The `DELTA` opcode is a Dynamic Lane bytecode instruction, but an explicit delta override can also be supplied through a native `ExecutionPlan` configuration to the static‑lane evaluator. The override is not required for minimal conformance. |
| Direct `effective_step` storage | `effective_step` stored as a `u32`, SHALL be ≥ 1 | Eliminates the former `step_freq`/`step_freq_overflow` encoding and optional extension. Since the header stores the resolved step directly, there is no alternative raw encoding to create fingerprint divergence. |
| Canonical `jitter_window_radius` default representation | `jitter_window_radius = 0` when effective radius is `10000` | Same reason: removes equivalent raw encodings from the fingerprint input. |
| Default iteration budgets | `max_eval_iterations = 65 536`; `total_max_scan_iterations = 2²⁶` | Provides deterministic defaults when the user does not supply explicit limits. |

## Appendix E — Minimal Conformance Vectors (Normative)

The following list describes categories of conformance test vectors and their expected outcomes.
The bullets are test requirements, not standalone normative requirements; normative conformance obligations are defined in the main body and in §6.

### Arithmetic, evaluator, and metrics

- All normative arithmetic paths and rounding modes, including fixed floor, fixed ceil, header `round_mode`, half‑to‑even, and integer square root.
- Deterministic integer standard deviation algorithm, including the two‑value closed form for advance regularity.
- Full‑precision metric computation before saturation:
  - `block_time_inaccuracy` saturates to `UINT32_MAX`
  - `jitter` saturates to `255`
  - `advance_regularity` and `peak_advance_regularity` saturate to `65535`
- Derived `advance_regularity_btu` computed from full‑precision average advance regularity, used only for detrimental threshold comparison.
- Detrimental marking uses full‑precision `jitter` and full‑precision `advance_regularity_btu`, never saturated stored fields.
- `map_type = 0` stores default thresholds `255` and `65535`.
- Refined N‑search algorithm, including closed‑form estimate, monotonic search, `N_hi` validation, and saturated skip classification.
- Alternative N‑search equivalence includes `N`, `N_hi`, validity flags, saturated sentinels, `FLAG_AVOID`, and `FLAG_INVALID`.
- Non‑long‑term N‑search bounded only by `MAX_N = 2³¹ − 1`, not by `max_eval_iterations`.
- Long‑term `max_eval_iterations` derived as `ceil(window_duration / quantum)` using 128‑bit arithmetic, saturated to `2⁶⁴ − 1`.
- Degenerate `window_duration = 0` produces structurally valid map with no meaningful resonance data.
- Guessing‑rule fallback: midpoint, then `freq_low`, then `freq_high`.
- Low‑frequency zone handling, including skipped invalid jitter points.

### Physical stability width

- Stability tolerance computed once per map:

  ```text
  stability_tolerance_time =
      max(quantum, round_half_even(reference_block_time / 1_000_000))
  ```

- Plateau where all central total times differ by at most `stability_tolerance_time`.
- Plateau boundary where one candidate’s central total time differs by more than `stability_tolerance_time`.
- `FLAG_INVALID` candidate acts as a hard boundary.
- `FLAG_SKIPPED` placeholder acts as a hard boundary.
- Type‑0 long‑jump entry acts as a hard boundary.
- Sparse‑omitted perfect intervals may be plateau members.
- `right == left` produces `stability_width = 0`.
- Pre‑saturation width greater than `65535` sets `STAB_SATURATED`; exactly `65535` clears it.
- No‑scan map has no Phase 2 computation.

### Map header and decoding

- Map header is exactly 64 bytes.
- File size validation: `64 + entry_count × 16`.
- Reserved bytes 28 and 29 must be zero; non‑zero rejected.
- `map_flags` reserved bits must be zero.
- `map_type > 1` rejected.
- `map_version != 0x0062` rejected.
- `reference_source > 3` rejected.
- `reference_block_time` / `reference_source` consistency rule enforced.
- `long_term_scan > 1` rejected.
- `effective_step == 0` rejected.
- `window_duration != 0` when `long_term_scan == 0` rejected.
- `window_duration == 0` when `long_term_scan == 1` accepted as degenerate scan.
- `quantum == 0`, `target_ticks == 0`, `mult_num == 0`, `mult_den == 0`, or `round_mode > 3` rejected.
- `time_unit > 12` rejected.
- Detrimental thresholds stored as `0` rejected.
- Empty map: no entries and `base_freq == 0`; non‑zero `base_freq` rejected.
- `evaluated_candidate_count` matches decoded entry stream after full validation.
- If `.gunzmeta.stability_tolerance_time` is present, it SHALL equal the
  normative tolerance computed from `quantum` and `reference_block_time`;
  mismatch is rejected.

### Map generation

- Long‑jump entries for large gaps, clamped scan regions, wide `SKIP_ZONE` intervals, and inter‑zone gaps.
- Long‑jump gaps strictly positive and exact multiples of `effective_step`.
- No single long‑jump gap exceeds `max_lj_gap`; overlong gaps split with no zero‑gap final entry.
- `max_lj_gap` computed using resolved `effective_step`.
- `FLAG_SKIPPED` placeholder always has `freq_delta_start = 0`.
- Sparse accumulator flush boundary at `FLAG_SKIPPED`.
- Sparse emission operates on dense candidate interval stream before final consolidation.
- All sparse accumulator long‑jump entries carry type `1`.
- All unevaluated long‑jump entries carry type `0`.
- Type‑1 long‑jump rejected if `map_flags.sparse_map == 0`.
- Sparse map with no omissions sets `map_flags.sparse_map = 0`.
- Positive `freq_delta_start` in dense map rejected.
- Sparse positive `freq_delta_start` must be exact multiple of `effective_step`.
- `FLAG_INVALID` entries always have `freq_delta_start = 0`.
- Run‑length overflow splits entries; subsequent entry has `freq_delta_start = 0`.
- Grouping consecutive candidates requires identical metrics and flags.
- `map_flags.sparse_map` matches actual omission state.

### Import/export

- Import verifies at least 64‑byte header before checksum.
- Canonical map data checksum validation before any other validation.
- Checksum mismatch returns `GUNZ_INVALID_LIBRARY`.
- Import validates `time_unit` and `map_version` against plan/runtime.
- Import rejects stored detrimental threshold `0`.
- Import fully decodes and validates all header and entry rules.
- Legacy threshold‑zero maps require normalisation before import.
- Object‑table overwrite semantics for `EXPORT` and `IMPORT`.

### Bytecode and VM

- Strict version matching: bytecode `0x00040000`, map `0x0062`.
- Bytecode `round_mode` values 4–255 rejected.
- Reserved opcodes rejected.
- `arg_count ≤ 16` enforced.
- `block_bytes ≤ 65535` enforced.
- Bytecode `time_unit > 12` rejected.
- Bytecode `target_ticks = 0` rejected.
- `ZONE` with `freq_high < freq_low` or frequency `0` rejected.
- Zone/skip‑zone grid alignment and disjointness enforced.
- `SCAN_RES` ordering enforced on effective inline sequence.
- `LOOP` with `count = 0` or `block_bytes = 0` rejected.
- Loop body bounds and nested containment enforced.
- Fuel accounting per instruction, including loop iterations.
- `HALT` with zero fuel succeeds.
- Fuel exhaustion and iteration‑limit exceedance precedence: iteration limit wins.
- `ADVANCE` rejects zero numerator or denominator.
- `DELTA` rejects `d_lo > d_hi`.
- `LIBREF` clears `ADVANCE`, `ROUND`, and `DELTA`, preserves pending `PURE_CALL`.
- `LIBREF` parameter consistency enforced for `quantum`, multiplier, and `jitter_window_radius`.
- Oracle opcodes optional; unsupported companion rejects opcodes with `GUNZ_MALFORMED_BYTECODE`.
- Capability‑requiring flags validated individually; unsupported required capabilities rejected.

### PURE_CALL and callback behavior

- Core candidate context is exactly 16 bytes.
- Minimum `output_size` for `PURE_CALL` bound to `ZONE` is 16 bytes.
- `PURE_CALL` consumed by `SKIP_ZONE` is discarded and not subject to minimum.
- Callback writes to candidate context buffer are ignored for map generation.
- Resulting map is identical to no‑callback evaluation.
- Callback writes SHALL NOT affect `.gunzstats` or `.gunzstatz`.
- Callback return values:
  - `GUNZ_OK` continues
  - `GUNZ_CALLBACK_FAILED` aborts run
  - `GUNZ_SANDBOX_VIOLATION` aborts run
- Callback exclusion list includes zero advance, N‑search failure, `MAX_N` exceeded, long‑term exhaustion, and no valid jitter points.
- Companion extension may extend context after offset 16; core 16 bytes remain mandatory prefix.

### Statistics files

- `.gunzstats` magic `0x475A4C04`.
- `.gunzstatz` magic `0x475A4C05`.
- File size validation for zero‑candidate files exactly 8 bytes.
- 96‑byte record structure.
- Cumulative accumulators saturate to `2¹²⁸−1`, no wrapping.
- `.gunzstats` alignment pass against `.gunzmap`.
- `FLAG_INVALID` entries still advance decoder current but emit no records.
- Type‑1 long‑jump expands to records.
- Dense candidate stream reconstruction from sparse maps.
- Compressed delta stream decoding and LEB128 minimal encoding.
- Zero‑mask run advancement and remaining candidate validation.

### Fingerprint and identity

- `xxh3_64` coverage: 64‑byte header and all 16‑byte entries.
- `xxh3_64` field offset 48–55 zeroed during computation.
- XXH3‑128 fingerprint field order excludes `xxh3_64`, reserved bytes, and `evaluated_candidate_count`.
- Dynamic‑lane fingerprint salt derived from bytecode lower 64 bits.
- Dynamic‑lane salting XORs first 8 bytes of fingerprint buffer.
- Static‑lane fingerprint unsalted.
- Fingerprint recomputed after any mutation.

### Plateau‑jump optimisation

- Reconstructed array from plateau‑jump produces identical map output to full scan.
- Constant‑metric interval requires identical Phase 1 metrics, central‑direction flags, and valid jitter set.
- Plateau‑jump disabled for zones with attached `PURE_CALL` unless callback return value provably constant.

### Metric extremes metadata

- `metric_extremes` SHALL be omitted when no candidate was successfully evaluated.
- When `metric_extremes` is present, its `*_min` and `*_max` fields SHALL use saturated stored values.
- When any `central_*_count` field is present, all three SHALL be present.
- The invariant `central_above_count + central_below_count + central_exact_count == evaluated_candidate_count` SHALL hold.
- Sparse‑omitted perfect intervals SHALL be included in `metric_extremes`.
- `metric_extremes` SHALL be omitted for derived maps.

### Appendix F — Reference Sandbox and Environment Snapshot Example *(Informative)*

#### F.1 Minimal WebAssembly Sandbox (Conceptual)

The following is a sketch of a minimal, deterministic WebAssembly sandbox that satisfies the `PURE_CALL` sandboxing requirements of §3.7.  It is provided as a reference to help implementers understand the expected isolation model.

- **Runtime:** A standalone WebAssembly runtime (e.g., Wasmtime or Wasmer) configured with *no host imports*.  Only the WASI‑null interface is available.
- **Determinism:** All non‑deterministic WASI calls (clock, random) are replaced by deterministic stubs that return fixed values (e.g., clock always returns 0, random always returns 0).
- **Memory limit:** 64 MiB of linear memory; any growth beyond this limit causes instant trap and is reported as `GUNZ_CALLBACK_FAILED`.
- **CPU budget:** A fixed instruction count limit (e.g., 1 000 000 WebAssembly instructions) per invocation.  If the limit is exceeded, the sandbox traps and the callback is considered failed.
- **Integration with GUNZ:** Before execution, the runtime compiles the `.wasm` module and instantiates it once.  For each `PURE_CALL`, the runtime calls the exported function specified by the bytecode’s `callback_id`, passing the argument array as a single linear‑memory buffer.  The return value is read from a predefined memory location.

This model provides isolation (no host filesystem, no network), determinism (no unpredictable external inputs), and resource limits (memory and CPU).  It is one possible implementation; any mechanism that guarantees the same properties is acceptable.
