# GUNZ‑DRIFT 1.0 — Intra‑Block Advance Trend Metric Extension  
*Companion to GUNZ 3.67.0*

---

## 1. Overview

GUNZ‑DRIFT extends the GUNZ resonance evaluator with a directional **drift** metric that captures the *intra‑block* accumulation of rounding decisions.  Unlike `advance_regularity`, which measures the variance of per‑cycle advances without regard to order, drift measures the **slope** of those advances across the cycles of a single block.

A positive drift means the per‑cycle advance increases over the course of a block (long cycles cluster toward the end).  A negative drift means the advance decreases (long cycles cluster toward the beginning).  A drift of zero indicates that the long and short cycles are uniformly distributed throughout the block.

This metric reveals a dimension of timing behaviour that the existing metrics are blind to — the direction in which rounding decisions accumulate within a block, independent of their magnitude.  It requires no new simulation infrastructure and is computed from data the evaluator already collects.

**Integration philosophy.**  Drift is stored in the extended **`.gunzstats`** companion file, not inside the map entry.  The map entry remains the standard 16‑byte structure defined in GUNZ 3.67.0 §4.2.  No custom map version is required; maps produced with drift enabled are standard GUNZ maps with `map_version = 0x0040`.  The extension is entirely in the optional statistics companion file.  Tools that require drift must read the companion statistics file; the `.gunzmap` alone does not contain this metric.

---

## 2. Definition

Let a block consist of `N` cycles.  Each cycle `i` (0‑based) contributes an advance value `a_i` of either `100 × adv_lo` or `100 × adv_hi` (ticks × 100), determined by the placement logic defined in §2.1.

The **intra‑block drift** `d` is the slope of the linear least‑squares fit of `a_i` against the cycle index `i`.

\[
d = \frac{N \cdot \sum (i \cdot a_i) - (\sum i) \cdot (\sum a_i)}{N \cdot \sum (i^2) - (\sum i)^2}
\]

where all sums run from `i = 0` to `N-1`.

Because the cycle indices form a known arithmetic progression, the sums of `i` and `i^2` have closed forms:

\[
S_i = \frac{N(N-1)}{2}, \qquad S_{i^2} = \frac{N(N-1)(2N-1)}{6}
\]

The normative computation is:

```
sum_a   = Σ a_i          (256‑bit unsigned)
sum_ia  = Σ (i · a_i)    (256‑bit unsigned)
num     = N · sum_ia − S_i · sum_a    (signed, may be negative)
den     = N · S_{i^2} − (S_i)²        (positive for N ≥ 2)
```

The absolute quotient `q = |num| / den` is computed using the half‑to‑even integer division defined in §4.5.1 of the core GUNZ specification (which applies to non‑negative operands).  The rounded drift value is:

```
d =  q  if num ≥ 0
d = −q  if num < 0
```

Equivalently, for negative numerators the tie‑breaking rule is: if the exact quotient lies exactly halfway between two integers, round to the even integer.  Examples: `−1.5 → −2`, `−0.5 → 0`, `−2.5 → −2`.

All multiplications shall use **256‑bit unsigned arithmetic** to prevent overflow.  The denominator is guaranteed to be positive for `N ≥ 2`.  For `N < 2`, drift is defined as **zero**.

The drift value `d` is a signed integer expressed in **ticks × 100 per cycle**.  It is **not** converted to base time units for storage; the conversion to base time units, if needed for scoring, follows the same pattern as for `advance_regularity` (§3.11 step 4 of the core specification).

### 2.1 Per‑Cycle Advance Sequence (Normative)

The evaluator determines `N_hi` — the number of long cycles in the block — by rounding `N * T / quantum` according to the selected `round_mode`.  This value is computed in §3.11 step 3 of the core specification and is **not** recomputed by the drift algorithm.  The drift metric must assign the long advances to exactly `N_hi` cycles in a pattern that is consistent with the evaluator's own computation but also sensitive to the continuous frequency.

The placement is performed by a deterministic Bresenham‑style error‑accumulation algorithm.  The algorithm guarantees exactly `N_hi` long cycles by construction, so the total block time and `advance_regularity` are unchanged.  The ordering of those long cycles depends on the continuous cycle time `T` through a phase offset derived from the continuous remainder of the block time, giving drift its discriminative power.

The drift metric uses the **continuous advances** `adv_lo_cont` and `adv_hi_cont` as defined in §3.11 step 3 of the core specification, regardless of whether an explicit delta override is active.  If a delta override is active, the override values `d_lo_ov`, `d_hi_ov` do **not** affect the drift sequence; the drift sequence is always derived from the continuous advances.  This is because drift measures the directional ordering of long‑cycle placement, which is determined entirely by the fractional timing of the continuous cycle time `T`.  The override changes the *magnitude* of each cycle's advance but not *which* cycles are long; the temporal pattern of long cycles is invariant under the override.

**Initialisation:**

Let `P = N * T` (the continuous block time before rounding, in base time units, computed using 128‑bit unsigned arithmetic).  The continuous remainder `rem` is:

    rem = P % quantum    (0 ≤ rem < quantum)

The continuous remainder `rem` is computed from the **unrounded** continuous block time `P = N * T`, not from the rounded block time `R`.  The `round_mode` affects `N_hi` but does not affect the drift placement.

The phase offset `E` is derived from the continuous remainder:

    E = (rem * N) / quantum    (integer division, floor)

Since `rem < quantum`, the product `rem * N` is at most `(quantum - 1) * N`, and the result `E` is guaranteed to be in the range `[0, N-1]`.

*Rationale:* deriving `E` from the continuous remainder ensures that the drift placement varies with the fractional timing of the block, capturing the directional information.  The Bresenham algorithm produces exactly `N_hi` long cycles for any initial error in `[0, N-1]`; the choice of `E` does not affect `N_hi` or any other evaluator metric, only the order of the long cycles.

**Bresenham placement loop** (for `i = 0` to `N-1`):

```
error = E
for i = 0 to N-1:
    error = error + N_hi
    if (error >= N):
        a_i = 100 × adv_hi
        error = error - N
    else:
        a_i = 100 × adv_lo
```

The resulting sequence `a_0, …, a_{N-1}` contains exactly `N_hi` long cycles (value `100 × adv_hi`) and `N − N_hi` short cycles (value `100 × adv_lo`).  The ordering is deterministic and varies with the fractional timing of the block.

**Properties:**

- When `rem = 0`, the continuous block time is an exact multiple of the quantum.  The initial error is `E = 0`, and the resulting pattern is the most uniform distribution of long cycles.  Drift will be zero (or very close to zero).
- As `rem` increases toward `quantum`, the initial error approaches `N-1`, producing a front‑loaded or back‑loaded pattern.  The drift formula will detect this as a non‑zero slope.

All intermediate computations shall use **128‑bit unsigned arithmetic** where required to avoid overflow.  The resulting sequence is bit‑identical for all conformant implementations given identical inputs.

The drift metric depends on the effective quantum value used by the evaluator, which is guaranteed to be `≥ 1` after parameter merging (§3.10 of the core specification).

**Jitter‑window scope.** The drift computation is performed for every valid jitter offset `Δ` in the jitter window. For each offset, the cycle time `T_jitter` is computed from the offset frequency `freq_candidate + Δ`, and the block parameters (`N`, `N_hi`) are derived from `T_jitter` exactly as described in §3.11 of the core GUNZ specification. The per‑jitter‑point drift values are then aggregated into the candidate‑level metrics `drift`, `drift_max`, and `drift_min` as defined in §4.

## 3. Interpretation

| Drift value | Meaning |
|-------------|---------|
| `d = 0` | Uniform distribution of long cycles.  No directional bias. |
| `d > 0` | Long cycles cluster toward the **end** of the block (advance increases). |
| `d < 0` | Long cycles cluster toward the **beginning** of the block (advance decreases). |

The magnitude of `d` is the average change in advance value per cycle, in ticks × 100.

Drift is independent of `advance_regularity`.  Two blocks with identical per‑cycle advance variance can have opposite drift if the long cycles are ordered differently.  Drift provides the directional information that variance discards.

---

## 4. Aggregation Across Jitter Points and Temporal Blocks

For each candidate frequency, the evaluator computes a per‑block drift value `d_j(Δ)` for every valid jitter offset `Δ` as defined in §2, using the block parameters (`N`, `N_hi`, `T_jitter`) that apply at that offset.

**Per‑jitter‑point aggregation (long‑term mode).** When `long_term_scan` is active, the per‑block drift values at a single jitter offset are averaged to obtain the per‑jitter‑point drift `d(Δ)`:

\[
d(Δ) = \frac{1}{B} \sum_{j=0}^{B-1} d_j(Δ)
\]

where `B` is the number of blocks evaluated at that jitter offset. The mean is rounded half‑to‑even using the signed convention of §2. In single‑block mode, `d(Δ) = d_0(Δ)` for the single block.

**Per‑candidate aggregation.** The per‑candidate drift values are obtained by aggregating the per‑jitter‑point values `d(Δ)` across all valid jitter points:

- `drift` — the arithmetic mean of all `d(Δ)` across all valid jitter points, rounded half‑to‑even (signed). If the jitter window contains only one valid point, `drift` equals `d(0)`.
- `drift_max` — the maximum value of `d(Δ)` observed over all jitter points (most positive, or least negative if all values are negative).
- `drift_min` — the minimum value of `d(Δ)` observed over all jitter points (most negative, or least positive if all values are positive).

All summations shall use at least **128‑bit signed** accumulation to prevent overflow. The arithmetic mean of per‑jitter‑point values uses the same signed half‑to‑even rounding convention as the per‑block mean.

Averaging signed drift values across jitter points may result in cancellation when the drift oscillates symmetrically within the window. This is physically meaningful: a candidate whose jitter window straddles a drift reversal genuinely has no net directional bias, and a zero mean accurately reflects that. The `drift_max` and `drift_min` fields preserve the extremes, so the full excursion envelope remains available for analysis.

## 5. Storage

### 5.1 Drift in the Extended `.gunzstats` File

Drift values are stored in the extended `.gunzstats` file defined by GUNZ 3.67.0 §4.8.  The file begins with a 4‑byte magic number `0x475A4C02` (little‑endian), followed by a 4‑byte little‑endian `candidate_count` giving the total number of records in the file.  This is the **only** valid magic for `.gunzstats` files.  A conformant decoder shall reject any `.gunzstats` file whose magic is not `0x475A4C02` with `GUNZ_MALFORMED_BYTECODE`.

The total file size in bytes is `8 + candidate_count × 32`.

The format uses **32‑byte records** with the following layout:

| Offset | Size | Field | Description |
|--------|------|-------|-------------|
| 0  | u32 | `block_count` | Number of temporal blocks evaluated. |
| 4  | u64 | `sum_block_time` | Sum of block times (base time units). |
| 12 | u64 | `sum_block_time_sq` | Sum of squared block times. |
| 20 | u16 | `count_adv_lo` | Number of short advances. |
| 22 | u16 | `count_adv_hi` | Number of long advances. |
| 24 | s16 | `drift` | Intra‑block drift, averaged across the jitter window and measurement window (ticks × 100 per cycle).  Zero if drift is not enabled or `N < 2`. |
| 26 | s16 | `drift_max` | Most positive (or least negative) drift value observed among all jitter points and blocks (ticks × 100 per cycle). |
| 28 | s16 | `drift_min` | Most negative (or least positive) drift value observed among all jitter points and blocks (ticks × 100 per cycle). |
| 30 | u16 | `reserved` | Reserved.  Must be written as zero by current encoders.  Decoders shall ignore this field; it is not part of the compression stream. |

All time values are in the base time unit.  The number of records equals the total number of candidates evaluated.

The `.gunzstats` file is emitted for any scan mode when drift computation is requested, not only when `long_term_scan` is active.  For single‑block scans, the `block_count` field is `1`, and the `drift`, `drift_max`, and `drift_min` fields contain the per‑candidate drift values after aggregation across the jitter window.

### 5.2 Compressed Statistics File (`.gunzstatz`)

The compressed `.gunzstatz` file uses the same 32‑byte record structure and a **distinct magic number `0x475A4C03`**.  The file begins with `0x475A4C03` (little‑endian), followed by the `candidate_count`, `anchor_freq_raw`, and the 32‑byte anchor record.  A conformant decoder shall reject any `.gunzstatz` file whose magic is not `0x475A4C03` with `GUNZ_MALFORMED_BYTECODE`.

The delta‑compression bitmask uses bits 0‑7 as follows:

| Bit | Field |
|-----|-------|
| 0 | `block_count` |
| 1 | `sum_block_time` |
| 2 | `sum_block_time_sq` |
| 3 | `count_adv_lo` |
| 4 | `count_adv_hi` |
| 5 | `drift` |
| 6 | `drift_max` |
| 7 | `drift_min` |

The `reserved` field is **not** delta‑compressed; the decompressor shall set it to zero after reconstructing a record.  (If a future extension repurposes these two bytes, the compression bitmask will be extended accordingly.)

### 5.3 Metadata

The `.gunzmeta` file shall include the following additional field when drift is computed:

| Key | Type | Description |
|-----|------|-------------|
| `drift_enabled` | boolean | `true` if the drift metric was computed. |

The `.gunzmeta` field `stats_fingerprint` shall cover the extended `.gunzstats` file, as always.

## 6. Relationship to Other Metrics

- **`advance_regularity`** measures the variance of per‑cycle advance values.  Drift measures the *slope*.  Together they provide a complete description of the distribution and ordering of long cycles within a block.
- **`jitter`** measures block‑time variation across the jitter window.  Drift is an intra‑block metric and is orthogonal to jitter.
- **`stability_width`** describes the width of the score valley.  Drift does not affect the score unless explicitly weighted into a custom scoring formula.

---

## 7. Integration with the Snowball Metaphor

The snowball rolls within a single block.  The sequence of per‑cycle advances is a trajectory, and the slope of that trajectory is the intra‑block drift.  A block whose long cycles cluster at the end is a snowball that accelerates as it rolls.  A block whose long cycles cluster at the beginning is a snowball that decelerates.  The drift metric captures this internal movement, making the snowball visible at the scale where it currently exists — inside the block.

## 8. Conformance

A conformant GUNZ‑DRIFT implementation must:

- Compute drift using the exact least‑squares formula defined in §2, with 256‑bit intermediates for `sum_a`, `sum_ia`, `num`, and `den`.
- Use a 128‑bit signed accumulator for the long‑term mode and jitter‑window aggregation (§4).
- Apply half‑to‑even rounding to the final division, using the signed rounding convention specified in §2.
- Produce the per‑cycle advance sequence using the placement algorithm of §2.1, with the initial error `E` derived from `rem = (N * T) % quantum` as specified, using the unrounded continuous block time `P = N * T`.
- For each candidate frequency, compute per‑block drift values at every valid jitter offset, aggregate per‑jitter‑point values in long‑term mode as the arithmetic mean, and then aggregate per‑jitter‑point values across all valid jitter points as the arithmetic mean (`drift`), maximum (`drift_max`), and minimum (`drift_min`), using at least 128‑bit signed accumulation and the signed half‑to‑even rounding convention of §2.
- Saturate the drift result to a signed 16‑bit integer before storage.
- Produce bit‑identical drift values for identical inputs.
- Emit the `.gunzstats` file with magic `0x475A4C02` and the 8‑byte header (`magic` + `candidate_count`) followed by 32‑byte records when drift is computed, for any scan mode.
- Reject any `.gunzstats` file whose magic is not `0x475A4C02` with `GUNZ_MALFORMED_BYTECODE`.
- Reject any `.gunzstatz` file whose magic is not `0x475A4C03` with `GUNZ_MALFORMED_BYTECODE`.
- Record `drift_enabled = true` in `.gunzmeta`.
- Compute `drift_max` as the maximum drift value across all jitter points and blocks, and `drift_min` as the minimum drift value across all jitter points and blocks (both signed, preserving original sign).
- If producing compressed `.gunzstatz`, write the magic `0x475A4C03` as the first four bytes.  Reject any `.gunzstatz` file with a different magic.

Support for GUNZ‑DRIFT is **optional** for GUNZ 3.67.0 conformance.  Implementations that do not support the drift extension shall write zero in the `drift`, `drift_max`, and `drift_min` fields and set `drift_enabled = false` (or omit the field) in `.gunzmeta`.  The `.gunzstats` file format (magic `0x475A4C02`) is mandatory when statistics are emitted.

## 9. Examples

### 9.1 Non‑Trivial Drift

Consider two frequencies that produce identical `N = 10`, `N_hi = 3`, `d_lo_cont = 5`, `d_hi_cont = 6` (in ticks, before scaling).  Their `jitter` and `advance_regularity` are identical.  However, because `T` differs by a fraction of a quantum, the continuous remainder `rem` differs, producing different initial errors:

- **Case A:** `rem` is small.  `E` is small.  The Bresenham algorithm places long cycles at indices 2, 5, 8.  
  Drift ≈ +17.3.  `drift_max = +17.3`, `drift_min = +17.3` (single‑block mode, single jitter point).

- **Case B:** `rem` is large.  `E` is close to `N-1`.  The Bresenham algorithm places long cycles at indices 0, 3, 6.  
  Drift ≈ −17.3.  `drift_max = −17.3`, `drift_min = −17.3`.

If these two cases occur at different jitter offsets of the same candidate, the per‑jitter‑point values are `+17.3` and `−17.3`.  The per‑candidate `drift` (arithmetic mean) is zero, indicating no net directional bias, while `drift_max = +17.3` and `drift_min = −17.3` capture the full oscillation envelope.  The velocity `drift_max − drift_min = 34.6` quantifies the total directional swing within the jitter window.

### 9.2 Zero Drift

When `rem = 0`, the continuous block time is an exact multiple of the quantum.  The initial error is `E = 0`, the Bresenham algorithm produces a perfectly alternating pattern, and drift is zero.  All three fields are zero.
