# GUNZ‑DRIFT 1.3.3 — Intra‑Block Advance Trend Metric Extension  
*Companion to GUNZ 3.81.0 (96‑byte `.gunzstats` format)*

## 1. Overview

GUNZ‑DRIFT extends the GUNZ resonance evaluator with a directional **drift** metric that captures the *intra‑block* accumulation of rounding decisions.  Unlike `advance_regularity`, which measures the variance of per‑cycle advances without regard to order, drift measures the **slope** of those advances across the cycles of a single block.

A positive drift means the per‑cycle advance increases over the course of a block (long cycles cluster toward the end).  A negative drift means the advance decreases (long cycles cluster toward the beginning).  A drift of zero indicates that the long and short cycles are uniformly distributed throughout the block.

This metric reveals a dimension of timing behaviour that the existing metrics are blind to — the direction in which rounding decisions accumulate within a block, independent of their magnitude.  It requires no new simulation infrastructure and is computed from data the evaluator already collects.

**Integration philosophy.**  Drift is stored in the extended **`.gunzstats`** companion file, not inside the map entry.  The map entry remains the standard 16‑byte structure defined in GUNZ 3.80.0 §4.2.  No custom map version is required.  The extension is entirely in the optional statistics companion file and the `.gunzmeta` metadata.  Tools that require drift must read the companion statistics file; the `.gunzmap` alone does not contain this metric.

## 2. Definition

Let a block consist of `N` cycles.  Each cycle `i` (0‑based) contributes an advance value `a_i` of either `100 × adv_lo` or `100 × adv_hi` (ticks × 100), determined by the placement logic defined in §2.1.

The **intra‑block drift** `d` is the slope of the linear least‑squares fit of `a_i` against the cycle index `i`.

\[
d = \frac{N \cdot \sum (i \cdot a_i) - (\sum i) \cdot (\sum a_i)}{N \cdot \sum (i^2) - (\sum i)^2}
\]

where all sums run from `i = 0` to `N-1`.

Because the cycle indices form a known arithmetic progression, the sums of `i` and `i^2` have closed forms:

\[
S_i = \frac{N(N-1)}{2}, \qquad S_{i^2} = \frac{N(N-1)(2N-1)}{6}
\]

The normative computation is:

```
sum_a   = Σ a_i          (256‑bit unsigned)
sum_ia  = Σ (i · a_i)    (256‑bit unsigned)
num     = N · sum_ia − S_i · sum_a    (signed, may be negative)
den     = N · S_{i^2} − (S_i)²        (positive for N ≥ 2)
```

The absolute quotient `q = |num| / den` is computed using the half‑to‑even integer division defined in §4.5.1 of the core GUNZ specification (which applies to non‑negative operands).  The rounded drift value is:

```
d =  q  if num ≥ 0
d = −q  if num < 0
```

Equivalently, for negative numerators the tie‑breaking rule is: if the exact quotient lies exactly halfway between two integers, round to the even integer.  Examples: `−1.5 → −2`, `−0.5 → 0`, `−2.5 → −2`.

All multiplications shall use **256‑bit unsigned arithmetic** to prevent overflow.  The denominator is guaranteed to be positive for `N ≥ 2`.  For `N < 2`, drift is defined as **zero**.

The drift value `d` is a signed integer expressed in **ticks × 100 per cycle**.  It is **not** converted to base time units for storage; the conversion to base time units, if needed for scoring, follows the same pattern as for `advance_regularity` (§3.11 step 4 of the core specification).  Before storage, the computed drift is saturated to the signed 16‑bit integer range `[−32768, 32767]`.

### 2.1 Per‑Cycle Advance Sequence (Normative)

The evaluator determines `N_hi` — the number of long cycles in the block — by rounding `N * T / quantum` according to the selected `round_mode`.  This value is computed in §3.11 step 3 of the core specification and is **not** recomputed by the drift algorithm.  The drift metric must assign the long advances to exactly `N_hi` cycles in a pattern that is consistent with the evaluator's own computation but also sensitive to the continuous frequency.

The placement is performed by a deterministic Bresenham‑style error‑accumulation algorithm.  The algorithm guarantees exactly `N_hi` long cycles by construction, so the total block time and `advance_regularity` are unchanged.  The ordering of those long cycles depends on the continuous cycle time `T` through a phase offset derived from the continuous remainder of the block time, giving drift its discriminative power.

The drift metric uses the **continuous advances** `adv_lo_cont` and `adv_hi_cont` as defined in §3.11 step 3 of the core specification, regardless of whether an explicit delta override is active.  If a delta override is active, the override values `d_lo_ov`, `d_hi_ov` do **not** affect the drift sequence; the drift sequence is always derived from the continuous advances.  This is because drift measures the directional ordering of long‑cycle placement, which is determined entirely by the fractional timing of the continuous cycle time `T`.  The override changes the *magnitude* of each cycle's advance but not *which* cycles are long; the temporal pattern of long cycles is invariant under the override.

**Initialisation:**

Let `P = N * T` (the continuous block time before rounding, in base time units, computed using 128‑bit unsigned arithmetic).  The continuous remainder `rem` is:

    rem = P % quantum    (0 ≤ rem < quantum)

The continuous remainder `rem` is computed from the **unrounded** continuous block time `P = N * T`, not from the rounded block time `R`.  The `round_mode` affects `N_hi` but does not affect the drift placement.

The phase offset `E` is derived from the continuous remainder:

    E = (rem * N) / quantum    (integer division, floor)

The product `rem × N` shall be computed using **128‑bit unsigned arithmetic** before division by `quantum`.  Since `rem < quantum`, the product is at most `(quantum − 1) × N`, and the result `E` is guaranteed to be in the range `[0, N-1]`.

*Rationale:* deriving `E` from the continuous remainder ensures that the drift placement varies with the fractional timing of the block, capturing the directional information.  The Bresenham algorithm produces exactly `N_hi` long cycles for any initial error in `[0, N-1]`; the choice of `E` does not affect `N_hi` or any other evaluator metric, only the order of the long cycles.

**Bresenham placement loop** (for `i = 0` to `N-1`):

```
error = E
for i = 0 to N-1:
    error = error + N_hi
    if (error >= N):
        a_i = 100 × adv_hi
        error = error - N
    else:
        a_i = 100 × adv_lo
```

The resulting sequence `a_0, …, a_{N-1}` contains exactly `N_hi` long cycles (value `100 × adv_hi`) and `N − N_hi` short cycles (value `100 × adv_lo`).  The ordering is deterministic and varies with the fractional timing of the block.

**Properties:**

- When `rem = 0`, the continuous block time is an exact multiple of the quantum.  The initial error is `E = 0`, and the resulting pattern is the most uniform distribution of long cycles.  Drift will be zero (or very close to zero).
- As `rem` increases toward `quantum`, the initial error approaches `N-1`, producing a front‑loaded or back‑loaded pattern.  The drift formula will detect this as a non‑zero slope.

All intermediate computations shall use **128‑bit unsigned arithmetic** where required to avoid overflow.  The resulting sequence is bit‑identical for all conformant implementations given identical inputs.

The drift metric depends on the effective quantum value used by the evaluator, which is guaranteed to be `≥ 1` after parameter merging (§3.10 of the core specification).

**Jitter‑window scope.** The drift computation is performed for every valid jitter offset `Δ` in the jitter window. For each offset, the cycle time `T_jitter` is computed from the offset frequency `freq_candidate + Δ`, and the block parameters (`N`, `N_hi`) are derived from `T_jitter` exactly as described in §3.11 of the core GUNZ specification. The per‑jitter‑point drift values are then aggregated into the candidate‑level metrics `drift`, `drift_max`, and `drift_min` as defined in §4.

## 3. Interpretation

| Drift value | Meaning |
|-------------|---------|
| `d = 0` | Uniform distribution of long cycles.  No directional bias. |
| `d > 0` | Long cycles cluster toward the **end** of the block (advance increases). |
| `d < 0` | Long cycles cluster toward the **beginning** of the block (advance decreases). |

The magnitude of `d` is the average change in advance value per cycle, in ticks × 100.

Drift is independent of `advance_regularity`.  Two blocks with identical per‑cycle advance variance can have opposite drift if the long cycles are ordered differently.  Drift provides the directional information that variance discards.

---

## 4. Aggregation Across Jitter Points and Temporal Blocks

For each candidate frequency, the evaluator computes a per‑block drift value `d_j(Δ)` for every valid jitter offset `Δ` as defined in §2, using the block parameters (`N`, `N_hi`, `T_jitter`) that apply at that offset.

**Per‑jitter‑point aggregation (long‑term mode).** When `long_term_scan` is active, the per‑block drift values at a single jitter offset are averaged to obtain the per‑jitter‑point drift `d(Δ)`:

\[
d(Δ) = \frac{1}{B} \sum_{j=0}^{B-1} d_j(Δ)
\]

where `B` is the number of blocks evaluated at that jitter offset. The mean is rounded half‑to‑even using the signed convention of §2. In single‑block mode, `d(Δ) = d_0(Δ)` for the single block.

**Per‑candidate aggregation.** The per‑candidate drift values are obtained by aggregating the per‑jitter‑point values `d(Δ)` across all valid jitter points:

- `drift` — the arithmetic mean of all `d(Δ)` across all valid jitter points, rounded half‑to‑even (signed). If the jitter window contains only one valid point, `drift` equals `d(0)`.
- `drift_max` — the maximum value of `d(Δ)` observed over all jitter points (most positive, or least negative if all values are negative).
- `drift_min` — the minimum value of `d(Δ)` observed over all jitter points (most negative, or least positive if all values are positive).

All summations shall use at least **128‑bit signed** accumulation to prevent overflow. The arithmetic mean of per‑jitter‑point values uses the same signed half‑to‑even rounding convention as the per‑block mean.

**Drift velocity.**  The **drift velocity** for a candidate is defined as:

```
drift_velocity = drift_max − drift_min
```

Because `drift_max` and `drift_min` are stored as `s16`, the subtraction may overflow a signed 16‑bit integer.  **Implementations shall promote both operands to signed 32‑bit integers (`s32`) before subtraction, then clamp the result to the range `[0, 65535]` and store it as a `u16`.**  The result is guaranteed to be non‑negative because `drift_max ≥ drift_min` by definition.

A small velocity indicates that the drift is stable across the jitter window; a large velocity indicates that the directional bias oscillates strongly, which may signal a fragile, knife‑edge operating point.

**Drift confidence.**  The number of valid jitter points `valid_jitter_points` that contributed to the aggregates is already stored in the `.gunzstats` record.  The **drift confidence** is the ratio `valid_jitter_points / maximum_jitter_points`, where `maximum_jitter_points` is the total number of jitter offsets before any are skipped, computed as:

```
maximum_jitter_points = 2 × (jitter_window_radius / 1000) + 1
```

For the default radius of 10000, this yields 21.

The per‑candidate confidence is rounded half‑to‑even to the nearest integer percentage.  The scan‑level `drift_confidence_min` is the minimum of those rounded values across all candidates.  A low confidence indicates that the drift aggregates were computed from a reduced jitter window (e.g., near the low‑frequency limit).

**Per‑block drift extremes (long‑term mode only).**  In addition to the per‑jitter‑point aggregates, the evaluator **MAY** track the absolute maximum and minimum per‑block drift values across all blocks and all jitter points, before any averaging.  These are stored as **global scan‑level summaries** in the `.gunzmeta` file (see §5.3), not per candidate.  They provide a raw envelope of the most extreme instantaneous drift seen during the entire measurement window.

*(Informative)* **Aggregation scope note:** Because `d(Δ)` is the average over all blocks at a given jitter offset, `drift_max` and `drift_min` reflect the extremes *across the jitter window*, not the raw per‑block extremes.  The global per‑block extremes `drift_block_extremes` in `.gunzmeta` fill this gap.  A single very large per‑block drift value may not appear in the per‑jitter‑point aggregates, but it will be visible in these scan‑level summaries.

Averaging signed drift values across jitter points may result in cancellation when the drift oscillates symmetrically within the window. This is physically meaningful: a candidate whose jitter window straddles a drift reversal genuinely has no net directional bias, and a zero mean accurately reflects that. The `drift_max` and `drift_min` fields preserve the extremes, so the full excursion envelope remains available for analysis.

## 5. Storage

### 5.1 Drift in the Extended `.gunzstats` File

Drift values are stored in the `.gunzstats` companion file defined by GUNZ 3.81.0 §4.8.  The file uses a **96‑byte** record format with magic number `0x475A4C04`.  The drift fields occupy the following offsets within each record:

| Offset | Field | Description |
|--------|-------|-------------|
| 48 | `drift` (s16) | Per‑candidate drift, averaged across jitter and measurement windows. |
| 50 | `drift_max` (s16) | Maximum per‑jitter‑point drift. |
| 52 | `drift_min` (s16) | Minimum per‑jitter‑point drift. |
| 54 | `valid_jitter_points` (u16) | Number of valid jitter offsets for this candidate. |

These offsets are unchanged from previous versions of this extension.  The additional fields introduced by GUNZ 3.81.0 — `advance_regularity_full` at offset 56, and the total block‑time sums at offsets 64 and 80 — lie outside the drift region and do not affect drift storage.

For the compressed variant `.gunzstatz`, see §5.2.

The file is emitted for any scan mode when drift computation is requested.  For single‑block scans, `block_count = 1` and the drift fields contain the per‑jitter‑point aggregates as defined in §4.

### 5.2 Compressed Statistics File (`.gunzstatz`)

The compressed `.gunzstatz` file is defined in GUNZ 3.81.0 §4.9.  It uses the same 96‑byte record structure and magic number `0x475A4C05`.  The delta‑compression bitmask is a little‑endian `u16` with 14 active bits (bits 0‑13); the drift fields are encoded at the following bits:

| Bit | Field |
|-----|-------|
| 7 | `drift` |
| 8 | `drift_max` |
| 9 | `drift_min` |

Bits 10‑13 are defined by the core specification (bit 10 = `valid_jitter_points`, bits 11‑13 = `advance_regularity_full`, `sum_total_block_time`, `sum_total_block_time_sq`).  Bits 14‑15 are reserved and must be zero.  DRIFT 1.3.3 does not use any additional bits; the bitmask is fully compatible with the core specification.

### 5.3 Metadata

The `.gunzmeta` file shall include the following additional fields when drift is computed.  All are optional; an implementation that does not compute a particular metric shall omit the corresponding field.

| Key | Type | Description |
|-----|------|-------------|
| `drift_enabled` | boolean | `true` if the drift metric was computed. |
| `drift_velocity_max` | integer | The maximum drift velocity (`drift_max − drift_min`) observed across all candidates in the scan.  A large value indicates the presence of a fragile operating point with strongly oscillating directional bias. |
| `drift_confidence_min` | integer (0‑100) | The minimum drift confidence (percentage of valid jitter points) among all candidates in the scan.  Low values indicate that part of the scan operated with a reduced jitter window. |
| `drift_block_extremes` | object | (Optional) Global per‑block drift extremes for the entire scan.  Present only when long‑term scan is active and the implementation records per‑block extremes.  The object contains: <br> – `max` (integer, s16 range): the most positive (or least negative) per‑block drift value observed anywhere in the scan. <br> – `min` (integer, s16 range): the most negative (or least positive) per‑block drift value observed anywhere in the scan. <br> If no per‑block extremes are recorded, this key is omitted. |
| `drift_fragile_candidates` | integer | (Optional) Number of candidates whose drift velocity exceeded the fragility threshold. |
| `drift_fragility_threshold` | integer | (Optional) The velocity threshold used to flag candidates as fragile. Present only when fragility detection is active. |

The `.gunzmeta` field `stats_fingerprint` shall cover the extended `.gunzstats` file, as always.  The `.gunzmeta` fields added by DRIFT do not affect the fingerprint.

## 6. Drift‑Aware `PURE_CALL` (Optional)

The GUNZ 3.81.0 specification allows a `PURE_CALL` callback attached to a `ZONE` to inspect and modify the candidate’s metrics.  When drift is enabled, a **drift‑aware** callback may also read the per‑candidate drift fields to influence its decisions.

### 6.1 Library Profile Extension

To declare a callback as drift‑aware, the library profile **SHALL** include an additional field `drift_aware` with the value `true` in the callback’s definition:

```json
{
  "callback_id": 1,
  "output_size": 40,
  "drift_aware": true
}
```

If `drift_aware` is absent or `false`, the callback is treated as a standard `PURE_CALL` and the drift fields are not populated.

### 6.2 Extended Candidate Context Buffer

When a drift‑aware callback is invoked, the runtime **SHALL** write the per‑candidate drift fields into the `output` buffer immediately after the standard 24‑byte candidate context structure, before zero‑filling any remaining bytes.  The extended layout is:

| Offset | Size | Field | Description |
|--------|------|-------|-------------|
| 0‑23 | 24 bytes | Standard candidate context | As defined in GUNZ 3.81.0 §3.11 step 5. |
| 24 | s16 | `drift` | Per‑candidate drift (saturated). |
| 26 | s16 | `drift_max` | Maximum per‑jitter‑point drift. |
| 28 | s16 | `drift_min` | Minimum per‑jitter‑point drift. |
| 30 | u16 | `drift_velocity` | `drift_max − drift_min`, computed with 32‑bit promotion and clamped to `[0, 65535]` as described in §4. |
| 32 | u16 | `valid_jitter_points` | Number of valid jitter offsets. |
| 34 | u16 | `reserved` | Zero. |
| 36‑… | variable | Scratch space | Zero‑filled up to `output_size − 1`. |

The total extended context is 36 bytes.  The callback **SHALL NOT** modify any of the drift fields; they are read‑only.

The library profile’s `output_size` for a drift‑aware callback **SHALL** be at least 36 bytes.  Plan construction shall fail with `GUNZ_INVALID_LIBRARY` if a drift‑aware callback is bound to a `ZONE` and its `output_size` is smaller than 36.

### 6.3 Fragility Flag (Optional)

If the runtime or the callback determines that the drift velocity exceeds a configured **fragility threshold**, it **MAY** record this in the `.gunzmeta` file.  The fragility threshold, if used, shall also be recorded (see §5.3).

## 7. Relationship to Other Metrics

- **`advance_regularity`** measures the variance of per‑cycle advance values.  Drift measures the *slope*.  Together they provide a complete description of the distribution and ordering of long cycles within a block.
- **`jitter`** measures block‑time variation across the jitter window.  Drift is an intra‑block metric and is orthogonal to jitter.
- **`stability_width`** describes the width of the score valley.  Drift does not affect the score unless explicitly weighted into a custom scoring formula.
- **Drift velocity** and **drift confidence** are summary statistics derived from the drift fields; they are intended for use by downstream analysis tools such as DEWASTER and AUTOTUNE.

---

## 8. Conformance

A conformant GUNZ‑DRIFT 1.3.3 implementation must:

- Compute per‑block drift using the Bresenham placement algorithm (§2.1) with the phase offset derived from the continuous remainder.  The product `rem × N` must use 128‑bit arithmetic; the drift formula must use 256‑bit accumulators; per‑block drift values must be saturated to `s16`.
- Aggregate per‑block drift across jitter points and temporal blocks exactly as described in §4, producing `drift`, `drift_max`, and `drift_min` per candidate.
- Store drift fields in the 96‑byte `.gunzstats` record at offsets 48‑55, with all other fields conforming to GUNZ 3.81.0 §4.8.
- Support the compressed `.gunzstatz` format (§5.2) using the specified bitmask bits; reserved bits 14‑15 must be zero.
- When drift is enabled, record `drift_enabled = true` in `.gunzmeta` together with any of the optional metadata fields described in §5.3 that are computed.
- Compute drift velocity as `(s32)drift_max − (s32)drift_min`, clamped to `[0, 65535]` and stored as `u16`.  The scan‑level `drift_velocity_max` and `drift_confidence_min` may also be recorded in `.gunzmeta`.
- If drift‑aware `PURE_CALL` is supported, populate the extended candidate context buffer (§6.2) for callbacks marked `drift_aware`, and reject plans where the callback’s `output_size` is less than 36 bytes.
- All other standard GUNZ 3.81.0 requirements for statistics emission and metadata remain unchanged.

Support for GUNZ‑DRIFT is **optional** for GUNZ 3.81.0 conformance.  Implementations that do not support drift shall write zero in the drift fields and set `drift_enabled = false` (or omit the field) in `.gunzmeta`.

## 9. Examples

### 9.1 Non‑Trivial Drift with Velocity

Consider a candidate with two valid jitter points:

- Point A: drift = +18
- Point B: drift = −18

Then `drift = 0`, `drift_max = +18`, `drift_min = −18`, and `drift_velocity = 36`.

If this candidate was evaluated in long‑term mode with two blocks at point A and two blocks at point B, and the per‑block drift values were [+20, +16] at A and [−17, −19] at B, then the global per‑block extremes would be `drift_block_extremes.max = +20` and `drift_block_extremes.min = −19`, recorded in `.gunzmeta`.

The velocity of 36 indicates that the directional bias swings strongly within the jitter window — a potential fragility signal — even though the net drift is zero.

### 9.2 Zero Drift

When `rem = 0`, drift is zero at every jitter point.  All drift fields are zero, velocity is zero, and per‑block extremes (if recorded) are zero.
