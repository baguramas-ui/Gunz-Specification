**GUNZ 3.26 — Performance Implementation Guide (Informative)**  

*How to build a high‑performance, conformant GUNZ dense scanner — safely and deterministically.*

---

## 1. Why performance matters

A typical AI‑driven tuning session may evaluate millions of frequency candidates across multiple zones and time‑unit scales. The core evaluator is the hot path; every microsecond saved there translates directly into faster feedback loops, lower energy consumption, and more responsive autonomous systems.

The techniques described in this guide can accelerate the dense scanner by **10–500×** while remaining **bit‑identical** to a naïve implementation. No approximations, no guesswork — only intelligent exploitation of the evaluator’s deterministic structure.

---

## 2. Fundamental rule

> **Any optimisation that changes a single bit of the output map is non‑conformant.**  
> The GUNZ resonance evaluator is a pure function. Its output is fully determined by the input parameters and the dense‑scan frequency grid. The goal is to compute that exact output with less work, not to compute something “close enough.”

### 3.1 Plateau‑jump — skip only when the entire jitter window is safe

#### Why it works

The block‑time of a single frequency is piecewise‑constant over intervals where both the integer cycle count `N` and the hi‑delta count `N_hi` are constant.  
However, the **jitter** — the standard deviation of 21 nearby frequencies — can change when the sliding window straddles a boundary between two such intervals.

Therefore, the score is constant **only** for candidates whose entire jitter window (all 21 offsets) lies within the same constant‑`N`/`N_hi` region.  
Inside a plateau of width `W` steps, the interior candidates that are at least `R = jitter_window_radius` steps from either edge satisfy this condition. Their 21 jitter points all yield the same block times, so jitter, advance regularity, and score are identical. They can be safely merged.

#### How to implement

1. **Enumerate constant‑`N`/`N_hi` intervals** over the whole zone using closed‑form inequalities (see below).
2. For each interval of width `W` (in frequency steps):
   - **Left edge zone** — evaluate every candidate from the interval start up to `R‑1` steps, inclusive.
   - **Interior** — if `W ≥ 2R+1`, choose the centre candidate, evaluate it **once**, and emit a single map entry with `run_length = W − 2R`. Do not evaluate the remaining interior points.
   - **Right edge zone** — evaluate the last `R` candidates step by step.
3. Continue to the next interval.

This respects the jitter window and guarantees bit‑identical output.

#### Computing the interval boundaries

The constant‑`N`/`N_hi` intervals are those where both `d_lo_cont` and `N_hi` remain unchanged.  
The boundary occurs where `round(N * T / quantum)` steps to the next integer, which depends on the active `round_mode`. A conformant implementation pre‑computes all such transition frequencies at plan‑construction time using integer arithmetic.

*(Note: The companion anti‑spec `UNSOLVE` intentionally ignores these transitions — here we **must** include them.)*

### 3.2 Per‑frequency block‑data cache + sliding‑window jitter

#### Why it works

Instead of recomputing the heavy block simulation for each jitter point of every candidate, we evaluate it **once per distinct frequency** and store the results.  
Because the jitter offsets are fixed at multiples of 1000 (in \(10^{-5}\,\text{Hz}\)) and the dense‑scan grid is integer, a cache resolution of **1** (the finest grid) guarantees that every jitter point lies exactly on a cached index. For each candidate, the 21 jitter values become a simple array look‑up.

#### How to implement — with plateau‑aware cache filling

A naïve cache would simulate every integer step, wasting work. We combine plateau logic:

1. **Enumerate plateaus** — the same constant‑`N`/`N_hi` intervals used in §3.1.
2. **For each plateau:**
   - Run the heavy block simulation **once** at any interior frequency. This yields the `block_time` and `advance_reg_raw` valid for the entire plateau.
   - Fill the pre‑allocated cache array for the plateau’s frequency range with those two constant values. A simple `memset` or tight loop is sufficient.
3. **The cache is now complete.** The number of heavy simulations equals the number of plateaus — typically a few hundred instead of millions.
4. **Sliding‑window jitter** proceeds as usual: for each candidate at index `i`, look up the 21 pre‑computed values (indices `i‑10000`, `i‑9000`, …, `i+10000`), compute population standard deviation and mean advance regularity (using SIMD if desired), then derive score and stability width.

#### Memory note

For a 100 Hz zone at resolution 1, the cache requires about 80 MB (10 million entries × 8 bytes), well within the capacity of modern hardware. If memory is constrained, a GCD‑based grid can shrink the cache at the cost of slightly more complex indexing.

### 3.3 Closed‑form advance regularity

The core specification permits computing advance regularity for a two‑valued multiset using the algebraically identical closed form:

```text
scaled_lo = 100 * adv_lo
scaled_hi = 100 * adv_hi
diff      = scaled_hi - scaled_lo

num = N_lo * N_hi * diff * diff
den = (N_lo + N_hi) * (N_lo + N_hi)

var = round_half_even(num, den)      // §4.5.1 – use half‑to‑even, not truncation
advance_reg_raw = isqrt_rounded(var)
```

The result is saturated to 65535.  
This formula avoids looping over individual cycles and is the **recommended** implementation.

---

### 3.4 SIMD vectorisation of the jitter window

With block‑times stored in a flat array, the 21‑value standard‑deviation computation is easy to vectorise. Use integer SIMD (AVX2, NEON) to load multiple block times and accumulate sums and sums‑of‑squares in wide (128‑bit or 256‑bit) integer registers.

Because all arithmetic is exact integer, addition is associative and commutative; the SIMD reduction order does not affect the final result. No special ordering is required.

---

### 3.5 Narrow integer arithmetic (64‑bit paths)

If static range analysis at plan‑construction time proves that all intermediate products fit in 64 bits, native 64‑bit operations may be used instead of extended precision. This can give a modest speed‑up, especially on platforms where 128‑bit software emulation is slow.

The analysis simply checks the maximum possible `N`, `T`, and multiplier values against the zone boundaries.

## 4. What **not** to do — the anti‑optimisations

The following shortcuts are tempting but produce **non‑conformant** maps. They are documented here so you never implement them.

### 4.1 Re‑using the candidate’s block time for all jitter points
Each jitter offset changes the frequency, which changes the block time. Assuming they are all equal is mathematically false and yields incorrect jitter values.

### 4.2 Linear interpolation of block times
Block time is not a smooth function; it’s piecewise‑constant with discrete jumps. Interpolation will miss transitions and invent non‑existent plateaus.

### 4.3 Reducing the jitter window size
The spec defines the window radius; using fewer points alters the standard deviation and breaks conformance.

### 4.4 Using floating‑point arithmetic
Floating‑point rounding is platform‑dependent and non‑deterministic. All arithmetic must be integer.

### 4.5 Any “oracle” that ignores `N_hi` transitions
As the companion document `GUNZ‑UNSOLVE` illustrates in detail, skipping the enumeration of `N_hi` integer‑crossing points (or `N * T / quantum` boundaries) leads to maps that are **grossly inaccurate**. The only safe way to avoid a full step‑by‑step scan is the window‑aware plateau‑jump described in this guide.

## 5. Putting it all together — the final scan pipeline

1. **Plan construction**  
   - Compute all constant‑`N`/`N_hi` interval boundaries for the zone.  
   - Perform static range analysis; decide between 64‑bit and 128‑bit arithmetic.

2. **Phase 1 — Build the full‑resolution block‑data cache**  
   - For each plateau, simulate one representative frequency, then fill the corresponding array segment with the resulting `block_time` and `advance_reg_raw`.  
   - The array covers every integer frequency step from `freq_low` to `freq_high`.

3. **Phase 2 — Candidate evaluation (sliding window)**  
   - Use the window‑aware plateau‑jump rules from §3.1: evaluate edge zones step‑by‑step; for each safe interior, evaluate one candidate and emit a merged entry.  
   - For every evaluated candidate, read the 21 pre‑computed values from the cache, compute jitter and advance regularity (SIMD‑accelerated if available), then calculate score and stability width.

4. **Phase 3 — Map emission**  
   - Apply run‑length consolidation, long‑jump sentinels, sparse merging, and the XXH3‑64 checksum as specified.
