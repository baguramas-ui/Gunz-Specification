# GUNZ Adaptive Orchestration Patterns *(Informative Companion)*

**Version:** 2.1 — Companion to GUNZ 3.81.0  
**Status:** Informative, non‑normative  
**Purpose:** Describe idiomatic patterns for using static resonance maps as building blocks for dynamic, condition‑aware system tuning.

---

## 1. Introduction

GUNZ produces immutable, deterministic resonance maps. A map is a perfect snapshot of timing stability for one set of parameters and one environmental state. By itself, a map does not adapt. **Adaptive behaviour is parametrable by an external orchestrator** — a human operator, an AI agent, or a runtime monitor — that decides *when* to consult a map, *which* map to use, and *when* to commission a new scan.

This guide collects patterns that exploit the map format’s features (fingerprints, session chains, calibrated references, companion statistics, and the bytecode ISA) to build responsive, self‑tuning systems. All patterns are non‑normative; they describe *how* one might use GUNZ, not *what* must be implemented.

---

## 2. Building a Library of Environmental Maps

Different operating conditions (temperature, supply voltage, CPU load, clock drift) can shift the resonance landscape. An orchestrator can pre‑compute maps for a set of representative conditions and store them in a map library.

**How to do it:**

1. Identify the varying environmental parameter (e.g., CPU temperature range 20 °C to 85 °C).
2. For each target condition, run the same bytecode program with an appropriate `session_id` and tag the `.gunzmeta` with the condition (you may use the `system_info` object or a custom extension).
3. Record the XXH3‑128 fingerprint of each map.
4. At runtime, monitor the environmental parameter. When it crosses a threshold, load the pre‑computed map whose conditions most closely match the current state.

**GUNZ features used:** Fingerprint for deduplication, `session_id` for grouping, `.gunzmeta` for storing context.

## 3. Map Overlay and Comparison

You can overlay multiple maps to find frequency ranges that are stable under *all* tested conditions — a “safe intersection” zone.

**Overlay via `JOIN` (pessimistic intersection):**  
Use the `JOIN` opcode to intersect two maps. The resulting map uses pessimistic merging: where both inputs have evaluated data, the worst (maximum) of jitter and advance regularity is taken; where one side has perfect‑resonance sparse intervals and the other has evaluated data, the evaluated data is preserved. Gaps appear only where both inputs lack evaluated data. Since `JOIN` takes the maximum of jitter and advance regularity, the intersection shows worst‑case behaviour across conditions. A frequency interval that remains wide and non‑avoid after joining several environmental maps is a robust operating point.

**Visual overlay:**  
Decode two maps and plot their `stability_width`, `FLAG_AVOID`, or score on the same frequency axis. Many tuning tools can import the 16‑byte entry format or the `.gunzstats` raw data to produce overlaid spectrograms.

**Dewaster analysis:**  
Feed the joined map to the **DEWASTER** companion tool (v2.1.2, compatible with GUNZ 3.81.0) to automatically extract the Efficiency Horizon and Doomfall across all conditions. This gives you the Pareto‑optimal operating points that survive under every tested environment.  If you supply the 96‑byte `.gunzstats` file (magic `0x475A4C04` / `0x475A4C05`), the Dewaster can reconstruct exact per‑candidate scores, making the horizon even more precise.

## 4. Building Performance Curves from Maps

A single map provides a one‑dimensional cross‑section (score vs. frequency) for fixed parameters. By varying one parameter systematically and collecting the resulting maps, you can construct multi‑dimensional response surfaces.

**Example – Weight sensitivity curve:**

- Keep all parameters constant except `jitter_weight`.
- Generate maps for weights 1, 2, 4, 8, 16.
- For a chosen frequency, extract the `score` (or `stability_width`) from each map’s `.gunzstats` file.
- Plot score vs. weight → understand how penalty coefficients influence the optima.

**Example – Multi‑resolution deepening curve:**

- Follow the iterative deepening procedure (§3.4.3 of the GUNZ 3.81.0 specification): scan the same band at `time_unit = 3`, `6`, `9`, `12`.
- For each resolution, record the frequency of the minimum‑score candidate and its stability width.
- The sequence forms a convergence curve showing how the optimum sharpens with finer time quantisation.

**GUNZ features used:** `.gunzstats` (raw per‑candidate data in 96‑byte records with magic `0x475A4C04`), `.gunzmeta` (parameter records), deterministic grid for exact alignment across maps.

## 5. Chaining Maps into a Refinement History

The Phoenix mechanism (§7 of the GUNZ 3.81.0 specification) allows maps produced by the same exploration session to be linked into a chain. Each map can reference the next via `chain_next_fingerprint` and its position with `chain_sequence`.

**Pattern – Iterative calibrated refinement:**

1. Start with a seed reference (guessed or explicit, recorded as `reference_source = 0` or `1`).
2. Generate Map 1. Identify the candidate with the smallest `block_time_inaccuracy`.
3. Compute its actual total block time; this becomes the calibrated reference for Map 2.
4. Generate Map 2 with `reference_source = 2` and `chain_sequence = 1`, linking back to Map 1.
5. Repeat until the reference stabilises (e.g., `block_time_inaccuracy` stops decreasing or falls below a chosen tolerance). The exact convergence criterion is implementation‑defined; the maps themselves remain deterministic regardless.

The chain of maps forms an auditable trail of convergence. An orchestrator can “replay” the chain later to verify that the environment hasn’t drifted.

## 6. Runtime Map Switching Based on Monitoring

An external monitor can detect when the current map’s predictions no longer match observed behaviour, and trigger a switch to a different pre‑computed map — or request a fresh scan.

**Simple switching rule (pseudocode):**

```
current_map = load("nominal.gunzmap")
while (system_running) {
    actual_jitter = measure_jitter_last_1000_cycles()
    expected_jitter = map_jitter_at_operating_frequency(current_map)
    if (actual_jitter > expected_jitter * DEVIATION_THRESHOLD) {
        // Environment changed. Try the next pre‑computed map.
        current_map = select_best_map_for_current_conditions(library)
    }
    sleep(monitoring_interval)
}
```

**Note on jitter saturation:** The map entry’s `jitter` field is a `u8` saturated to 255 (base time units). If your expected jitter regularly exceeds this, the raw `.gunzstats` file provides full‑precision values (via the total block‑time sums in the 96‑byte records) and should be used for monitoring. The saturated map entry still correctly indicates whether the zone is detrimental or not.

**Adaptive re‑scanning:**  
When no library map matches, the orchestrator can dynamically construct a new bytecode program (using the Full Profile VM, bytecode version `0x00030050`) with the current observed `reference_block_time` (calibrated) and request a scan. The new map then enters the library for future use. The GUNZ runtime itself never initiates re‑scans; that action is always triggered from outside.

## 7. Using Environment Snapshots for Conditional Orchestration

In Full Profile, the `PURE_CALL` callback can read an **Environment Snapshot** — an immutable, signed snapshot of hardware capabilities, prior scan statistics, etc. This enables the bytecode program itself to make deterministic branching decisions without side effects.

**Pattern – Self‑adaptive scan program:**

A dynamic bytecode program can:

- Read the snapshot to obtain the current CPU base frequency or available timer resolutions.
- Use `PURE_CALL` to decide which frequency zone to scan next, based on previous scan results stored in the snapshot.
- Emit `ZONE` instructions selectively, skipping ranges already known to be detrimental.

**Important:** The Environment Snapshot is **read‑only for the duration of a single scan**. The program cannot update it mid‑scan. All prior results must be loaded into the snapshot before the plan is constructed. This guarantees deterministic execution: the same snapshot plus the same bytecode always yields the same map.

Because the snapshot is part of the plan’s identity, any two executions with the same snapshot and same bytecode will produce bit‑identical maps, preserving determinism while allowing environment‑aware exploration.

## 8. Oracle‑Guided Constraint Tuning

The **ORACLE** companion specification enables constraint‑based queries without full scans. This dramatically accelerates the search for operating points that meet specific requirements.

**Pattern – Fast feasibility check:**

1. Define your hard per‑candidate constraints: `max_jitter`, `max_advance_regularity`, `max_block_time_inaccuracy`.
2. Issue an Oracle query over the target frequency range with `query_class = 0`.
3. If the Oracle returns non‑empty intervals, operating points exist that satisfy all constraints. Pick the midpoint of the widest interval.
4. If empty, relax the least critical constraint and re‑query.

*(Stability‑width constraints are not included here because they require a full dense scan. Stability width can be evaluated later using a local scan and the Dewaster.)*

**Pattern – Oracle‑assisted Dewaster refinement:**

1. Use the Oracle to find all intervals satisfying coarse per‑candidate constraints.
2. Within each interval, run a local dense scan with drift enabled (GUNZ‑DRIFT).
3. Feed the resulting maps to the Dewaster to extract the Efficiency Horizon.
4. Select the horizon point with the lowest drift velocity (`drift_max − drift_min`).

**GUNZ features used:** GUNZ‑ORACLE, GUNZ‑DRIFT, DEWASTER, `.gunzoracle` output format.

## 9. Drift‑Aware Calibration

The **DRIFT** extension captures intra‑block directional timing — the slope of per‑cycle advances within a block. Combined with the drift velocity metric (`drift_max − drift_min`), it reveals not just where the timing is stable, but whether that stability is robust or fragile.

**Pattern – Avoiding knife‑edge operating points:**

1. Run a dense scan with drift enabled across your target range.
2. For each candidate, extract:
   - `score` (from the map or `.gunzstats`)
   - `drift` (average directional slope, from the 96‑byte `.gunzstats` record at offset 48)
   - `drift_velocity = drift_max − drift_min` (from offsets 50 and 52)
3. Prefer candidates with:
   - Low score (truth‑aligned)
   - Low |drift| (balanced internal timing)
   - Moderate drift velocity (adaptive, not fragile)

**Interpretation guide:**

| Drift | Velocity | Meaning |
|-------|----------|---------|
| ~0 | ~0 | Perfectly still — either the ultimate basin or the smoothing trap. |
| ~0 | Low | Adaptive resonance; the snowball rolls gently with perturbations. |
| ~0 | High | Fragile knife‑edge; stable only at the exact center. |
| Non‑zero | Any | Biased timing; long cycles cluster toward one end of the block. |

**GUNZ features used:** GUNZ‑DRIFT (`.gunzstats` drift fields in the 96‑byte record), GUNZ‑Dewaster.

## 10. Archival and Historical Analysis

Map libraries are immutable and can be stored alongside firmware or system images. Since every map carries its own integrity proof (XXH3‑64) and a globally unique fingerprint (XXH3‑128), they can be treated as tamper‑evident documents.

**Long‑term deployment health tracking:**

- Archive maps from periodic “health check” scans over months.
- Plot the evolution of the minimum achievable `block_time_inaccuracy` or stability width at the operating frequency.
- A gradual drift indicates hardware aging or clock degradation, providing an early warning before timing violations occur.

**Persona‑aware archival:**  
If you are using **GUNZ‑PERSONA**, link each health‑check map to the AI’s identity map via `chain_next_fingerprint`. This records not just *what* was measured, but *who* measured it and in what internal state. The calibration history becomes part of the AI’s permanent identity.

---

## 11. Important Limitations

- **Maps are static.** They do not update themselves. If the physical system changes (e.g., a fan turns on, changing temperature), a previously optimal frequency may become detrimental. The orchestrator must detect this and act.
- **The map only knows its own scan conditions.** Using a map outside its original environment is valid only if you are confident the resonance landscape hasn’t shifted. Always verify with a short validation measurement if possible.
- **Drift and velocity are not part of the core map entry.** They reside in the companion `.gunzstats` file. Ensure your pipeline preserves these files if you rely on drift‑aware calibration.
- **Oracle queries are deterministic but require the GUNZ‑ORACLE companion.** Implementations that do not support ORACLE will reject its opcode.

## 12. Summary

| Pattern | Key GUNZ feature | Adaptation triggers |
|---------|------------------|---------------------|
| Environmental map library | Fingerprints, `session_id`, `.gunzmeta` | External monitor detects condition change |
| Map overlay / JOIN | `JOIN` opcode, spatial continuity, Dewaster | Manual or scheduled intersection |
| Curve building | `.gunzstats` (96‑byte, magic `0x475A4C04`), `.gunzmeta`, deterministic grid | Offline analysis, AI decision‑making |
| Chained refinement | Calibrated reference, `chain_sequence` | Convergence monitoring |
| Runtime switching | Library of pre‑computed maps, monitor | Jitter / regularity drift detection |
| Self‑adaptive bytecode | `PURE_CALL`, Environment Snapshot | Internal program logic (deterministic) |
| Oracle‑guided tuning | GUNZ‑ORACLE, GUNZ‑DRIFT, Dewaster | Constraint‑based queries |
| Drift‑aware calibration | GUNZ‑DRIFT (velocity = drift_max − drift_min) | Fragility detection |
| Archival & health tracking | XXH3‑64, XXH3‑128, chaining, GUNZ‑PERSONA | Scheduled health scans |

These patterns are not exhaustive; they are starting points. The static, verifiable nature of GUNZ maps makes them reliable anchors for dynamic systems, but the intelligence that weaves them together lies entirely in the orchestrator — and that is by design.
