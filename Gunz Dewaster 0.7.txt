## 1. Overview

GUNZ‑DEWASTER is a post‑processing companion that analyses an existing GUNZ resonance map and identifies the **Efficiency Horizon** — the set of operating points beyond which any improvement in one metric can only be purchased by degrading another.

The Dewaster does **not** modify the GUNZ core evaluator. It reads a `.gunzmap` file, applies a deterministic dominance algorithm, and produces an annotated map or a separate horizon report. The scanner remains the unforgiving integer truth anchor; the Dewaster is the lens that reveals when the search has reached the edge of the useful world.

### 1.1 Map Preprocessing (Normative)

Before applying any filtering or dominance logic, a conformant Dewaster shall transform the raw `.gunzmap` file into a flat list of consolidated entries with absolute frequency positions. This process is mandatory and must be performed identically by all implementations.

**1. Header parsing.**  
The map header shall be parsed according to GUNZ 3.81.0 §4.2.1.  The effective step size is obtained from `step_freq` (with `0` → default 1) when `step_freq_overflow == 0`, or from the 4‑byte `u32` extension immediately following the header when `step_freq_overflow == 1`.

**2. Sparse‑interval expansion (conditional).**  
The Dewaster shall determine whether the map was produced with sparse‑map emission by examining the `sparse_map` field in the `.gunzmeta` file’s `plan_parameters` object, if available.  

- If `.gunzmeta` is present **and** `plan_parameters.sparse_map` is `true`, the map is a sparse map.  The Dewaster shall reconstruct the full frequency grid by inserting explicit zero‑metric entries for any interval that was omitted.  
- If `.gunzmeta` is absent, or `plan_parameters.sparse_map` is `false` or not present, the map is **not** sparse.  No expansion is performed; the map entries as read from the file directly represent the evaluated candidates.

**Sparse expansion procedure (when active):**  
The Dewaster processes entries sequentially, maintaining the expected next starting frequency.  For each non‑skipped, non‑long‑jump entry, let `end = start + run_length × step_freq`.  The next entry’s expected start is `end`.  If the next entry’s actual start (computed as `current + freq_delta_start`) exceeds this expected start, the difference is an omitted perfect‑resonance interval.  The Dewaster shall insert one or more explicit entries covering that interval, each with all quantitative metrics set to zero, `flags = 0`, and `run_length` set to fill the gap (respecting the u16 limit).  Long‑jump entries are emitted as usual and reset the expected start.

The expansion ensures that after removal of long‑jump and `FLAG_SKIPPED` entries during alignment (§1.3), the remaining entries correspond one‑to‑one with the evaluated candidates and the records in `.gunzstats`.  Long‑jump and skipped entries are retained in the expanded list for frequency tracking and are removed only when alignment is performed.

*Note: These synthetic entries correspond to candidates that were evaluated by the scanner and have records in the `.gunzstats` file.  They are treated as valid operating points for Doomfall analysis but are excluded from the Efficiency Horizon to prevent all‑zero metrics from dominating the frontier.  Each entry carries an internal boolean **synthetic flag** that is preserved through all pipeline stages.*

**3. Absolute‑frequency reconstruction (sequential method).**  
The starting frequency of each entry is determined sequentially.  Initialize `current = base_freq`.  For each entry (processed in map order):

- `start = current + freq_delta_start`
- If the entry is a long‑jump entry (sentinel `run_length == 0` and `block_time_inaccuracy == 0`): ending frequency is `start + gap`, where `gap` is the signed 64‑bit integer decoded from bytes 8–15 (in 10⁻⁵ Hz units). Set `current = start + gap`.
- Otherwise: ending frequency is `start + run_length × step_freq`. Set `current = start + run_length × step_freq`.

This method matches the core GUNZ map‑decoding logic and avoids off‑by‑one errors.

**4. Optional pre‑consolidation for the Efficiency Horizon.**  
After expansion, consecutive entries with identical metrics and flags may be merged into a single entry as per the map consolidation rules (GUNZ 3.81.0 §3.11), **provided they have the same synthetic provenance**: synthetic entries (those created during sparse‑interval expansion) shall only be merged with other synthetic entries; entries present in the original map shall only be merged with other original entries.  The merged entry retains the synthetic provenance of its constituents.  

This pre‑consolidation is **optional** and may be applied **only** to the copy of the candidate list used for the display‑only Efficiency Horizon (user‑visible output).  It **shall not** be applied to the candidate list destined for the Doomfall analysis (§4.4); the Dewaster must retain the original, unconsolidated list of entries for all Doomfall processing, as sustained degradation detection depends on the unmerged candidate sequence.

The resulting list of entries, each annotated with its start and end frequency (both in 10⁻⁵ Hz), is the input to the filtering rules of §2.2.

### 1.2 Unit Conversions

User‑supplied parameters in the Dewaster are often given in human‑friendly units (Hz), while internal GUNZ frequencies are stored in 10⁻⁵ Hz.  The following conversions shall be applied:

| Parameter | Input Unit | Internal Unit | Conversion |
|-----------|------------|----------------|------------|
| `baseline_max_distance_hz` | Hz | 10⁻⁵ Hz | multiply by 100 000 |
| `adaptive_radius_factor` | (unitless) | – | – |
| `stability_width` (map field) | 0.0001 Hz | 10⁻⁵ Hz | multiply by 10 |

All internal computations use 10⁻⁵ Hz; conversions to Hz for display are informational and shall be performed by dividing by 100 000.

### 1.3 Alignment of `.gunzstats` Records to Candidates

Whenever the Dewaster must pair `.gunzstats` records with map entries (for score reconstruction, `stability_precise` mode, or any other purpose), the following alignment procedure shall be performed identically by all implementations.

- Apply sparse‑interval expansion (§1.1 step 2) to the raw `.gunzmap` to obtain a complete expanded entry list (which includes long‑jump entries).
- **Run the sequential frequency reconstruction** (§1.1 step 3) on this complete expanded list.  This yields an absolute start frequency for every entry (including long‑jump entries).  The resulting frequencies shall be stored alongside each entry.
- Remove long‑jump entries and `FLAG_SKIPPED` entries from the list.  The remaining entries keep their pre‑computed absolute frequencies; they must **not** be recomputed from the reduced list.  (Synthetic entries created during expansion represent evaluated candidates and **must not** be removed; they correspond to `.gunzstats` records.)
- Sum the `run_length` values over the remaining entries; the total must equal the number of records in `.gunzstats`. If not, abort.
- Pair the entries with the `.gunzstats` records in order, consuming `run_length` records per entry.

This procedure ensures that every candidate is assigned the correct frequency and the corresponding `.gunzstats` record.  It is invoked from §2.1.1, §4.2.4, and §4.3 as needed.

## 2. The Efficiency Horizon

For a resonance map and a set of user‑selected **trade‑off metrics**, an operating point **A** *dominates* operating point **B** if:

- **A** is strictly better than **B** in at least one metric, and
- **A** is no worse than **B** in every other metric.

The **Efficiency Horizon** is the set of all map entries that are not dominated by any other entry in the same map. These entries form the optimal frontier of the scan. Any entry *not* on the horizon is strictly inferior: there exists another operating point in the same scan that matches or beats it in every trade‑off metric, and beats it in at least one.

If two entries have identical values for all trade‑off metrics, neither dominates the other; both shall be included in the horizon if they are not dominated by any other entry. This preserves the full set of equivalent optimal points.

### 2.1 Trade‑Off Metric Directions

The metrics used to define dominance are selected by the user (or the AI agent) according to the engineering goal. For all metrics except `freq`, the direction is intrinsic and fixed:

| Metric | Direction |
|--------|-----------|
| `block_time_inaccuracy` | lower is better |
| `jitter` | lower is better |
| `advance_regularity` | lower is better |
| `score` | lower is better (see §2.1.1) |
| `stability_width` | higher is better |
| `freq` | user‑declared (minimise or maximise) |

The user may declare the direction for `freq` only. Common configurations:

| Primary metric | Secondary metric | Interpretation |
|----------------|------------------|----------------|
| `block_time_inaccuracy` (lower) | `jitter` (lower) | Accuracy vs. stability |
| `score` (lower) | `freq` (user‑declared) | Overall quality vs. resource cost |
| `block_time_inaccuracy` (lower) | `stability_width` (higher) | Accuracy vs. robustness |

#### 2.1.1 Availability of the `score` Metric

The per‑candidate `score` is not stored directly in the `.gunzmap` file.  The Dewaster may offer `score` as a trade‑off metric **only if** it can reconstruct per‑candidate scores.  This requires:

- A `.gunzstats` file (96‑byte records, magic `0x475A4C04` or compressed `0x475A4C05`), as defined by GUNZ 3.81.0, containing total block‑time sums (`sum_total_block_time`, `sum_total_block_time_sq`) and the optional `advance_regularity_full` field.
- The companion `.gunzmeta` file providing the scan parameters `jitter_weight`, `advance_regularity_weight`, `mult_num`, `mult_den`, and `quantum`.
- Alignment of `.gunzstats` records to map entries, as described in §1.3.

Additionally, if the map was produced with sparse‑map emission, the `.gunzmeta` file’s `plan_parameters.sparse_map` flag is required to correctly expand the candidate list.  If the map is known not to be sparse (or the sparse flag is absent/false), the expansion step is skipped.  The reconstruction procedure handles both cases.

If the `.gunzstats` file or the required scan parameters are not available, the Dewaster **SHALL NOT** include `score` in the list of selectable trade‑off metrics.  If the user requests `score` under these conditions, the Dewaster shall report an error and exit.

**Reconstruction procedure.**  For each candidate, after alignment (§1.3), the Dewaster computes:

1. **Jitter:** population standard deviation of all **total** block times (raw block time + hold/sep contribution), using `block_count`, `sum_total_block_time`, `sum_total_block_time_sq` from the `.gunzstats` record.  This matches the scanner’s internal jitter, which is computed from the same total block‑time values.  The population standard deviation shall be computed using the integer algorithm defined in GUNZ 3.81.0 §4.5.3 (or the algebraically identical closed‑form for advance regularity), including half‑to‑even rounding.  If `block_count == 0`, the candidate’s data is invalid; the Dewaster shall treat the candidate as unclassified for Doomfall purposes and exclude it from the Efficiency Horizon.
2. **Block‑time inaccuracy:** taken directly from the `block_time_inaccuracy` field of the candidate’s map entry.  This is the value the scanner computed from the total block time at the central candidate frequency (Δ = 0), saturated to `UINT32_MAX`.  *(Note: If the true inaccuracy exceeded `UINT32_MAX`, the stored value is capped and the reconstructed score will differ from the scanner’s internal score.  Such candidates are almost certainly marked `FLAG_AVOID` and are excluded from the Efficiency Horizon by default.)*
3. **Advance regularity term:**  
   - If the `.gunzstats` record’s `advance_regularity_full` field (offset 56) is non‑zero, use that value (exact, full‑precision).  
   - Otherwise, use the saturated `advance_regularity` from the map entry (approximate).
4. **Advance regularity in base time units:** `advance_regularity_btu = round_half_even( (adv_reg × mult_den × quantum) / (mult_num × 100) )`.
5. **Score:** `score = block_time_inaccuracy + jitter_weight × jitter + advance_regularity_weight × advance_regularity_btu`.
6. **Saturate to `UINT64_MAX`:** `score = min(score, UINT64_MAX)`.  This matches the scanner’s internal behaviour (GUNZ 3.81.0 §3.11 step 4) and guarantees that the reconstructed score is identical to the scanner’s saturated score when the exactness conditions hold.

The `.gunzstats` record’s raw block‑time sums (`sum_block_time`, `sum_block_time_sq`) are not used in score reconstruction; they are preserved for other analytical tools.

**Exactness of the reconstructed score.**  
When the `.gunzstats` file was produced by the same scan as the `.gunzmap` and its companion `.gunzmeta`, and `advance_regularity_full` is present (non‑zero) in the `.gunzstats` records, the reconstructed score is **identical** to the scanner’s internal score, provided the `block_time_inaccuracy` was not saturated (i.e., the true inaccuracy did not exceed `UINT32_MAX`).  Saturation of `block_time_inaccuracy` occurs only for extreme operating points far from the reference, which are almost certainly flagged `FLAG_AVOID` and excluded from analysis by default.  There are no restrictions on `hold_cycles` or `sep_cycles`; the 96‑byte record supplies the total block‑time sums for jitter.

When `advance_regularity_full` is unavailable, the Dewaster uses the saturated `u16` map‑entry value.  For the vast majority of candidates the saturated value is exact; only candidates whose true advance regularity exceeded 65535 are affected, and they are almost certainly marked `FLAG_AVOID`.  In those rare cases, the Dewaster’s score will be slightly lower than the scanner’s, which has negligible impact on horizon analysis.  When the saturated map‑entry value is used, the reconstructed score is **not** guaranteed to be bit‑identical to the scanner’s internal score; the discrepancy is bounded and confined to those candidates.

### 2.2 Entry Filtering

Before the dominance check, the Dewaster shall exclude the following entries from the set of candidates considered for the Efficiency Horizon:

- **Long‑jump entries** (sentinel `run_length == 0` and `block_time_inaccuracy == 0`). These represent gaps in the scan, not operating points.
- **Skipped entries** (`FLAG_SKIPPED` set). These were not evaluated.
- **Detrimental entries** (`FLAG_AVOID` set). These represent operating points the scanner itself has flagged as undesirable. A user may explicitly request their inclusion via a configuration flag (`--include‑avoid`), but the default is exclusion.
- **Synthetic entries produced by sparse‑interval expansion** (§1.1 step 2). These entries have all quantitative metrics set to zero and `flags = 0`; they were not present in the original `.gunzmap` file and represent perfect‑resonance points that were never individually emitted by the scanner.  They are **excluded from the Efficiency Horizon** to prevent a single all‑zero candidate from dominating every other operating point.  (Their inclusion in the Doomfall candidate set is governed by §4.3 and §4.4 step 1.)

Additionally, when `stability_width` is among the selected trade‑off metrics, entries with zero `stability_width` are excluded. This prevents the horizon from being cluttered with points that have no measurable stability. If all entries in the map have zero stability width and this metric is selected, the resulting horizon will be empty — a correct reflection of the data. Users may choose to omit `stability_width` from the trade‑off set when scanning at coarse `time_unit`.

*(Informative: zero stability width is normative for all entries when `time_unit < 9`, and may also occur for individual entries at finer time‑units when the score tolerance is unrepresentably small.  Users who see an empty horizon and are scanning at a coarse `time_unit` should consider whether `stability_width` is a meaningful metric for their use‑case.)*

**Baseline selection for Doomfall:** Regardless of the `--include‑avoid` flag, the baseline used in the Doomfall algorithm is always chosen from **non‑avoided** horizon entries. If no non‑avoided horizon entry exists, the Doomfall cannot be computed and the algorithm shall report “No valid baseline available” and exit.

## 3. Reaching the Horizon – The Dewaster Algorithm

Given a GUNZ resonance map and a choice of trade‑off metrics with their directions, a conformant Dewaster shall determine the Efficiency Horizon by a deterministic procedure whose output depends only on the map and the metric selection.

**Normative dominance check:**
Let `M` be the list of consolidated map entries after applying the filtering rules of §2.2. An entry `A` dominates entry `B` if, for every trade‑off metric `m`:

- If `m` is “lower‑is‑better”: `A.m ≤ B.m`
- If `m` is “higher‑is‑better”: `A.m ≥ B.m`

and at least one of the inequalities is strict.

**Determining the horizon:**
The **Efficiency Horizon** is the subset of entries that are **not** dominated by any other entry. Any deterministic algorithm that produces this exact subset is conformant. The reference algorithm is the naive O(N²) pairwise comparison, which is sufficient for maps containing a few hundred consolidated entries. For larger maps, efficient skyline algorithms (e.g., O(N log N) after sorting) are permitted, provided they produce identical output.

**Output:** The Dewaster shall produce a list of frequency intervals (start‑freq, end‑freq) and their associated metrics for every entry that lies on the Efficiency Horizon. The output format is implementation‑defined; a companion file with extension `.gunzhorizon` is suggested.

## 4. Beyond the Horizon – The Doomfall (Normative)

The Efficiency Horizon tells the user which operating points are optimal given the declared trade‑offs. It does not, however, indicate which direction along the frequency axis leads to degradation. The **Doomfall** is an analysis that answers this question: *if I continue scanning in this direction, will things get worse?*

### 4.1 User Inputs for Doomfall

To compute the Doomfall, the user must supply the following inputs beyond those required for the horizon:

| Input | Description |
|-------|-------------|
| **Primary metric** | Which trade‑off metric is the user's primary concern. Must be one of the metrics selected for the horizon. |
| **Scan direction** | `increasing` (default) or `decreasing` — which direction along the frequency axis represents "forward" movement. |
| **Sufficiency threshold** (optional) | A numeric threshold for how much a secondary metric must improve to offset primary degradation. The threshold is expressed in the natural units of the secondary metric (e.g., nanoseconds for jitter, ticks×100 for advance regularity). If omitted, any worsening of the primary metric is considered decisive regardless of secondary gains. |
| **Minimum Doomfall run** (`min_doomfall_run`, optional) | The minimum number of consecutive candidates that must satisfy the Doomfall inclusion condition for a Doomfall interval to be emitted. Recommended default is **5**. |
| **Baseline mode** (`baseline_mode`, optional) | One of `nearest` (default), `pareto`, `stability_window`, `stability_precise`, `adaptive_radius`. |
| **Baseline maximum distance** (`baseline_max_distance_hz`, optional) | (Used by `nearest`, `stability_window`, `adaptive_radius`) Maximum allowed frequency distance between a candidate and its baseline. Default: `20.0` Hz. |
| **Adaptive radius factor** (optional, used by `adaptive_radius`) | Multiplier for step size when computing the adaptive radius. Default: `10`. |
| `.gunzstats` file | Required for `stability_precise` mode; used for `score` metric reconstruction when available. |
| `--iteration-limited` flag | (Optional) User‑supplied flag indicating the scan was truncated by the global iteration limit. |

All frequency‑domain parameters are converted to 10⁻⁵ Hz internally using the conversion rules in §1.2.

> *Note:*  A single sufficiency threshold is applied to all secondary metrics.  Because secondary metrics may have different units and natural scales (e.g., nanoseconds for jitter, ticks × 100 for advance regularity), users must choose a threshold that is meaningful across all selected metrics, or use the same units for all secondary metrics.  The Dewaster does not perform unit conversion between different metric types.  Users who mix secondary metrics of different units should be aware that a single absolute threshold treats improvements in those metrics as directly comparable, which may not reflect their true engineering trade‑off.

> **Note on synthetic entries and `stability_width`:** When `stability_width` is the primary metric, synthetic entries (which have zero stability width) will always be considered degraded.  This may produce Doomfall intervals that reflect the omission of perfect‑resonance points rather than genuine degradation.  Users are advised to avoid selecting `stability_width` as the primary metric when analysing sparse maps, or to use a baseline mode that is insensitive to stability width (e.g., `pareto` or `nearest` with appropriate secondary metrics).

If the user selects `score` as the primary metric but the Dewaster cannot reconstruct per‑candidate scores (because the required `.gunzstats` or `.gunzmeta` data is absent), the Doomfall analysis shall abort with an error message indicating that the primary metric is unavailable.  The Efficiency Horizon alone may still be computed for the remaining metrics.

### 4.2 Baseline Selection Modes

The Doomfall algorithm must select, for each candidate beyond the last horizon point, a **baseline** horizon entry against which degradation is measured. The selection method is determined by `baseline_mode`. All modes are optional to implement; if a mode is offered, its output must be deterministic for identical inputs.

**Tie‑breaker determinism.**  In any mode, if multiple horizon entries remain tied after applying all primary selection criteria (including primary‑metric and frequency‑distance tie‑breakers), the Dewaster shall select the entry with the **smallest start frequency**.  This guarantees deterministic output across all implementations.

**Definition of “best primary metric.”**  In all baseline selection procedures, the phrase “best primary metric” means: the smallest value if the primary metric is lower‑is‑better, or the largest value if the primary metric is higher‑is‑better.

#### 4.2.1 `nearest` Mode

Select the non‑avoided horizon entry with the smallest absolute frequency difference to the candidate’s start frequency. In case of tie, pick the one with the better primary metric. If the distance exceeds `baseline_max_distance_hz` (converted to internal units), the candidate is **unclassified**. Apply the universal tie‑breaker if needed.

#### 4.2.2 `pareto` Mode

Select a baseline using global metric dominance, independent of frequency.

- Collect all non‑avoided horizon entries that are **no worse** than the candidate in **every** secondary metric.
- If this set is non‑empty, pick the entry with the **best primary metric** (most favourable direction). In case of tie, pick the one with the smallest absolute frequency difference to the candidate. Apply the universal tie‑breaker if still tied.
- If the set is empty, the candidate is **unclassified**.

#### 4.2.3 `stability_window` Mode (Heuristic)

Use the approximate stability intervals stored in the map entries.

- For each non‑avoided horizon entry with `stability_width > 0`, compute the symmetric stability interval:  
  `hw_10uHz = (stability_width × 10) / 2`   (integer division, truncating toward zero)  
  `[ freq − hw_10uHz, freq + hw_10uHz ]`
- Collect all horizon entries whose interval contains the candidate’s start frequency.
- If the set is non‑empty, pick the entry with the best primary metric (tie: smallest frequency distance). Apply the universal tie‑breaker if still tied.
- If the set is empty, the candidate is **unclassified**.

**Caveat:** The stability interval is a heuristic; the map entry stores only the total width, not the actual left/right boundaries. Users requiring exact boundaries must use `stability_precise` mode.

#### 4.2.4 `stability_precise` Mode (Requires `.gunzstats`)

This mode recomputes exact per‑candidate stability intervals using Dewaster‑reconstructed scores, then assigns baselines from the same stability valley.  It provides the most precise baseline and can be made **exact** when the `.gunzstats` file includes the optional `advance_regularity_full` field.

**Prerequisites:**
- The `.gunzstats` file (96‑byte records, magic `0x475A4C04` or compressed `0x475A4C05`), containing total block‑time sums as defined by GUNZ 3.81.0.
- The `.gunzmeta` file (for scan parameters, and for the `sparse_map` flag if the map is sparse).
- The Dewaster **shall** abort with an error if `.gunzstats` is missing; it **shall not** abort if `advance_regularity_full` is absent (it will use saturated advance regularity from the map entry).
- If the map was produced with sparse‑map emission and `.gunzmeta` is missing or does not contain the `sparse_map` flag, the Dewaster **shall** abort with an error because it cannot correctly expand the candidate list.
- This mode requires `time_unit ≥ 9` to produce non‑trivial stability intervals.  If invoked with `time_unit < 9`, every candidate will be unclassified; an implementation may emit a warning to the user.

**Procedure:**

1. **Reconstruct per‑candidate scores** using the method of §2.1.1.  Alignment of `.gunzstats` records to candidates is performed as described in §1.3.
2. **Run the normative Phase 2 stability‑width algorithm** (GUNZ 3.81.0 §3.11 Phase 2) on those scores to obtain exact left/right stability boundaries and stability width for every candidate.  
   The Dewaster shall apply the `time_unit`‑dependent tolerance exactly as defined.  When `time_unit < 9`, stability width is set to **zero** for all candidates.
3. **Provide reconstructed scores for subsequent use.**  
   The per‑candidate scores computed in step 1 and the stability intervals from step 2 are stored alongside the candidate entries for use in the Doomfall Preprocessing Pipeline (§4.3).
4. **Group candidates into stability valleys.**  
   The candidate list at this stage contains no long‑jump entries (they were removed during alignment, §1.3).  Unevaluated gaps between zones correspond to positions where a long‑jump entry was removed; stability intervals naturally do not overlap across these gaps.  Therefore, grouping candidates into stability valleys by overlap/touch automatically respects zone boundaries.  A valley that contains no horizon entries (from the horizon produced by the preprocessing pipeline, §4.3) yields **unclassified** candidates.
5. **For a Doomfall candidate beyond the last horizon point**, identify its valley. If the candidate lies outside any valley, it is **unclassified**. If the valley contains horizon entries, select the one with the best primary metric (tie: smallest frequency distance, then universal tie‑breaker).

When `advance_regularity_full` is present (non‑zero) in the `.gunzstats` records, the reconstructed scores are **identical** to the scanner’s internal scores (subject to the saturation caveat of §2.1.1), and the resulting stability intervals are **bit‑identical** to those the scanner would have produced.  This holds for both sparse and non‑sparse maps; sparse‑map expansion and alignment supply the full candidate list and associated `.gunzstats` data.

#### 4.2.5 `adaptive_radius` Mode

A heuristic that uses the map’s step size and horizon density to define a local frequency radius.

- Compute the median absolute frequency gap between consecutive non‑avoided horizon entries. If there are fewer than 2 horizon entries, use the map’s effective step size `step_freq` (in 10⁻⁵ Hz) multiplied by `adaptive_radius_factor`.  The result is a frequency value in 10⁻⁵ Hz, consistent with the internal unit used for all other frequency‑domain computations in this section.
- Compute radius `r = max( step_freq × adaptive_radius_factor, median_gap )`. Both terms are in 10⁻⁵ Hz.
- Find all non‑avoided horizon entries within `r` of the candidate’s start frequency (absolute distance ≤ `r`). Among them, pick the entry with the best primary metric (tie: smallest frequency distance). Apply the universal tie‑breaker if still tied.
- If no horizon entry lies within the initial radius `r`, the radius shall be doubled repeatedly until at least one horizon entry is found or the radius exceeds `baseline_max_distance_hz`.  If the maximum distance is exceeded without finding a horizon entry, the candidate is unclassified.

### 4.3 Doomfall Preprocessing Pipeline

Before the Doomfall algorithm steps are executed, the Dewaster shall perform the following preprocessing steps on the expanded, pre‑processed map (§1.1).  These steps ensure that the candidate set and the Efficiency Horizon are consistent with any reconstructed metrics.

**1. Score availability and reconstruction.**  
If the user has selected `score` as a trade‑off metric, or if `stability_precise` baseline mode is active, the Dewaster shall reconstruct per‑candidate scores as described in §2.1.1.  Alignment of `.gunzstats` records to candidates (§1.3) must be performed beforehand.  The scores are attached to each candidate and used in subsequent steps.

**2. Candidate list for Doomfall.**  
The Doomfall algorithm (§4.4) operates on the original, unconsolidated list of non‑horizon candidates.  The optional pre‑consolidation described in §1.1 step 4 **shall not** be applied to this list; any consolidation performed for the Efficiency Horizon must be done on a separate copy, and the Dewaster must retain the unconsolidated list for Doomfall processing.  This ensures that sustained degradation over multiple consecutive candidates can be correctly detected.

**3. Efficiency Horizon recomputation (if needed).**  
If `score` is among the user‑selected trade‑off metrics **and** the Dewaster successfully reconstructed per‑candidate scores, the Efficiency Horizon shall be recomputed from the **unconsolidated** candidate pool (since the Doomfall pipeline must use the unconsolidated list).  The recomputation uses the reconstructed score as the value for the `score` metric while retaining the original map‑entry values for all other trade‑off metrics.  The filtering rules of §2.2 (including the exclusion of synthetic entries) apply identically.  The recomputed horizon replaces the original horizon for all Doomfall purposes.  

If `score` is not a selected metric, or if scores could not be reconstructed, the Dewaster shall recompute the Efficiency Horizon from the **unconsolidated** candidate list using the original map‑entry metrics.  This ensures that the Horizon used for Doomfall is always derived from the same unconsolidated list as the candidate set \(D\).  The optional pre‑consolidation of §1.1 step 4 may be applied only to the display‑only Horizon (user‑visible output) and must not be used for baseline selection.

The output of this pipeline is the unconsolidated list of candidates with final metrics and a deterministic Efficiency Horizon.  These are the inputs to the Doomfall algorithm steps (§4.4).

### 4.4 Deterministic Doomfall Algorithm Steps

**Prerequisite guard.** If the Efficiency Horizon is empty, or no non‑avoided horizon entry exists, the Doomfall is undefined. Report “No valid baseline” and exit.

The following steps assume that the preprocessing pipeline (§4.3) has already produced a final Efficiency Horizon \(H\) and an unconsolidated candidate list.

1. **Define the candidate set \(D\).**  
   Let \(D\) be all entries from the candidate list that are **not** in \(H\) and are **not** long‑jump entries (`run_length == 0` and `block_time_inaccuracy == 0`) and **not** `FLAG_SKIPPED` entries.  
   Detrimental entries (`FLAG_AVOID`) are also excluded from \(D\) unless `--include‑avoid` is active.  
   **Synthetic entries** created during sparse‑interval expansion are **always retained** in \(D\); they are real evaluated candidates and must be present for a complete analysis. Candidates with `block_count == 0` (invalid data, as identified during score reconstruction) are **excluded** from \(D\); they cannot satisfy any inclusion condition and would otherwise appear as unclassified hard boundaries.  This exclusion is applied regardless of their presence in the horizon.

2. **Sort** \(D\) in ascending order of start frequency (or descending if `scan_direction = decreasing`).

3. **Identify the last horizon point** in the scan direction. Let \(f_{\text{last\_h}}\) be the frequency of the horizon entry with the highest frequency (lowest, for `decreasing`).  If multiple horizon entries share the extreme frequency, the one with the smallest start frequency is used.  All entries in \(D\) with start frequency beyond \(f_{\text{last\_h}}\) are **candidates**.  For scans with `scan_direction = decreasing`, “beyond” means start frequency **strictly less** than \(f_{\text{last\_h}}\).  (Synthetic entries created during sparse‑expansion represent real evaluated candidates and are included.)

4. **For each candidate** \(E\), in frequency order:
   - Invoke `select_baseline(E, H, baseline_mode, …)`. If the result is `unclassified`, skip the candidate (it does not contribute to any Doomfall run, but acts as a hard boundary for merging).
   - Let `h` be the selected baseline.
   - Compute \(\Delta_{\text{primary}}\) as follows:
     - If the primary metric is **lower‑is‑better**: \(\Delta_{\text{primary}} = E.\text{metric} − h.\text{metric}\).
     - If the primary metric is **higher‑is‑better**: \(\Delta_{\text{primary}} = h.\text{metric} − E.\text{metric}\).
     A positive \(\Delta_{\text{primary}}\) indicates worsening of the primary metric.
   - For every secondary metric \(m\), determine if \(E.m\) is strictly better than \(h.m\). If yes, record the improvement magnitude:
     - If the secondary metric is **lower‑is‑better**: \(\delta_m = h.m − E.m\).
     - If the secondary metric is **higher‑is‑better**: \(\delta_m = E.m − h.m\).
     \(\delta_m\) is always positive when an improvement exists.
   - **Inclusion condition:** \(E\) is added to the Doomfall if **all** of the following hold:
     - \(\Delta_{\text{primary}} > 0\) (primary metric strictly worsened).
     - For every secondary metric that improved, the improvement \(\delta_m\) is **strictly below** the user‑supplied sufficiency threshold (if provided).  If no threshold is provided, any strict worsening of the primary qualifies regardless of secondary improvements.
   - If the user selected **only** the primary metric, the sufficiency‑threshold condition is vacuously satisfied.

5. **Apply minimum sustained degradation.** A Doomfall interval shall consist of at least `min_doomfall_run` consecutive Doomfall‑positive candidates. Shorter runs are discarded.  
   The Dewaster shall retain, for each classified candidate, a Boolean flag indicating whether it satisfied the inclusion condition of step 4.  This flag is used in step 7 to distinguish candidates that were dropped solely by the run‑length filter from those that genuinely failed the inclusion test.  
   *(Informative: The storage format of the per‑candidate Boolean flag is an implementation detail; any representation that allows correct evaluation of the merging rule in step 7 is conformant.)*

6. **Trailing‑edge exception.** If a run of Doomfall‑positive candidates extends to the last candidate in the scan and has length at least 1 but less than `min_doomfall_run`, it is emitted as a trailing‑edge Doomfall.  The interval shall be marked with `trailing_edge: true`.  
   Additionally, if the scan boundary was artificially caused by the global iteration limit, the interval shall be marked with `boundary_artificial: true`.  The Dewaster determines this by checking, in order: (a) the `.gunzmeta` file’s `scan_zones` array — if any zone contains `"excluded": true`, the scan was truncated by the iteration pre‑pass; (b) the user‑supplied `--iteration-limited` flag.  If neither source is available, the Dewaster omits the `boundary_artificial` field.

7. **Merge adjacent runs.** Adjacent Doomfall runs separated by gaps of fewer than `min_doomfall_run` non‑Doomfall candidates **shall** be merged into a single interval **only if** every candidate in the gap failed solely because its run was too short (i.e., it satisfied the inclusion condition in step 4 but was dropped in step 5). If any candidate in the gap failed due to primary metric improvement, no change, or a secondary threshold exceedance, the gap is a hard boundary and runs are not merged.
   Candidates classified as `unclassified` in step 4 are treated as a hard boundary for run merging: adjacent Doomfall runs separated by an unclassified candidate shall not be merged, regardless of the length of the gap.

8. **Output** Doomfall intervals with start/end frequencies, metrics, and any `trailing_edge` and `boundary_artificial` flags.

### 4.5 Interpretation

The Doomfall identifies regions where the primary metric is degrading and secondary metrics are not improving enough to compensate. It is a natural stop‑signal for an autonomous agent. For a human engineer, it is a warning that the trade‑off has turned unfavourable.

## 5. Relationship to the Phoenix Mechanism

When chaining scans, the Dewaster can serve as convergence detector and stop‑signal generator:

- **After each scan**, compute the Efficiency Horizon.
- **Compare** the current horizon to the previous scan’s horizon; if substantially unchanged, the agent has likely converged.
- **If Doomfall is enabled**, stop scanning if the current range extends into a Doomfall region.
- **Before refining the reference**, verify that the calibrated reference lies on the current horizon; if not, update it.

## 6. Relationship to ORACLE

| Tool | Question Answered | When to Use |
|------|-------------------|-------------|
| **ORACLE** | "Where are frequencies satisfying these constraints?" | Before a full scan, to narrow the search range. |
| **DEWASTER** | "Among already scanned frequencies, which are the best trade‑offs?" | After a scan, to interpret results and decide whether to continue. |

ORACLE finds promising regions; DEWASTER evaluates what was found.

## 7. Integration with GUNZ

The Dewaster is an **external tool**. It operates on existing `.gunzmap` files. No new GUNZ opcodes, map versions, or header fields are required.

A conformant Dewaster:

- Shall accept a `.gunzmap` file and a specification of trade‑off metrics.
- Shall perform map preprocessing (§1.1), including handling of `step_freq_overflow` and sparse‑map expansion.
- Shall apply filtering (§2.2) for the Efficiency Horizon; for Doomfall, the preprocessing pipeline (§4.3) and candidate filtering (§4.4 step 1) shall be applied.
- Shall produce a deterministic Efficiency Horizon (§3). When `score` is a selected trade‑off metric and reconstructed scores are available, the horizon shall be recomputed as required by §4.3 step 3 before Doomfall processing.
- Shall implement one or more Doomfall baseline modes (§4.2) and the associated Doomfall algorithm (§4.4). Each implemented mode must produce deterministic output, including the universal tie‑breaker.
- May annotate the map by writing a companion file (e.g., `.gunzhorizon`).
- When processing `.gunzstats` files, shall accept the 96‑byte record format with magic `0x475A4C04` (raw) or `0x475A4C05` (compressed), as defined in GUNZ 3.81.0.
- When processing `.gunzstatz` (compressed) files, shall correctly decode the u16 bitmask and accept bits 11‑13 (advance_regularity_full, sum_total_block_time, sum_total_block_time_sq) when present.
- When reconstructing scores, shall use the full procedure of §2.1.1, including the integer standard deviation algorithm of GUNZ 3.81.0 §4.5.3 and `UINT64_MAX` saturation.

The Dewaster is **not required** for GUNZ conformance.

## 8. Interpretation Notes *(Informative)*

**Choosing trade‑off metrics:** The same map can have different horizons depending on what the user values. There is no single “true” horizon — only the horizon corresponding to the declared goal.

**Detrimental entries and `--include‑avoid`:** By default, `FLAG_AVOID` entries are excluded. With `--include‑avoid`, they appear in the horizon but are never used as Doomfall baselines.

**Non‑convex trade‑offs:** The Efficiency Horizon does not assume convexity. Gaps indicate no operating point fills that trade‑off region. The Doomfall analysis relies only on local comparisons and is independent of convexity.

**Decision‑support, not enforcement:** The Dewaster makes the trade‑off visible. The human (or AI) retains full authority.

## 9. Conformance

A conformant GUNZ‑DEWASTER implementation must:

- Accept a valid GUNZ `.gunzmap` file compliant with version `0x004D`.
- Accept user‑specified trade‑off metrics with directions.
- Apply map preprocessing (§1.1), correctly decoding `step_freq_overflow` and reconstructing sparse‑omitted intervals.
- Apply entry filtering (§2.2) for the Efficiency Horizon; for Doomfall, apply the preprocessing pipeline (§4.3) and candidate filtering (§4.4 step 1).
- Implement the dominance check (§3) and produce a deterministic Efficiency Horizon. When `score` is a selected trade‑off metric and reconstructed scores are available, recompute the horizon as required by §4.3 step 3 before Doomfall processing.
- Implement one or more Doomfall baseline modes (§4.2) and the Doomfall algorithm (§4.4). Each implemented mode must produce deterministic output, including the universal tie‑breaker.
- Not modify the original `.gunzmap` file unless writing a separate annotated copy.
- When `score` is offered, use the reconstruction procedure of §2.1.1, including the integer standard deviation of GUNZ 3.81.0 §4.5.3 and `UINT64_MAX` saturation; if `.gunzstats` or the required metadata parameters are unavailable, refuse to provide `score`.

  [199.99999 – 200.00000]  inaccuracy=0.000  jitter=0.00
  [209.79000 – 209.80000]  inaccuracy=1.200  jitter=0.00

# Appendix — Tide Map Extension (Informative)

*This appendix describes an optional extension to GUNZ‑DEWASTER that enables correct analysis of tide‑compensated resonance maps produced by the GUNZ Tide Scan (Appendix T of the core GUNZ specification).  Implementations that support tide maps shall follow this specification to ensure deterministic output.*

---

## G.1 Overview

A tide‑compensated resonance map is produced by evaluating every candidate frequency against a modulation curve—a sequence of offsets applied to the truth anchor (§T.3).  The map entry stores the candidate’s `block_time_inaccuracy` computed against the **nominal** (unmodulated) anchor, while the scanner’s internal score and stability width are computed from the **aggregated** score across all modulation phases.

The standard Dewaster score reconstruction uses the map’s `block_time_inaccuracy`, which is the static nominal value.  Consequently, a naive Dewaster analysis would produce an incorrect Efficiency Horizon and Doomfall for tide maps.  This extension overrides the score reconstruction when tide metadata is present and `score` is a selected trade‑off metric, computing the exact aggregated score that matches the scanner’s internal value.

---

## G.2 Prerequisites

The extension is activated **only when** the companion `.gunzmeta` file contains the key `tide_enabled` with value `true` **and** the user has selected `score` as one of the trade‑off metrics.  If `score` is not selected, the Dewaster uses the standard map‑entry metrics unchanged.

When `tide_enabled` is `true` and `score` is selected, the `.gunzmeta` file must additionally provide:

- `tide_curve` – array of signed 32‑bit integers (the modulation offsets, in base‑time units).  
- `tide_mode` – string, either `"worst_case"` or `"average"`.  
- `reference_block_time` – the nominal anchor (already present in `.gunzmeta`).

If any of these required tide fields is missing, or if the `.gunzstats` file is unavailable, the Dewaster **shall refuse to offer `score`** as a trade‑off metric and report an error to the user, exactly as it does for a missing `.gunzstats` file in the standard case.

The `.gunzstats` file (96‑byte records) is required, as for standard score reconstruction.  The optional `advance_regularity_full` field is used if available; otherwise the saturated map‑entry value is used.

---

## G.3 Tide‑Aware Score Reconstruction

For each candidate, after alignment with its `.gunzstats` record (§1.3 of the Dewaster), the Dewaster computes the following in place of the standard score reconstruction:

1. **Jitter:** computed exactly as in the standard reconstruction (population standard deviation of total block times from `sum_total_block_time` and `sum_total_block_time_sq`).  This value is independent of the modulation and is used for all phases.

2. **Average total block time:**  
   `avg_total_time = round_half_even( sum_total_block_time / block_count )`  
   (identical for all phases).

3. **Advance regularity term:** computed exactly as in the standard reconstruction, using `advance_regularity_full` if available, else the map entry’s saturated value.  This term is also invariant across phases.

4. **Per‑phase score:**  
   Let `N_phases = length(tide_curve)`.  For each `p = 0 … N_phases−1`:
   - Compute the modulated reference:  
     `ref_p = reference_block_time + tide_curve[p]` (using 64‑bit signed addition; the tide appendix guarantees `0 ≤ ref_p ≤ UINT32_MAX`).
   - Compute the phase‑specific score:  
     `S_p = |avg_total_time − ref_p| + jitter_weight × jitter + advance_regularity_weight × advance_regularity_btu`.  
     **All arithmetic in this computation shall use 128‑bit unsigned integers** to avoid overflow, exactly as in the core evaluator’s score formula (GUNZ 3.81.0 §3.11 step 4).  
   - **Saturate** `S_p` to `UINT64_MAX`: `S_p = min(S_p, UINT64_MAX)`.  This matches the scanner’s internal saturation before aggregation.

5. **Aggregation:**
   - **`worst_case`:**  
     `aggregated_score = max(S_p)` over all `p`.  If multiple phases share the maximum, any may be chosen (the value is identical).  
   - **`average`:**  
     `aggregated_score = round_half_even( Σ S_p / N_phases )`, where the sum is accumulated in a **128‑bit unsigned integer** before division.  Half‑to‑even rounding is used per GUNZ 3.81.0 §4.5.1.

6. **Final score:** `aggregated_score` is the candidate’s score for all subsequent Dewaster operations (Efficiency Horizon, Doomfall baseline comparison, stability‑precise recomputation).

---

## G.4 Caveats and Limitations

- **`block_time_inaccuracy` in the map is static.**  The map entry’s `block_time_inaccuracy` is `|total_time − A₀|` (the nominal anchor).  It does **not** represent the worst‑case or average inaccuracy across the modulation cycle.  If the user selects `block_time_inaccuracy` as a trade‑off metric alongside `score`, the Efficiency Horizon will mix a static metric with the tide‑aggregated score, which may not reflect the true engineering trade‑offs.  Users are advised to rely on `score` as the primary metric for tide maps, or to be aware of this limitation.

- **Jitter and advance regularity** are unaffected by the modulation (only the anchor varies) and are correctly represented by their map entries.

- **Stability‑width recomputation** (`stability_precise` mode) is fully exact with the aggregated score.

- **Doomfall baseline selection** uses the tide‑aware horizon and is therefore correct.

- **No other Dewaster algorithms** are affected by this extension.

---

## G.5 Integration with the Core Dewaster

When this extension is implemented, the Dewaster shall check for the presence of `tide_enabled = true` in the `.gunzmeta` file during the Doomfall Preprocessing Pipeline (§4.3 of the Dewaster).  If present, and if `score` is among the selected trade‑off metrics, it shall use the tide‑aware score reconstruction (§G.3) instead of the standard reconstruction (§2.1.1) for all candidates.  The remainder of the pipeline (horizon recomputation, Doomfall steps) operates identically on the resulting scores.

If `tide_enabled` is `true` but `score` is not a selected metric, the Dewaster proceeds normally with the static map‑entry metrics; no error is raised.
