## 1. Overview

GUNZ‑DEWASTER is a post‑processing companion that analyses an existing GUNZ resonance map and identifies the **Efficiency Horizon** — the set of operating points beyond which any improvement in one metric can only be purchased by degrading another.

The Dewaster does **not** modify the GUNZ core evaluator, nor does it require new byte‑code opcodes. It reads a `.gunzmap` file, applies a deterministic dominance algorithm, and produces an annotated map or a separate horizon report. The scanner remains the unforgiving integer truth anchor; the Dewaster is the lens that reveals when the search has reached the edge of the useful world.

### 1.1 Map Preprocessing (Normative)

Before applying any filtering or dominance logic, a conformant Dewaster shall transform the raw `.gunzmap` file into a flat list of consolidated entries with absolute frequency positions. This process is mandatory and must be performed identically by all implementations.

**1. Header parsing.**  
The map header shall be parsed according to GUNZ 3.67.0 §4.2.1.  The effective step size is obtained from `step_freq` (with `0` → default 1) when `step_freq_overflow == 0`, or from the 4‑byte `u32` extension immediately following the header when `step_freq_overflow == 1`.

**2. Sparse‑interval expansion.**  
If the map’s `sparse_map` flag is set, any implicit gap between the ending frequency of one entry and the starting frequency of the next entry shall be filled with one or more explicit entries having all quantitative metrics set to zero and `flags = 0`.  These entries represent perfect‑resonance points omitted for storage efficiency.  The expansion shall produce a continuous frequency axis with no gaps except those represented by long‑jump entries.

**3. Absolute‑frequency reconstruction (sequential method).**  
The starting frequency of each entry is determined sequentially.  Initialize `current = base_freq`.  For each entry (processed in map order):

- `start = current + freq_delta_start`
- If the entry is a long‑jump entry (sentinel `run_length == 0` and `block_time_inaccuracy == 0`): ending frequency is `start + gap`, where `gap` is the signed 64‑bit integer decoded from bytes 8–15 (in 10⁻⁵ Hz units). Set `current = start + gap`.
- Otherwise: ending frequency is `start + run_length × step_freq`. Set `current = start + run_length × step_freq`.

This method matches the core GUNZ map‑decoding logic and avoids off‑by‑one errors.

**4. Consolidation.**  
After expansion, consecutive entries with identical metrics and flags may be merged into a single entry as per the map consolidation rules (GUNZ 3.67.0 §3.11).  This step is optional but recommended to reduce the input size for the dominance algorithm.

The resulting list of entries, each annotated with its start and end frequency (both in 10⁻⁵ Hz), is the input to the filtering rules of §2.

### 1.2 Unit Conversions

User‑supplied parameters in the Dewaster are often given in human‑friendly units (Hz), while internal GUNZ frequencies are stored in 10⁻⁵ Hz.  The following conversions shall be applied:

| Parameter | Input Unit | Internal Unit | Conversion |
|-----------|------------|----------------|------------|
| `baseline_max_distance_hz` | Hz | 10⁻⁵ Hz | multiply by 100 000 |
| `adaptive_radius_factor` | (unitless) | – | – |
| `stability_width` (map field) | 0.0001 Hz | 10⁻⁵ Hz | multiply by 10 |

All internal computations use 10⁻⁵ Hz; conversions to Hz for display are informational and shall be performed by dividing by 100 000.

## 2. The Efficiency Horizon

For a resonance map and a set of user‑selected **trade‑off metrics**, an operating point **A** *dominates* operating point **B** if:

- **A** is strictly better than **B** in at least one metric, and
- **A** is no worse than **B** in every other metric.

The **Efficiency Horizon** is the set of all map entries that are not dominated by any other entry in the same map. These entries form the optimal frontier of the scan. Any entry *not* on the horizon is strictly inferior: there exists another operating point in the same scan that matches or beats it in every trade‑off metric, and beats it in at least one.

If two entries have identical values for all trade‑off metrics, neither dominates the other; both shall be included in the horizon if they are not dominated by any other entry. This preserves the full set of equivalent optimal points.

### 2.1 Trade‑Off Metric Directions

The metrics used to define dominance are selected by the user (or the AI agent) according to the engineering goal. For all metrics except `freq`, the direction is intrinsic and fixed:

| Metric | Direction |
|--------|-----------|
| `block_time_inaccuracy` | lower is better |
| `jitter` | lower is better |
| `advance_regularity` | lower is better |
| `score` | lower is better (see §2.1.1) |
| `stability_width` | higher is better |
| `freq` | user‑declared (minimise or maximise) |

The user may declare the direction for `freq` only. Common configurations:

| Primary metric | Secondary metric | Interpretation |
|----------------|------------------|----------------|
| `block_time_inaccuracy` (lower) | `jitter` (lower) | Accuracy vs. stability |
| `score` (lower) | `freq` (user‑declared) | Overall quality vs. resource cost |
| `block_time_inaccuracy` (lower) | `stability_width` (higher) | Accuracy vs. robustness |

#### 2.1.1 Availability of the `score` Metric

The per‑candidate `score` is not stored directly in the `.gunzmap` file.  The Dewaster may offer `score` as a trade‑off metric **only if** it can obtain the exact per‑candidate score that was computed by the scanner.  This is possible **only** when:

- A `.gunzstats` file is supplied, containing the raw per‑candidate statistics needed to recompute the full‑precision advance regularity and subsequently the score for **every** candidate; **and**
- The companion `.gunzmeta` file (or the map header) supplies the scan parameters `jitter_weight`, `advance_regularity_weight`, `mult_num`, `mult_den`, `quantum`, and `reference_block_time`.

If the `.gunzstats` file is not available, the Dewaster **SHALL NOT** include `score` in the list of selectable trade‑off metrics.  If the user requests `score` under these conditions, the Dewaster shall report an error and exit.

When `score` is selectable, the Dewaster shall recompute the exact score for each candidate using the formula in GUNZ 3.67.0 §3.11 Step 4, using the per‑candidate full‑precision advance regularity average derived from the `.gunzstats` records (not the saturated field from the map entry) to ensure deterministic output.

*(Informative: the `advance_regularity_btu` term in the GUNZ score formula is `advance_regularity_btu = (advance_regularity × mult_den × quantum) / (mult_num × 100)`, computed with half‑to‑even rounding per GUNZ 3.67.0 §3.11 Step 4.  The division by 100 converts advance regularity from ticks × 100 to tick units; the multiplier domain conversion is handled by the `mult_den × quantum / mult_num` factor.  The Dewaster must use this exact formula when recomputing `score`.)*

The `|total_time − reference_block_time|` term required by the score formula is equal to the `block_time_inaccuracy` value stored in the map entry **when the true absolute difference does not exceed `UINT32_MAX`**.  If the difference exceeds `UINT32_MAX`, the stored field is capped at `UINT32_MAX` and does not reflect the scanner's internal uncapped value used for the score.  For precise score recomputation in those edge cases, the Dewaster must use the raw `total_time` from the `.gunzstats` file (specifically `sum_block_time / block_count`).  Otherwise, the Dewaster shall use the stored `block_time_inaccuracy` directly.

### 2.2 Entry Filtering

Before the dominance check, the Dewaster shall exclude the following entries from consideration:

- **Long‑jump entries** (sentinel `run_length == 0` and `block_time_inaccuracy == 0`). These represent gaps in the scan, not operating points. *(Long‑jump entries represent unevaluated gaps; they are therefore excluded from both the Efficiency Horizon and the Doomfall candidate set.)*
- **Skipped entries** (`FLAG_SKIPPED` set). These were not evaluated.
- **Detrimental entries** (`FLAG_AVOID` set). These represent operating points the scanner itself has flagged as undesirable. Including them in the horizon would contradict the scanner's own assessment. A user may explicitly request their inclusion via a configuration flag (`--include‑avoid`), but the default is exclusion.

Additionally, when `stability_width` is among the selected trade‑off metrics, entries with zero `stability_width` are excluded. This prevents the horizon from being cluttered with points that have no measurable stability. If all entries in the map have zero stability width and this metric is selected, the resulting horizon will be empty — a correct reflection of the data. Users may choose to omit `stability_width` from the trade‑off set when scanning at coarse `time_unit`.

*(Informative: zero stability width is normative for all entries when `time_unit < 9`, and may also occur for individual entries at finer time‑units when the score tolerance is unrepresentably small.  Users who see an empty horizon and are scanning at a coarse `time_unit` should consider whether `stability_width` is a meaningful metric for their use‑case.)*

**Baseline selection for Doomfall:** Regardless of the `--include‑avoid` flag, the baseline used in the Doomfall algorithm is always chosen from **non‑avoided** horizon entries. If no non‑avoided horizon entry exists, the Doomfall cannot be computed and the algorithm shall report “No valid baseline available” and exit.

## 3. Reaching the Horizon – The Dewaster Algorithm

Given a GUNZ resonance map and a choice of trade‑off metrics with their directions, a conformant Dewaster shall determine the Efficiency Horizon by a deterministic procedure whose output depends only on the map and the metric selection.

**Normative dominance check:**
Let `M` be the list of consolidated map entries after applying the filtering rules of §2.2. An entry `A` dominates entry `B` if, for every trade‑off metric `m`:

- If `m` is “lower‑is‑better”: `A.m ≤ B.m`
- If `m` is “higher‑is‑better”: `A.m ≥ B.m`

and at least one of the inequalities is strict.

**Determining the horizon:**
The **Efficiency Horizon** is the subset of entries that are **not** dominated by any other entry. Any deterministic algorithm that produces this exact subset is conformant. The reference algorithm is the naive O(N²) pairwise comparison, which is sufficient for maps containing a few hundred consolidated entries. For larger maps, efficient skyline algorithms (e.g., O(N log N) after sorting) are permitted, provided they produce identical output.

**Output:** The Dewaster shall produce a list of frequency intervals (start‑freq, end‑freq) and their associated metrics for every entry that lies on the Efficiency Horizon. The output format is implementation‑defined; a companion file with extension `.gunzhorizon` is suggested.

## 4. Beyond the Horizon – The Doomfall (Normative)

The Efficiency Horizon tells the user which operating points are optimal given the declared trade‑offs. It does not, however, indicate which direction along the frequency axis leads to degradation. The **Doomfall** is an analysis that answers this question: *if I continue scanning in this direction, will things get worse?*

### 4.1 User Inputs for Doomfall

To compute the Doomfall, the user must supply the following inputs beyond those required for the horizon:

| Input | Description |
|-------|-------------|
| **Primary metric** | Which trade‑off metric is the user's primary concern. Must be one of the metrics selected for the horizon. |
| **Scan direction** | `increasing` (default) or `decreasing` — which direction along the frequency axis represents "forward" movement. |
| **Sufficiency threshold** (optional) | A numeric threshold for how much a secondary metric must improve to offset primary degradation. The threshold is expressed in the natural units of the secondary metric (e.g., nanoseconds for jitter, ticks×100 for advance regularity). The user is responsible for unit consistency. If omitted, any worsening of the primary metric is considered decisive regardless of secondary gains. |
| **Minimum Doomfall run** (`min_doomfall_run`, optional) | The minimum number of consecutive candidates that must satisfy the Doomfall inclusion condition for a Doomfall interval to be emitted. Recommended default is **5**. |
| **Baseline mode** (`baseline_mode`, optional) | One of `nearest` (default), `pareto`, `stability_window`, `stability_precise`, `adaptive_radius`. Determines how the baseline horizon entry is selected for each candidate. |
| **Baseline maximum distance** (`baseline_max_distance_hz`, optional) | (Used by `nearest`, `stability_window`, `adaptive_radius`) Maximum allowed frequency distance between a candidate and its baseline. Candidates farther away are unclassified. Default: `20.0` Hz. |
| **Adaptive radius factor** (optional, used by `adaptive_radius`) | Multiplier for step size when computing the adaptive radius. Default: `10`. |
| `.gunzstats` file | Required for `stability_precise` mode. |

All frequency‑domain parameters (`baseline_max_distance_hz`) are converted to 10⁻⁵ Hz internally using the conversion rules in §1.2.

> *Note:*  A single sufficiency threshold is applied to all secondary metrics.  Because secondary metrics may have different units and natural scales (e.g., nanoseconds for jitter, ticks × 100 for advance regularity), users must choose a threshold that is meaningful across all selected metrics, or use the same units for all secondary metrics.  The Dewaster does not perform unit conversion between different metric types.

### 4.2 Baseline Selection Modes

The Doomfall algorithm must select, for each candidate beyond the last horizon point, a **baseline** horizon entry against which degradation is measured. The selection method is determined by `baseline_mode`. All modes are optional to implement; if a mode is offered, its output must be deterministic for identical inputs. The modes are defined in the following subsections.

#### 4.2.1 `nearest` Mode

Select the non‑avoided horizon entry with the smallest absolute frequency difference to the candidate’s start frequency. In case of tie, pick the one with the better primary metric. If the distance exceeds `baseline_max_distance_hz` (converted to internal units), the candidate is **unclassified**.

#### 4.2.2 `pareto` Mode

Select a baseline using global metric dominance, independent of frequency.

- Collect all non‑avoided horizon entries that are **no worse** than the candidate in **every** secondary metric (i.e., for each secondary metric, the baseline’s value is not worse than the candidate’s according to that metric’s direction).
- If this set is non‑empty, pick the entry with the **best primary metric** (most favourable direction). In case of tie, pick the one with the smallest absolute frequency difference to the candidate.
- If the set is empty, the candidate is **unclassified**.

This mode answers: “Is this candidate behind the entire Pareto frontier in the primary metric, while offering no secondary advantage?”

#### 4.2.3 `stability_window` Mode (Heuristic)

Use the approximate stability intervals stored in the map entries.

- For each non‑avoided horizon entry with `stability_width > 0`, compute the symmetric stability interval:  
  `[ freq − sw_10uHz, freq + sw_10uHz ]`  
  where `sw_10uHz = stability_width × 10` (converts 0.0001 Hz to 10⁻⁵ Hz).
- Collect all horizon entries whose interval contains the candidate’s start frequency.
- If the set is non‑empty, pick the entry with the best primary metric (tie: smallest frequency distance).
- If the set is empty, the candidate is **unclassified**.

**Caveat:** The stability interval is a heuristic; the map entry stores only the total width, not the actual left/right boundaries. The symmetric interval centered on the entry’s start frequency may not correspond to the true stability region. Users requiring exact boundaries must use `stability_precise` mode with a `.gunzstats` file.

#### 4.2.4 `stability_precise` Mode (Requires `.gunzstats`)

Recompute the exact stability intervals from the raw per‑candidate statistics, with a deterministic alignment of `.gunzstats` records to candidate frequencies.

**Alignment procedure.**  To use the `.gunzstats` records, the Dewaster must pair each record with its corresponding candidate frequency.  This pairing shall be performed as follows:

1. **Perform sparse‑interval expansion** (§1.1 step 2) on the raw `.gunzmap` entries to obtain a complete, expanded list of entries covering the full scanned frequency range.  This expansion inserts synthetic zero‑metric entries for any frequency intervals that were omitted by the `sparse_map` mechanism.
2. **Filter out unevaluated entries.** From the expanded list, remove all long‑jump entries and entries with `FLAG_SKIPPED` set.  The remaining entries are the **evaluated entries** — those corresponding to candidates that were actually scanned by the evaluator.  This set includes both the original evaluated entries and the synthetic zero‑metric entries added during expansion (which represent candidates that were evaluated but omitted from the compressed map).
3. **Verify record count.**  Let `L_total` be the sum of `run_length` over these evaluated entries.  This is the total number of candidates that were actually evaluated.  The number of records in the `.gunzstats` file must equal `L_total`.  If they differ, the Dewaster shall abort with an error.
4. **Assign frequencies.**  Using the sequential frequency reconstruction method (§1.1 step 3) on the expanded map, determine the start frequency of each evaluated entry.  For each such entry with start frequency `f_start`, `step_freq`, and `run_length = L`, the candidate frequencies are `f_start`, `f_start + step_freq`, …, `f_start + (L−1) × step_freq`.  These frequencies are paired in order with the next `L` records from the `.gunzstats` file.

After alignment, the Dewaster has a list of tuples `(frequency, block_time_inaccuracy, sum_block_time, sum_block_time_sq, count_adv_lo, count_adv_hi, …)` for every evaluated candidate.  Using these data:

- The Dewaster recomputes the exact Phase 2 stability intervals \([L, R]\) for every candidate using the normative stability‑width algorithm (GUNZ 3.67.0 §3.11 Phase 2), yielding the true stability width and boundaries.
- It groups candidates into contiguous **stability valleys**: a maximal contiguous sequence of candidates (in frequency order) where the stability intervals overlap or touch (i.e., the end of one interval ≥ start of the next interval). Each valley has an associated set of horizon entries that fall within it. If a valley contains no horizon entries, candidates in that valley are **unclassified** for Doomfall.
- For a candidate beyond the last horizon point, the baseline is the horizon entry belonging to the same stability valley as the candidate. If the candidate lies outside any valley, it is **unclassified**. If the valley contains multiple horizon entries, pick the one with the best primary metric (tie: smallest frequency distance).

This mode provides the most precise Doomfall baseline, directly derived from the scanner’s own stability logic.

#### 4.2.5 `adaptive_radius` Mode

A heuristic that uses the map’s step size and horizon density to define a local frequency radius.

- Compute the median absolute frequency gap between consecutive non‑avoided horizon entries. If there are fewer than 2 horizon entries, use the map’s `step_freq` (converted to Hz) times `adaptive_radius_factor`.
- Compute radius `r = max( step_freq_hz × adaptive_radius_factor, median_gap )`. Both terms are converted to 10⁻⁵ Hz internally.
- Find all non‑avoided horizon entries within `r` of the candidate’s start frequency (absolute distance ≤ `r`). Among them, pick the entry with the best primary metric (tie: smallest frequency distance).
- If no horizon entry lies within the initial radius `r`, the radius shall be doubled repeatedly.  At each step, the set of horizon entries within the new radius is re‑evaluated.  The process stops when at least one horizon entry is found or the radius exceeds `baseline_max_distance_hz`.  If the maximum distance is exceeded without finding a horizon entry, the candidate is unclassified.

### 4.3 Deterministic Doomfall Algorithm

**Prerequisite guard.** If the Efficiency Horizon is empty, or no non‑avoided horizon entry exists, the Doomfall is undefined. Report “No valid baseline” and exit.

**Consolidation requirement.** Before the Doomfall algorithm begins, the Dewaster **shall** apply map‑entry consolidation (§1.1 step 4) to the filtered entry set.  Consecutive entries with identical metrics and flags must be merged.  This ensures that all implementations operate on the same set of candidates, preventing fragmentation from affecting run‑length detection.

1. **Compute the Efficiency Horizon** \(H\) and let \(D\) be all other consolidated entries that passed filtering (§2.2) but are not on the horizon.

2. **Sort** \(D\) in ascending order of start frequency (or descending if `scan_direction = decreasing`).

3. **Identify the last horizon point** in the scan direction. Let \(f_{\text{last\_h}}\) be the frequency of the horizon entry with the highest frequency (lowest, for `decreasing`). All entries in \(D\) with start frequency beyond \(f_{\text{last\_h}}\) are **candidates**.

   Synthetic entries generated by sparse‑interval expansion (§1.1 step 2) — i.e., entries with all quantitative metrics zero and `flags = 0` that were not present in the original `.gunzmap` file — **shall be excluded** from the candidate set.  These entries represent perfect‑resonance points that were never evaluated by the scanner; they cannot satisfy the Doomfall inclusion condition and may interfere with run‑length counting.

   *Design note:*  The Doomfall analysis only considers candidates whose frequency lies beyond the last (or before the first, for decreasing scans) horizon entry in the scan direction.  Degradation that occurs between separated horizon peaks — i.e., at frequencies that are not beyond the global frontier — is not flagged by this algorithm.  This choice reflects the Dewaster's role as a “stop signal” for continued scanning in a given direction, not a comprehensive audit of all sub‑optimal regions.  Users who need to identify degraded zones between horizon peaks should inspect the Efficiency Horizon gaps directly.

4. **For each candidate** \(E\), in frequency order:
   - Invoke `select_baseline(E, H, baseline_mode, …)` as defined in §4.2. If the result is `unclassified`, skip the candidate (does not contribute to any run).
   - Let `h` be the selected baseline.
   - Compute \(\Delta_{\text{primary}}\) as the change in the primary metric from `h` to `E`. Positive means worsening (higher for lower‑is‑better; lower for higher‑is‑better).
   - For every secondary metric \(m\), determine if `E.m` is strictly better than `h.m`. If yes, record improvement magnitude \(\delta_m\).
   - **Inclusion condition:** `E` is added to the Doomfall if **all** of the following hold:
     - \(\Delta_{\text{primary}} > 0\) (primary metric strictly worsened).
     - For every secondary metric that improved, the improvement \(\delta_m\) is below the user‑supplied sufficiency threshold (if provided). If no threshold is provided, any strict worsening of the primary qualifies regardless of secondary improvements.
   - If the user selected **only** the primary metric as a trade‑off metric (i.e., there are no secondary metrics), the sufficiency‑threshold condition is vacuously satisfied.  The inclusion condition then reduces to: the primary metric must strictly worsen.

5. **Apply minimum sustained degradation.** Let the classified candidates be a sequence of Boolean values (Doomfall / non‑Doomfall). A Doomfall interval shall consist of at least `min_doomfall_run` consecutive Doomfall‑positive candidates. Shorter runs are discarded.

6. **Trailing‑edge exception.** If a run of consecutive Doomfall‑positive candidates extends to the last candidate in the scan (map boundary) and has length at least 1 but less than `min_doomfall_run`, it is emitted as a trailing‑edge Doomfall.  The interval shall be marked with `trailing_edge: true`.  Additionally, if the map boundary was caused by the global iteration limit (`total_max_scan_iterations`), the interval shall also be marked with `boundary_artificial: true` to distinguish it from a natural resonance cliff.

7. **Merge adjacent runs.** Adjacent Doomfall runs separated by gaps of fewer than `min_doomfall_run` non‑Doomfall candidates **shall** be merged into a single interval **only if** every candidate in the gap failed solely because its run was too short (i.e., it satisfied the inclusion condition in step 4 but was dropped in step 5). If any candidate in the gap failed due to primary metric improvement, no change, or a secondary threshold exceedance, the gap is a hard boundary and runs are not merged. Merging produces a single continuous frequency range.

   Candidates classified as `unclassified` (no baseline found) in step 4 are treated as a hard boundary for the purpose of run merging: adjacent Doomfall runs separated by an unclassified candidate shall not be merged, regardless of the length of the gap.

8. **Output** Doomfall intervals with start/end frequencies, metrics, and any `trailing_edge` and `boundary_artificial` flags.

### 4.4 Interpretation

The Doomfall identifies regions where the primary metric is degrading and secondary metrics are not improving enough to compensate. It is a natural stop‑signal for an autonomous agent. For a human engineer, it is a warning that the trade‑off has turned unfavourable.

---

## 5. Relationship to the Phoenix Mechanism

When chaining scans, the Dewaster can serve as convergence detector and stop‑signal generator:

- **After each scan**, compute the Efficiency Horizon.
- **Compare** the current horizon to the previous scan’s horizon; if substantially unchanged, the agent has likely converged.
- **If Doomfall is enabled**, stop scanning if the current range extends into a Doomfall region.
- **Before refining the reference**, verify that the calibrated reference lies on the current horizon; if not, update it.

## 6. Relationship to ORACLE

| Tool | Question Answered | When to Use |
|------|-------------------|-------------|
| **ORACLE** | "Where are frequencies satisfying these constraints?" | Before a full scan, to narrow the search range. |
| **DEWASTER** | "Among already scanned frequencies, which are the best trade‑offs?" | After a scan, to interpret results and decide whether to continue. |

ORACLE finds promising regions; DEWASTER evaluates what was found.

## 7. Integration with GUNZ

The Dewaster is an **external tool**. It operates on existing `.gunzmap` files. No new GUNZ opcodes, map versions, or header fields are required.

A conformant Dewaster:

- Shall accept a `.gunzmap` file and a specification of trade‑off metrics.
- Shall perform map preprocessing (§1.1).
- Shall apply filtering (§2.2).
- Shall produce a deterministic Efficiency Horizon (§3).
- Shall implement one or more Doomfall baseline modes (§4.2) and the associated Doomfall algorithm (§4.3). If a mode is supported, its output must be deterministic.
- May annotate the map by writing a companion file (e.g., `.gunzhorizon`).

The Dewaster is **not required** for GUNZ conformance.

## 8. Interpretation Notes *(Informative)*

**Choosing trade‑off metrics:** The same map can have different horizons depending on what the user values. There is no single “true” horizon — only the horizon corresponding to the declared goal.

**Detrimental entries and `--include‑avoid`:** By default, `FLAG_AVOID` entries are excluded. With `--include‑avoid`, they appear in the horizon but are never used as Doomfall baselines.

**Non‑convex trade‑offs:** The Efficiency Horizon does not assume convexity. Gaps indicate no operating point fills that trade‑off region. The Doomfall analysis relies only on local comparisons and is independent of convexity.

**Decision‑support, not enforcement:** The Dewaster makes the trade‑off visible. The human (or AI) retains full authority.

---

## 9. Conformance

A conformant GUNZ‑DEWASTER implementation must:

- Accept a valid GUNZ `.gunzmap` file.
- Accept user‑specified trade‑off metrics with directions.
- Apply map preprocessing (§1.1).
- Apply entry filtering (§2.2).
- Implement the dominance check (§3) and produce a deterministic Efficiency Horizon.
- Implement one or more Doomfall baseline modes (§4.2) and the Doomfall algorithm (§4.3). Each implemented mode must produce deterministic output.
- Not modify the original `.gunzmap` file unless writing a separate annotated copy.

## 10. Example

Given a map covering 200–250 Hz, trade‑off set `(block_time_inaccuracy, jitter)` (both lower‑is‑better), the Efficiency Horizon might be:

```
Efficiency Horizon (block_time_inaccuracy vs jitter):
  [199.99999 – 200.00000]  inaccuracy=0.000  jitter=0.00
  [209.79000 – 209.80000]  inaccuracy=1.200  jitter=0.00
  [249.99999 – 250.00000]  inaccuracy=10.500  jitter=0.00
```

Now consider the Doomfall with primary `block_time_inaccuracy`, scan direction `increasing`, no sufficiency threshold, `min_doomfall_run=5`, and `baseline_mode=nearest` (`baseline_max_distance_hz=20`). The candidate at 250.1 Hz has inaccuracy 10.6, jitter 0.0; its baseline is the 250 Hz horizon entry (inaccuracy 10.5). Δ_primary = +0.1 → Doomfall‑positive. Subsequent candidates may form runs that are filtered and merged as described.

Using `baseline_mode=pareto` on the same data, a candidate far away that is worse in both metrics would still be flagged; a candidate that improves jitter might escape classification, depending on secondary metric improvements.

Different modes answer different questions, producing distinct Doomfall intervals for the same map. The Efficiency Horizon, however, remains invariant across all modes—it is the single, canonical answer to “what are the best trade‑offs?”
