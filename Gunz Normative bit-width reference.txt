# GUNZ 5.0.0 — Normative Bit‑Width Requirements  
**Companion Reference**

*This is a non‑normative companion to GUNZ 5.0.0. It reflects the bit‑width requirements as they appear in the core specification, including the Fixed Safe Profile parameter caps of §3.4.1. All normative statements belong to the main specification; this document exists to explain the rationale.*

---

The required bit‑widths are not arbitrary; they are the **smallest widths that are mathematically safe for all valid parameter combinations** under the Fixed Safe Profile. Implementers may not choose a narrower type even if they believe a particular input combination will not overflow, because the specification is designed to be safe for **all valid parameter combinations** — including worst‑case `time_unit`, maximum `mult_num`, minimum `quantum`, and extreme `N`.

The one exception is the **standard deviation accumulation width relaxation** described in §4.5.3: an implementation *may* use narrower intermediates **if and only if** it can mathematically prove that the resulting standard deviation is bit‑identical to the output of the 256‑bit computation for all inputs within the normative bounds. For all other operations, the listed bit‑widths are mandatory.

---

## What changed in GUNZ 5.0.0

GUNZ 5.0.0 is a major revision. Relative to earlier GUNZ versions, the following changes affect arithmetic bit‑widths:

- **Scalar score removed.** The evaluator no longer computes a single combined score. Instead it produces three independent lower‑is‑better metrics: `block_time_inaccuracy`, `jitter`, and `advance_regularity`. There is no longer a “score” whose sum requires 128‑bit accumulation. Each metric is saturated individually.

- **Fixed Safe Profile caps introduced.** §3.4.1 imposes normative maximum parameter values for implementations using 128/256‑bit exact runtimes: `target_ticks ≤ 2²⁵`, `quantum ≤ 2³⁰`, `mult_num ≤ 2²⁰`, `mult_den ≤ 2²⁰`, `window_duration ≤ 2⁴⁵`, `time_unit ≤ 12`. These caps drastically reduce the worst‑case numeric ranges compared to earlier drafts that allowed `u32` maxima throughout. All bit‑width analysis below assumes these caps.

- **Standard deviation algorithm changed.** The old `isqrt_rounded` has been removed. The new algorithm is **exact rational** with `isqrt_floor` and an integer midpoint comparison. This affects the intermediate widths for `S2`, `V`, `D`, `var_floor`, `midpoint_x4`, and `V_x4`.

- **`.gunzstats` record expanded to 96 bytes** with `u128` accumulators for sums and sums‑of‑squares, and a new `u64` `advance_regularity_full` field. These are specified to saturate at `2¹²⁸−1` rather than wrap.

- **Advance regularity now uses the mandatory two‑valued closed form.** It has no `S` or `S2` accumulator. Only `V` and `D` are computed, both in 256‑bit arithmetic. The general sample‑by‑sample algorithm is used only for total block‑time jitter and other non‑two‑valued metrics.

## Normative Bit‑Width Requirements

| Operation | Minimum Bits | Notes / Bounds (under Fixed Safe Profile) |
|-----------|--------------|--------------------------------------------|
| Parameter storage (header fields, map entries, frequency values) | 64‑bit | All stored fields use `u32`/`u64` or smaller. |
| Cycle time `T` | 64‑bit | `T = 10^(time_unit+5) / freq_candidate`. For `time_unit ≥ 10`, numerator may be computed in 128‑bit before division (encouraged but not required). |
| Continuous deltas `d_lo_cont`, `d_hi_cont` | 64‑bit | Derived from `T / quantum`. |
| `N` (cycle count) | 64‑bit | Bounded by `MAX_N = 2³¹−1`. |
| `N × T` | **128‑bit** | Used in `R = round(N × T / quantum) × quantum`. Under caps: `N ≤ 2³¹−1`, `T ≤ 10¹⁷` ⇒ product ≤ 2.1×10²⁶, exceeds 64‑bit. |
| `R`, `Q = R / quantum`, `N_hi = Q − N × d_lo_cont` | **128‑bit** | All derived from the 128‑bit `N×T`. |
| Block time (DELTA override) | **128‑bit** | `((N−N_hi)×d_lo_ov + N_hi×d_hi_ov) × quantum`. With `d_lo_ov,d_hi_ov ≤ 2³²−1`, `N ≤ 2³¹−1`, `quantum ≤ 2³⁰` (cap), worst case ≈ 2×10⁶⁸, which fits 128‑bit. |
| `(hold_cycles + sep_cycles) × T` | **128‑bit** | `hold_cycles+sep_cycles ≤ 510`, `T ≤ 10¹⁷` ⇒ product ≈ 5.1×10¹⁹, exceeds 64‑bit. |
| `total_time`, `|total_time − reference_block_time|` | **128‑bit** | Computed with 128‑bit arithmetic; result saturated to `UINT32_MAX` for storage. |
| `block_time_inaccuracy` (long‑term exact rational mean) | **256‑bit** | `sum_total` and `ref_scaled` use 256‑bit unsigned; division half‑to‑even. |
| `advance_regularity_btu` numerator | **128‑bit** | `(avg_advance_regularity_internal × mult_den × quantum)`. Under caps: max ≈ 5.9×10²², far below 2¹²⁸. |
| Sum `S = Σ xᵢ` (jitter only) | **128‑bit** | Used only by the general standard deviation algorithm for total block‑time jitter. |
| Sum of squares `S2 = Σ (xᵢ)²` (jitter only) | **256‑bit** | Used only by the general standard deviation algorithm for total block‑time jitter. |
| Advance‑regularity variance numerator `V` | **256‑bit** | `V = n_a · n_b · (a − b)²`. Closed form only; no `S`/`S2`. |
| Advance‑regularity denominator `D` | **256‑bit** | `D = n²`. Closed form only. |
| General variance numerator `V` (jitter) | **256‑bit** | `V = n·S2 − S²`. General algorithm only. |
| `D = n²` (general algorithm) | **256‑bit** | Under the Fixed Safe Profile with `DELTA`, the jitter sample count `n` can reach `2^55`, so `D = n² < 2^110`. 256‑bit is more than sufficient. |
| `var_floor = V // D` | **256‑bit numerator** | Floor division of 256‑bit by 256‑bit. |
| `q = isqrt_floor(var_floor)` | **256‑bit input** | `var_floor` may be up to 2²⁵⁶; `isqrt_floor` returns up to 2¹²⁸. |
| `midpoint_x4 = D × (4q² + 4q + 1)` | **256‑bit** | Under caps, product fits in 256‑bit. |
| `V_x4 = 4 × V` | **256‑bit** | `V` is 256‑bit; multiplying by 4 could exceed 256 bits, but in practice under caps `V` is far below 2²⁵². Spec requires 256‑bit; implementations may use 256‑bit with overflow checks or prove safety. |
| Sparse‑map accumulator (§4.2) | **128‑bit signed (`s128`)** | Accumulates `run_length × effective_step` over many omitted intervals. `effective_step ≤ 2³²−1`, `run_length ≤ 65535` ⇒ per‑interval gap ≤ 2⁴⁸; many intervals can sum beyond 2⁶³−1. |
| Long‑term cumulative block time (§3.11 step 3) | **128‑bit unsigned** | Sum of raw block times compared against `window_duration ≤ 2⁴⁵`; a 64‑bit accumulator would overflow. |
| Ceiling division for `max_eval_iterations` (§3.4.2) | **128‑bit for `a + b - 1`** | `ceil(window_duration / quantum)`: `window_duration ≤ 2⁴⁵`, `quantum ≥ 1`, addition safe in 128‑bit. |
| `.gunzstats` cumulative sums (`sum_block_time`, etc.) | **128‑bit unsigned** | Stored as `u128` and saturated to `2¹²⁸−1`. |

**Implementers must not use narrower arithmetic than stated here.** Wider arithmetic is always permitted. The requirements apply to all profiles and all valid parameter combinations under the Fixed Safe Profile. If an implementation uses the alternative extended‑range compliance path of §3.4.1, it must provide its own formal overflow proof.

## Why 128‑bit for `N × T`

- `N` can be as large as `2³¹ − 1` (≈ 2.1 × 10⁹).  
- `T` can reach `10^(time_unit+5)`. With `time_unit = 12` and `freq_candidate = 1`, `T = 10¹⁷`.  
- Their product is ≈ 2.1 × 10²⁶, which is **larger than `2⁶⁴`** (≈ 1.8 × 10¹⁹).  
- 64‑bit would overflow; 128‑bit is the next safe width. So this requirement is exact.

## Why 128‑bit for block time with DELTA overrides

- The override values `d_lo_ov` and `d_hi_ov` are `u32` (max 2³²−1).  
- `quantum` is capped at `2³⁰` by the Fixed Safe Profile.  
- The sum `(N−N_hi)×d_lo_ov + N_hi×d_hi_ov` can be ≈ `N × 2³²`. Multiplying by `quantum` gives a value up to `N × 2⁶²` ≈ 2.1 × 10⁹ × 4.6 × 10¹⁸ ≈ 9.6 × 10²⁷, which fits comfortably in 128‑bit.

## Why 128‑bit for `(hold_cycles + sep_cycles) × T`

- `hold_cycles` and `sep_cycles` are `u8`, so their sum is ≤ 510.  
- `T` is at most 10¹⁷.  
- The product is ≈ 5.1 × 10¹⁹, which is **just above `2⁶⁴`** (1.8 × 10¹⁹). So 64‑bit would overflow; 128‑bit is needed.

## Why 128‑bit is sufficient for `advance_regularity_btu`

The product is `avg_advance_regularity_internal × mult_den × quantum`. We bound each factor under the Fixed Safe Profile:

- **`avg_advance_regularity_internal`** – the per‑jitter‑point population standard deviation of the two per‑cycle advance values `a = 100 × adv_lo_cont` and `b = 100 × adv_hi_cont`. For a two‑valued multiset, the standard deviation is at most `|a − b| / 2`.  
  The difference `|adv_hi_cont − adv_lo_cont|` is bounded by `ceil(mult_num / mult_den)`. With `mult_den = 1`, this is `mult_num ≤ 2²⁰`. Therefore `|a − b| ≤ 100 × 2²⁰ = 104,857,600`, and the standard deviation is at most **52,428,800** ticks×100.

- **`mult_den`** – capped at `2²⁰` by the Fixed Safe Profile.

- **`quantum`** – capped at `2³⁰`.

Product bound:

```
52,428,800 × 2²⁰ × 2³⁰ = 52,428,800 × 2⁵⁰ ≈ 5.9 × 10²²
```

This is far below `2¹²⁸` (≈ 3.4 × 10³⁸). **128‑bit arithmetic is entirely safe** for the numerator.

## Why 256‑bit for sum of squares (`S2`) and variance numerator (`V`) — jitter path

This section applies only to **total block‑time jitter**, which uses the general sample‑by‑sample algorithm. Advance regularity does not use `S2`; it uses the mandatory closed form, whose `V` and `D` are proven in Appendix G to fit in 256 bits.

For jitter, the required 256‑bit width is proven in **Appendix G**, which bounds:

```text
S2_total < 2^186
```

under the Fixed Safe Profile caps. Consequently:

```text
V = n·S2 − S²
  < n·S2
  < 2^55 × 2^186
  = 2^241
```

Both `S2` and `V` fit comfortably in 256 bits.

## Why 256‑bit is required for the standard deviation division and square root

After `V` and `D` are obtained — either from the general algorithm for jitter or from the closed form for advance regularity — the exact rational standard deviation step uses:

- `V` is a 256‑bit quantity.
- `D = n²` can be up to `2^110` (jitter) or `2^110` (advance regularity under the corrected bound).
- `var_floor = V // D` requires 256‑bit division.
- `q = isqrt_floor(var_floor)` requires a 256‑bit input.
- `midpoint_x4` and `V_x4` are 256‑bit intermediates.

Therefore the final steps are identical for both metrics and require 256‑bit arithmetic.

## Additional requirements for sparse‑map and long‑term accumulators

- **Sparse‑map accumulator** – Must be a signed 128‑bit integer (`s128`). It accumulates gaps of `run_length × effective_step`. Under caps, `run_length ≤ 65535`, `effective_step ≤ 2³²−1`, so each gap ≤ 2⁴⁸. Many intervals can sum beyond 2⁶³−1, so 64‑bit would silently wrap. The overflow‑reduction algorithm (§4.2) relies on detecting when the accumulator exceeds `max_lj_gap` or the `s16` delta range. A 64‑bit accumulator would produce invalid maps.

- **Long‑term cumulative block time** – Must be accumulated in an unsigned 128‑bit integer. In long‑term mode, the evaluator repeats blocks until the total (excluding hold/sep) reaches `window_duration`, which can be up to 2⁴⁵. A 64‑bit accumulator would overflow after a few blocks of large `N×T`.

- **Ceiling for `max_eval_iterations`** – When computing `ceil(window_duration / quantum)`, the addition `window_duration + quantum - 1` must be performed in 128‑bit. With `window_duration ≤ 2⁴⁵` and `quantum ≥ 1`, overflow is not a risk, but the formula requires 128‑bit for safety.

## Beginner’s Pitfalls

**1. Storage width ≠ computation width.**  
Fields like `block_time_inaccuracy` are stored as `u32`, but the subtraction `|total_time − reference_block_time|` must be computed in **128‑bit** before being saturated down to 32‑bit. Beginners often do the subtraction directly in 32‑bit, causing silent overflow.

**2. Saturation vs. overflow.**  
Saturation happens *after* the exact computation. You must compute the value in a wide type first, then clamp it to the field width. Computing in a narrow type that overflows first is a bug.

**3. No scalar score.**  
GUNZ 5.0.0 does not compute a single combined score. There is no need for a 128‑bit score sum. Each metric (`block_time_inaccuracy`, `jitter`, `advance_regularity`) is stored and saturated independently.

**4. When 256‑bit is truly mandatory.**  
The jitter general algorithm and the advance‑regularity closed form both require 256‑bit accumulators for `V`, `D`, `var_floor`, `midpoint_x4`, and `V_x4`. The jitter general algorithm additionally requires 128‑bit `S`. Most other operations fit in 128‑bit or less.

**5. Signed vs. unsigned.**  
Almost all arithmetic is unsigned. The main exception is the sparse‑map accumulator, which is **signed** because gaps can accumulate and be stored as `freq_delta_start` (`s16`). Using an unsigned accumulator there would break the overflow‑detection logic.

## Engineer’s Quick Reference Checklist

- [ ] `N × T` → 128‑bit
- [ ] `R`, `Q`, `N_hi` → 128‑bit
- [ ] DELTA block time → 128‑bit
- [ ] `(hold+sep) × T` → 128‑bit
- [ ] `total_time` and subtraction → 128‑bit
- [ ] Long‑term `block_time_inaccuracy` exact rational mean → 256‑bit
- [ ] `advance_regularity_btu` numerator → 128‑bit
- [ ] Standard deviation `S` → 128‑bit (jitter only)
- [ ] Standard deviation `S2`, `V`, `D`, `var_floor`, `midpoint_x4`, `V_x4` → 256‑bit (unless relaxation proven)
- [ ] Advance‑regularity `V` and `D` → 256‑bit closed form (no `S`/`S2`)
- [ ] `isqrt_floor` input → 256‑bit (output ≤ 128‑bit)
- [ ] Sparse‑map accumulator → 128‑bit signed
- [ ] Long‑term cumulative block time → 128‑bit unsigned
- [ ] Ceiling for `max_eval_iterations` → 128‑bit for the addition
- [ ] `.gunzstats` cumulative sums → 128‑bit unsigned, saturate at `2¹²⁸−1`

## Where relaxation *is* allowed

The only place the specification permits narrower arithmetic is for the standard deviation accumulators (`S2`, `V`, and related 256‑bit intermediates). An implementation **may** use 128‑bit intermediates instead of 256‑bit **if and only if** it can mathematically prove that the resulting standard deviation is bit‑identical to the 256‑bit result for all valid inputs (§4.5.3). This is a high bar; most implementations will simply use 256‑bit.

For every other operation, the stated bit‑widths are the minimum safe widths and cannot be reduced.

---

## Could we have over‑estimated any of them?

No. Every width requirement can be triggered by a legal combination of parameters within the Fixed Safe Profile, or by the extended‑range alternative if formally proven. For implementations using the standard caps, the specified widths are exactly what is needed to guarantee correctness across the entire parameter space.

If you are concerned about performance on platforms without native 128‑ or 256‑bit arithmetic, note that software emulation is acceptable and typical for these wide integer operations. The Minimal Profile still requires the evaluator’s heavy arithmetic, but the absence of dynamic lane and callbacks reduces other overhead.
